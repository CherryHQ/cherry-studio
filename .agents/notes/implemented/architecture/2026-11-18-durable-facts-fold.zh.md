# Agent Note: 以折叠方式派生 Durable behavior 事实与观测

Status: implemented

[English](2026-11-18-durable-facts-fold.md) | 中文

## 问题

此前，Pi Durable 的各个使用方都从已提交日志重新计算出当前状态，Cherry 又在好几层重复这样做。#24500 的负载（一个会话约 5,500 条历史、12 个以上子智能体，并带内联图片）让每次重算都既昂贵又频繁：

- **behavior 事实。** [`agent-behavior`](../../proposed/architecture/2026-10-18-agent-behavior-package.md) 把事实定义为完整谱系的历史、已出现的 key，以及直接子对话的事实。Durable 适配器每次读取都重新组装它们。#24714 之后只读新增的条目，但每次读取仍要：
  - 扫描本对话和每个子对话的全部任务；
  - 用缓存里的全部条目重算历史；
  - 对每个子对话，按每个保留的运行查一次 submission，并把子对话的整段历史加总。

  每次工具调用（审批钩子）、每个 behavior 步骤的两到四次、每次提交输入，以及给子智能体发消息、等待回答和停止时都会读取。发消息和等待回答这两条路径还会不经任何缓存、连同图片扫描子对话的完整历史。
- **运行时观测。** 适配器每次发布提交和每次实时预览，都对已加载的历史重跑 `historyOf`。每次更新都发布完整快照，尽管观测合约也有 `message.upsert`、`message.remove` 和 `input.changed`。
- **主进程投影。** 每次更新都是快照，所以 Main 每次更新都要按每条历史输入解析一遍上下文行。`ChildThreadProjection` 每次刷新都会重读、重新装饰并重写每个活跃子对话的 archive 和 checkpoint。

#24714 加的缓存减少了条目读取，但没有去掉重算，而且它跟着运行时一直存在，没有淘汰。

这套设计要保证的几件事，都不需要每个事件重算一次：

- 决定和它的写入在同一个提交里；
- 带 key 的操作至多执行一次；
- 只靠日志就能恢复；
- 观测出现缺口后能恢复。

`agent-behavior` 已经写明了增量实现需要满足的性质，即回放不变量 I3：增量缓存等于全量重算。

## 决定

每一份派生状态都是带游标的日志折叠：按提交顺序，对每个新条目和新任务应用同一个 reducer。重建就是从空状态应用同一个 reducer，所以增量结果在构造上就等于重建结果；折叠状态随时可以丢弃，不影响结果。折叠只放在内存里，日志仍是唯一的权威来源。

### P1 — Durable 适配器里的 behavior 事实（#24814）

- **每个对话一份折叠。**
  - 折叠归运行时的 Session 所有，behavior harness 和运行时共用。
  - 折叠里存：历史、key 集合、子对话 id、来源和计划记录、工具任务的 call key、运行 id、每次运行的保留记录和用量、每次运行的最后一条回复，以及最近一次 assistant 的调用集合。
  - 不存条目正文，也不存图片。
- **在事务内追平。** 读取前，折叠分三步推进：
  - 读游标之后的新条目。
  - 按谱系里的每个对话，从新到旧读比已知最新任务更新的任务。任务 id 在同一条提交线上按提交顺序分配，任务也从不删除。
  - 只对还可能变化的状态做点读：没结束的 behavior 任务、最新的 generation 任务，以及 submission 还没绑定运行的保留记录。

  `LiveDoc`、`InboxDoc` 和用量汇总文档仍然是点读。事务写过之后就不能再读（`ReadAfterWrite`），所以折叠只会推进到已提交的状态。
- **迟到的工具任务。** 顺序执行的工具轮次，会在 assistant 条目之后才创建后面几个调用的任务。这种任务会就地更新那个调用的 key，以及通过这个调用解析出 key 的工具结果。
- **事实。** `readFacts` 用本对话和直接子对话的折叠组装 `ConversationFacts`。事实的结构和决策代码都没有变。
- **只读所需部分。**
  - 工具审批钩子从本对话的折叠里读计划、目标轮次和调用窗口，不读子对话。
  - 步骤里的追加校验只在追加不进入运行的输入（quiet input）时，点读目标对话是否空闲。
  - 给子智能体发消息、等待回答和停止，读子对话的折叠，不再读它的历史。
- **生命周期。** 10 分钟没被用过的折叠在下次读取时丢弃；Session 关闭时丢弃全部折叠。

### P2 — 运行时观测（#24817）

- 运行时发布的历史复用对话的折叠，不再每次发布和预览都重跑 `historyOf`。
- 适配器在第一次发布时、每次 `gap` 之后和运行开始时发布 `snapshot`，因为 Main 靠这些快照识别自主回合。其他更新只为改动的部分发布 `message.upsert`、`message.remove` 和 `input.changed`；活动状态变化（包括运行结束）时再加一条 `activity.changed`。如果一次更新的改动无法还原新的消息顺序，就改为发布快照。完成信号随该次更新的最后一帧送达。

### P3 — 主进程投影（#24818）

- Main 只处理一次更新里改动的输入，不再处理快照里的每一条输入。
- `ChildThreadProjection` 保留原有的 archive 读取时机，因为 Claude Code 和 Pi 的子对话也共用它，而只有 Durable 的实时 ID 等于 archive ID。它的已提交投影在多次读取之间保留，所以一次读取只重新装饰源有变化的消息，checkpoint 和响应归属也只在变化时才写入。一条消息只有在和已存行从 JSON 读回的样子（其中值为 undefined 的字段不存在）不同时才保存，所以重新打开子对话不会重写任何消息；打开时只读一次 archive。
- 运行结束以 `activity.changed` 送达 Main，由它携带完成信号。运行开始时仍然发送快照：Durable 把每个观测事件单独作为一批投递，如果运行开始也用增量，Main 会在开始自主回合之前就投影这次运行的内容、放置 steer。

### 不在范围内

- 消息 part 存储和界面按 key 订阅：#24019 那条栈。
- 图片和超大工具输出的存储：#24650 和 #23873。
- 进程内网关调用，#24650 已推迟。
- Pi 适配器：它的事实读的是内存里的分支，不读存储。
- 把上下文 checkpoint 改成按行存储：它每个回合写一次，之后有修改再写，子对话投影也不再每次刷新都重写它。

## 考虑过的替代方案

- **保留 #24714 的缓存，只限制它的生命周期。** 它缓存的是折叠的输入，不是结果：每次读取仍要重算历史，并重新扫描任务、子对话的 submission 和用量。
- **把折叠作为 Durable 文档，在同一个提交里写入。** 重启后还在，但事实包含完整历史，每个提交都要重写一份很大的文档，而且每个 Durable 写入方都得维护它。每个 Session 重建一次，比每个提交都写一次便宜。
- **把 `Ledger.read` 换成按调用点的查询。** 这会打破"决定只依赖事实"的规则，还要改 `agent-behavior` 和两个适配器。折叠保留了合约，同时去掉了开销。
- **用 `observeCommits` 推进折叠。** 发布在存储完成后一个宏任务才到，事务可能在折叠看到上一个提交之前就开始了。在事务内追平是精确的，代价只是一次有上限的扫描。

## 后果

- 一个对话在某个 Session 里第一次被读取，或闲置 10 分钟之后再被读取时，会从日志重建折叠；之后的读取只付出新提交行的代价。
- 折叠有缺陷时，得到的是错误的事实，而不只是慢。折叠不持久化，所以之后发现状态有误，丢弃折叠就能修复。
- 从新到旧扫描任务，依赖 Durable 按提交顺序分配任务 id，条目读取已经依赖同样的前提。如果将来某个 Durable 版本不按顺序接纳提交，任务就需要一个提交游标。
- 子对话运行的用量先加汇总用量，再把条目用量作为一个总和加上。当这次运行有原生压缩汇总时，`costUsd` 可能和以前的加法顺序在最后一位浮点数字上不同。
- 观测方要从 upsert 或重放后的视图读取一次运行的最终内容，不能再依赖运行结束时的快照。
- 在 #24500 的负载形态上，主进程分配减少三分之一，峰值堆内存减少 35%。界面读取消息列表的开销、每轮约 43 MB 的保留堆增长，以及随子任务累积而增长的每轮读取，仍然存在。
- 本 note 在 Spec PR #24813 获得批准之前，按作者的决定改为 implemented。

## 验证

- AC1 — `tests/factsFold.test.ts` 运行所有适用的 `agent-behavior` 合约用例，每次读取都在同一个事务里把已预热的折叠和从空重建的折叠对比，没有不一致；`tests/history.test.ts` 检查迟到的工具任务在任意折叠顺序下得到相同的 key，以及已预热和空折叠读到相同的事实，包括只读到某条较早条目的读取；去掉迟到任务的 key 改写，这两处测试都会失败（#24814）。
- AC2 — `tests/factsFold.test.ts`"reads only unseen rows on repeated facts reads and on the child answer and stop paths"：经计数事务，重复读取读 0 条条目、0 次任务点读、0 个 submission，每个谱系对话至多读一行任务；追加一条条目后的读取读 1 条条目（#24814）。
- AC3 — 同一个测试里，对已结束的子对话调用 `awaitAnswer` 和 `stop` 读 0 条条目，合约套件表明结果不变；工具审批钩子只推进本对话的折叠、quiet input 校验只读 `LiveDoc` 和 `InboxDoc`，以及发消息路径，由检查 `src/behavior/harness.ts` 的代码确认，没有计数测试（#24814）。
- AC4 — 10 分钟内用过的折叠保持预热（读 0 条条目），更久没用的会重建（读 3 条条目）且事实相同；`runtime.ts` 里 Session 关闭时的清理没有运行时层面的测试（#24814）。
- AC5 — 每一层的 `pnpm exec vitest run --project agent-runtime-pi-durable` 都通过：17 个文件，#24814 上 172 个通过，#24817 和 #24818 上 175 个通过，6 个跳过（两次合约运行里各有三个 Durable 不支持的用例）。
- AC6 — `tests/projection.test.ts` 检查预览、工具调用预览、它的已提交条目和一个工具结果在基线快照之后以 `message.upsert` 帧送达，并重放成重建的视图；`gap` 之后的帧是快照；完成信号随该次更新的最后一帧送达；`tests/runtime.test.ts` 检查流式文本以部分 upsert 送达，`tests/history.test.ts` 检查折叠的历史等于 `historyOf`（#24817）。
