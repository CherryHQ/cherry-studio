# Agent Note：CherryIN 模型端点刷新

Status: implemented

[English](2026-11-14-cherryin-model-endpoint-refresh.md) | 中文

## 问题

CherryIN 模型发现会读取 `supported_endpoint_types`，但初始化和手动拉取模型会跳过已有记录。因此，服务端改变协议后，已保存的模型仍会路由到过期端点。

## 决策

由应用管理的主进程服务刷新内置 CherryIN 提供商已有模型的端点。启动 30 秒后首次检查，此后每六小时检查。持久化的上次尝试时间也会对重启、失败和空响应进行请求节流。提供商不存在或未启用、没有启用的凭证、本地模型列表为空时，不发起请求，也不推进该时间戳。

端点值及其顺序以服务端为准，不增加来源字段或数据库迁移。当服务端为精确匹配的模型 ID 提供已识别且非空的端点时，覆盖此前保存的端点以及之后手动修改的端点。其他模型设置和模型集合保持不变。模型缺失、端点声明为空、声明仅含未知端点、响应为空或请求失败时，保留本地数据。

同一时间只运行一个请求。请求超时为 30 秒，并在关闭时中止。应用响应前再次检查提供商配置，并重新读取当前本地模型，避免重新创建已删除的记录。复用现有模型批量更新，在原子提交后使模型查询失效。不会重试正在进行的生成请求。

## 考虑过的替代方案

记录端点来自服务端还是用户可以保留手动覆盖，但会引入当前需求不需要的持久化归属合同。选定规则明确以服务端为准。仅更新远端注册表无法替换已保存的端点覆盖值。复用模型列表对账则会引入不需要的模型增删。

## 影响

端点变化会在符合条件的定时检查中同步，无需升级应用。手动端点修改保留至下一次成功刷新。新增协议实现仍然需要升级应用。未启用或新配置的提供商在下一次定时检查时重新判断资格；不增加设置监听器，也不在生成请求时引入网络依赖。

## 验证

- Regression — `src/main/services/__tests__/CherryInModelSyncService.test.ts`：使用真实数据库和生产迁移验证已有模型的路由变化、同步资格、设置和模型集合保留、跨重启节流、空响应和失败响应、关闭以及过期的在途结果。
- Regression — `src/main/ai/provider/__tests__/listModels.test.ts`、`src/main/data/services/__tests__/ModelService.test.ts` 和 `src/main/data/__tests__/CacheService.persist.test.ts`：覆盖复用的模型列表规范化、模型原子写入及投影，以及调度状态的持久化存储。
