# Agent Note: Capability-driven multi-image limits for Agent requests

Status: implemented

English | [中文](2026-11-19-agent-multi-image-limits.zh.md)

## Problem

Agent requests containing multiple images failed upstream with `At most 1 image(s) may be provided in one prompt`, after a paid request was already sent. Chat tolerates multiple images (native vision input or the OCR fallback), but Agent turns forward attachments through runtime-specific channels — Pi and Pi-Durable as absolute file paths the agent reads with its tools, Claude Code as native Anthropic image blocks — with no shared image definition, no per-model limit, and no pre-send validation. Retry behavior for the rejected turn was unverified.

## Decision

`src/shared/ai/agentImageLimits.ts` owns one image predicate and order-preserving counters shared by message parts, runtime payloads, and composer attachments. `resolveMaxAgentImages` reads the production `Model` contract (`Model.maxAgentImages` in `src/shared/data/types/model.ts`): explicit per-model declarations win, vision models without one are unlimited (the bundled provider-registry 0.8.0 catalog declares no caps, so with bundled data preflight is a no-op and enforcement activates only when a deployment declares a cap or an upstream rejection names one; supported models receive every image; Pi/Durable preserve user order, Claude native blocks may emit managed images before workspace images due to routing), and non-vision models defer to the existing graceful fallbacks (OCR text, path references, Read guards) instead of a new upfront block. `ProviderRegistryService.mergePresetModel` and `applyPresetAndOverride` propagate the registry-owned cap from `ModelConfig.maxAgentImages` and `ProviderModelOverride.limits.maxAgentImages` (top-level alias supported), and `enrichRowsFromRegistryTx` inherits registry caps for custom rows; custom rows remain limit-free unless the registry supplies one. `assertAgentImageLimit` throws `AgentImageLimitError` carrying the actual limit, count, and `sent` flag; an upstream `At most N image(s)` parser converts provider rejections into the same shape, with `sent: true` for Claude Code result-boundary failures only — Pi/Pi-Durable mid-turn tool-read failures keep their existing error path.

Enforcement runs before any paid provider call and before any DB writes. `AgentChatContextProvider.validateDispatch` validates the turn's image count against the turn model's limit, and `prepareAgentSessionDispatch` re-checks before the busy `saveMessage` and before the idle `persistDispatchTx`, so an over-limit submission never leaves a committed user row or a pending assistant row without a stream to settle it; the edit route revalidates inside the fork transaction so an over-limit replacement rolls back and leaves original rows intact; on the enqueue/beginTurn race the just-committed rows are deleted best-effort and the limit error stays authoritative. The renderer composer blocks in `handleSendDraft` and re-checks in `sendQueuedPayload` when follow-ups drain (counting both attachments and prebuilt file parts for Resend), so a model change while queued cannot slip through; main-side rejections preserve the typed limit across IPC and surface the localized limit warning with draft kept; channel admission sends the typed limit message instead of the generic processing error. Main `AgentSessionRuntimeService` validates in `beginTurn`, `enqueueUserMessage`, and `admitTurn` (history-inclusive with routed filtering via `assertRoutedAgentImageLimit`, so only actually routed replayed images gate a text-only send while orphaned managed history passes), covering composer sends, retries, follow-ups, steers, and channel/remote inputs for every runtime; `admitTurn` validates against the turn's captured `turn.modelId` (matching `connectionTarget` for live turns) so an agent-default change during connection opening cannot re-gate the opening turn. Claude Code additionally guards native image-block construction (before file I/O and the SDK call), normalizes SDK admission rejections that name an upstream cap, and normalizes provider `result` failures via `normalizeResultImageLimitFailure` using `consumePendingImageCount` (first over-limit in submission order, so a two-image failure preserves an unplaced five-image steer; UUID correlation remains a TODO; text-only steers cannot overwrite a pending count; replayed blocks included) with sent-aware wording. Remote access maps the typed limit to rejected/CONFLICT with limit/count details instead of interrupted/INTERNAL. Rejected pre-send turns keep drafts and history intact, so retry preserves attachments and instructions. Four locale keys (`agent.image_limit_exceeded`, `error.agent_image_limit_exceeded`, `error.agent_image_limit_exceeded_after_send`, `error.agent_image_limit_detail`) ship translated in all 18 catalogs, and `serializeError` preserves limit/count/runtime/sent plus i18n keys across IPC.

## Alternatives considered

- Silently dropping or downsampling extra images: loses user data without consent; rejected.
- Auto-batching images across sequential turns: changes comparison and multi-screenshot semantics, which require all images in one prompt; the chosen behavior is block-with-limit.
- A new provider-registry catalog field for chat image limits: implemented as registry-owned `ModelConfig.maxAgentImages` and `ProviderModelOverride.limits.maxAgentImages` (no user_model column, no DB migration); existing preset rows inherit on next read.
- Converting mid-turn Pi tool-read failures: Pi attaches images lazily through tools, so only initial attachments are pre-validated; Pi/Durable tool-read failures keep their existing error path and are not converted by the Claude-only sent-aware normalizer.

## Consequences

Out-of-the-box behavior is unchanged: with no declared limit, Pi/Durable forward all attached images in user order and Claude forwards all supported images (native routing may group managed images first). Enforcement is fail-closed only when a limit is declared or an upstream rejection names one. Pre-send validation runs before DB writes (edit route revalidates inside the transaction), so over-limit turns leave no orphaned user rows, pending assistant rows, or remote reservations; remote maps the typed limit to rejected/CONFLICT; the sent-aware result boundary (`sent: true`, `error.agent_image_limit_exceeded_after_send`) is Claude-only and shows the request was already sent. Non-vision fallback behavior is untouched, and painting `maxInputImages` remains a separate image-generation concern. Renderer and main share the same `AGENT_IMAGE_EXTS` counting definition (shared `imageExts` plus AVIF/HEIC/HEIF/TIFF) so both sides count the same attachments before managed copies are created; the shared routing table stays untouched so non-vision AVIF/HEIC keeps its local-path fallback instead of rerouting into OCR.
