# Agent Note: Notes 反斜杠数学定界符

Status: implemented

[English](2026-11-14-notes-backslash-math-delimiters.md) | 中文

## 问题

2.x 的 Notes 使用 TipTap RichEditor 和 `@tiptap/markdown`（marked），其数学 tokenizer 仅识别 `$$` 和 `$`。1.x 的 markdown-it 管线支持 `\[…\]`，因此使用反斜杠定界符的既有笔记在富文本编辑器中失去了公式渲染。

序列化器还会转义普通文本中的 `[` 和 `]`。若只添加反斜杠数学 tokenizer，新保存的普通方括号会在重新加载时变成公式：`[x]` 会变成 `\[x\]`。

## 决策

[增强数学扩展](../../../../src/renderer/components/RichEditor/extensions/enhancedMath.ts)新增两个仅贡献 tokenizer 的扩展。它们用独立 token 类型映射到既有 `blockMath` 和 `inlineMath` 节点，不重写美元 tokenizer。

单行 `\[…\]` 和 `\(…\)` 生成 `inlineMath`。当 `\[` 独占起始行、前面仅有 0–3 个 ASCII 空格时，跨行匹配 `\]` 并生成 `blockMath`。Notes 不实现 chat 的 display 提升：行内定界符中的换行、`\tag` 和 `\begin{…}` 不会触发拆分成块。唯一例外是用户把公式编辑成自身定界符无法表达的 latex，且该公式是文档根或引用下段落唯一子节点时，才按块形式写出（见后果）。通过输入规则自动转换不在本次修复范围内。

两个属性保存原始写法：`delimiter` 与 `markdownSource`（`{ raw, latex }` 对）。两者都会渲染进 HTML（`data-math-delimiter`、`data-math-source`、`data-math-source-latex`），`parseHTML` 再从这些属性读回，因此这一对属性不会被强调边界回退丢弃，可以跨 HTML 往返保留。只要 latex 仍等于 `markdownSource.latex`，序列化就逐字回放 `raw`，包括块公式的前导缩进；一旦 latex 被编辑，过期的快照不再回放，改按原定界符输出规范形式——例外是后果段描述的升块情形，写的是块形式，因此会把 `\(…\)` 变成 `\[…\]`。美元语法与纯文本复制保持既有行为。

既有 [markdown 补丁](../../../../patches/@tiptap__markdown@3.26.1.patch)只对**不在链接文字内**的文本取消闭合方括号的转义；开方括号始终转义，链接文字内的闭合方括号仍然转义。因此普通 `[x]` 保存为 `\[x]`（开括号带反斜杠、闭括号不带），它自身没有数学闭合定界符；而形如 `[x\]y](url)` 的链接文字保持转义、文字不丢失。

配对扫描在复用缓存前会校验：只有当前源串是被扫描源串的已验证后缀、且起点位于扫描器字符边界（紧邻起点之前的连续反斜杠数量为偶数）时才复用，因为 marked 会把同一个 token 数组复用于不同源串（块引用加懒续行时）。

## 考虑过的替代方案

- 替换美元 tokenizer 会扩大兼容性影响面，而支持反斜杠语法并不需要这样做。
- 像 chat 那样把行内公式提升为 display 块，或添加输入规则转换，会改变超出既有笔记加载和保存范围的编辑行为。
- 保持序列化器的转义不变，会让新保存的普通方括号在重新加载时静默变成公式。
- 仅在 `](` 周围有条件地转义 `[`，会失去对 `[x][id]` 和 `[x][]` 等引用链接形式的既有保护；运行时覆盖序列化器私有方法则会绕过仓库既有补丁机制。

## 后果

2.x 已经保存成 `\[x\]` 的普通方括号文本无法与反斜杠数学区分，仍会作为公式加载。序列化器改动保护新写入，无法消除历史字节的歧义。

编辑后的公式按自身定界符输出规范形式（`\(<latex>\)`；块形式则是 `\[` 行 + latex + `\]` 行，单行 `\[<latex>\]` 情形沿用行内形式），升块例外见下文。不做美元回退：若 latex 含自身闭合序列、换行或该定界符无法表达的其他内容，重载仍会截断。把「美元改写是否无损」枚举成条件已被证明不可靠（含空格的空行、标题打断段落、CR 规范化、上游块公式的 `trim()`、闭合符后紧邻文本），因此干脆不做有损改写。仍有一类情况被救回：不再复用原文快照、且新 latex 需要块形式（含换行、自身闭符或首尾空白）的反斜杠行内公式，当它是文档根或引用下段落的唯一子节点，且新 latex 既不含 `$`、也没有「前面最多 3 个空格、以 `\]` 开头」的行时，改写提升为块形式，可表达换行与该行内闭符——注意这会把 `\(…\)` 公式重写成 `\[…\]`；位于列表项、表格单元格、句中有兄弟节点，或 latex 自身含 `$` 或这样的 `\]` 行时仍保留原定界符，上面描述的重载损失照旧存在，而不是改变文档结构。这两种被拒的情形保留原定界符，于是重载会把 latex 当 Markdown 重新解释：行内定界符不能跨换行配对，换行前没有有效闭符时原开符不会生成行内公式，其余文本可能丢掉转义（`\]` 行重载成 `]`）、留在纯文本里，或在 latex 自带美元定界符时变成新公式（latex 里的 `$$z$$` 会变成块公式）。这份损失来自无法表达换行的定界符，本 PR 不修复；升块拒绝的只是「写出一条不同的公式、再让它冒充用户的编辑结果」。

原文保留仅覆盖 tokenizer 收到的文本，不包含原文件的 CRLF、容器前缀或表格编码。源码视图（CodeEditor）不渲染公式。方括号闭符扫描会跳过同一行内确实配对的 `\(…\)` 区间，因此被转义的普通 `[x]` 不会与藏在圆括号公式里的 `\]` 配对（否则重载会变成吞掉周边文本的方括号公式）。美元公式同样算排除区间，判据与上游 tokenizer 完全一致（从 `$$` 起 `^\$\$([^$]+)\$\$`，否则 `^\$([^$]+)\$(?!\$)`，按 `indexOf('$')` 向前扫），因此 `$…$` / `$$…$$` 内部的 `\(`、`\)`、`\]` 既不会开启圆括号区间，也不会闭合方括号公式。残留的是镜像情形：latex 内含配对 `\(…\)`、且闭符 `\]` 落在该区间内的方括号公式不会被识别为公式。
普通方括号文本之后即使有字面包含 `\]` 的代码片段，也不会再消费公式的闭符：凡是被 Marked 判定为代码片段、链接（行内式或参考式）、自动链接或原始 HTML 的 `\]` 都不闭合**行内**公式，且行内开符不会跨过这类区间去配闭符；行首的闭符仍可闭合**块**公式，但跨过被扫描源全文的美元区间会屏蔽这样的闭符——这正是上文升块条件要排除含 `$` 的 latex 的原因。区间来自 Marked 自身对同一段源文本做的内联词法，按各 token 的 `raw` 累加得到偏移，因此**跨行才闭合**的代码片段与同行闭合的一样受保护，未配对的反引号仍按普通文本处理、不会吞掉闭符，链接目标也只在 Marked 真正读出目标的位置受保护。仅当文本同时含 `\[`/`\(` 和可能开启 Marked 内联结构的字符——反引号、`<`、`@`、`www.`、`http`/`https`/`ftp` 协议，或未转义的 `[`——时才请求该扫描，结果按源缓存并有防重入标志；裸主机名或裸邮箱是否受保护只取决于 Marked 是否为它产出链接 token，该门禁不触发时不会建立 Marked 派生区间（美元与配对圆括号区间仍独立生效，URL 协议要求带 `://`）。强调边界的 HTML 回退现在会保留公式元数据：块公式与行内公式渲染 `data-math-delimiter` 与 `data-math-source`，这些属性会被读回，因此回退往返不再把公式改写成美元语法；补丁里的同名嵌套 span 深度配对也改用与 schema 相同的判据——`span` + `data-type="inline-math"` 或 `div` + `data-type="block-math"`，取 HTML 解析器会保留的第一个 `data-type` 值并做实体解码，属性边界只认 HTML 的 ASCII 空白，且只看引号外的属性——因此只作用于数学节点，普通 `<span>` 内容（包括带 `data-latex` 的普通 span 或包着数学 span 的普通 span）仍保留其链接与标记。该回退仍有嵌套 paragraph 的既有缺陷：在 base commit `d7e53eaf` 上使用美元公式也能复现。独立的美元公式用例钉住这一缺陷，留待单独修复 HTML 回退；它并非由反斜杠定界符导致。

图片 alt 中含 `]` 的往返缺陷来自既有 Image 序列化器，不在本次修复范围内。

另有四条限制继承自 base 编辑器，这里只做记录，因为它们在共享测试里表现为「首轮与后两轮不同」：有序列表中的块公式保存后因缩进重载成纯文本（`$$` 形式在 `d7e53eaf` 上同样复现）；href 含 `\]` 的自动链接或原始 anchor 首存保留反斜杠、重载后丢失（`$$` 同样复现）；链接闭括号前的尾随空格会被移到链接之外；链接内含代码片段会触发 `enhancedLink,code` schema 并重新序列化。覆盖这些情形的用例断言的是稳定的第二、三轮，而不是宣称三轮完全一致。

未被判定为公式的文本，内容不变，但定界符字节不一定保留：链接文字之外的 `]` 不再转义，因此段落里手写的 `\]` 会被写成 `]`，将来再修也无法从文件里找回。这与上面「存量字节」是同一笔取舍，只影响契约不认定为公式的文本。

行首仅有 0–3 个 ASCII 空格、独占一行的 `\[`，只要在**tokenizer 当前扫描的源**（正在解析的块容器的剩余源，而非整篇文档）内找到配对 `\]`，就生成块公式。因此分处两个不同引用或列表容器的定界符不会配对，而同一容器内的两半可以。行首本身来自 lexer 而非 token 数组：扩展为每个 lexer 实例包装一次 `blockTokens`，用栈记录每次调用起始的源，由「该源中当前后缀之前的那个字符」决定——是换行或没有前一字符才算行首。当该源栈不可用、或当前源不是栈顶源的后缀时，退回按 token 数组判定（tokens 为空，或末 token 的 raw 以换行结尾）。该判定只读一个字符；marked 把同一个 token 数组复用于另一个源、且该源内容恰为前一个后缀时也依然正确，引用懒续行即属此列。跨过该行的美元行内公式或代码片段让位于块定界符，列表和引用内也遵循此契约；不再用美元上下文仿真保护候选：受保护区间不再来自手写规则，而是用当前配置的 Marked 实例对同一段源文本做内联词法，按每个 token 的 `raw` 长度累加得到偏移，代码片段、链接（行内式或参考式）、自动链接与原始 HTML 占据的正是 Marked 渲染时的边界——本仓依赖的 Marked 版本里自动链接与裸 URL 都返回 `link` token，集合里其余名称属防御性判断，而非各自独立的 token 类型。这趟词法只在源文本含 `\[` 或 `\(` 时执行，按源字符串缓存并限制条数，词法期间用模块级标志让本扩展放弃匹配以免重入。美元公式仍按上游正则识别，且起点必须落在这些区间之外；随后第二趟遍历匹配 `\[`/`\]` 与 `\(`/`\)`，跳过落在区间内的定界符，保留区间之前已开启的起点，跳过的区间含换行时清空同行公式栈并前移行起点。由此有一个有意为之的结论：Marked 留作纯文本的 `\]` 会闭合行内公式，而**行内**配对不会跨过这样的区间；Marked 派生区间不限制块闭符，块闭符仍须满足行首规则，且可能被当前扫描源里的美元区间屏蔽——跨过块开符的先行美元或代码片段会被该开符打断。所以 `\[a] [a][b]` 接 `(url\]url)` 时保持纯文本且链接完好（Marked 把目标读作 `url]url`）。正是这条行内跨度规则保证行内公式的保存与重载幂等：只有在自己的字节能重新解析成同样节点时，公式才被创建。圆括号配对仍限同一行。美元与圆括号区间对行内与块两种扫描都生效；由 Marked 得出的代码片段、链接、自动链接与 HTML 区间只约束行内配对：块配对由同一扫描源内行首 `\[` 与行首 `\]` 决定，除非该源里的美元区间屏蔽了这个闭符；这也正是升块后的 latex 即使含代码片段或链接仍能原样重载的原因。紧凑列表仍有上游限制：块后的文本可能直接成为 `listItem` 的子节点，产生非法节点。多反引号代码片段也仍有上游序列化限制，重载时可能丢失代码标记。嵌套的自闭合数学 span 也会在其后的文本上经由 HTML 路径丢失内容；撤回补丁 hunk 并直接调用 `pasteHTML` 在 base 上同样可复现，属上游行为。

配对扫描按 token 数组缓存，复用前校验后缀和字符边界；边界不合法时重新扫描。边界校验仅向回遍历紧邻起点的连续反斜杠。同节点数的同进程测量显示，反斜杠路径与美元路径同量级：最近两次 307 项测试整轮里，33 KiB 的两者中位数为 414.5 / 276.0 ms 与 346.6 / 251.0 ms，132 KiB 为 8229.6 / 4555.0 ms 与 6844.6 / 4327.6 ms，观测比值为 1.4–1.8x。因此性能用例钉住的是病态输入的绝对上限（未闭合开括号、未闭合圆括号、开括号出现在 132 KiB 文档靠后位置、短公式密集），以及同节点数下不超过 3 倍的美元相对门禁——美元一侧设 150 ms 下限，避免极快基线把调度抖动放大成失败，实际条件是 `反斜杠耗时 <= 3 × max(美元耗时, 150 ms)`；两条路径交替各测两轮、取较小中位数能削弱但无法消除单向进程负载的影响。不钉住不同尺寸间的增长率——同样 4 倍输入下美元路径自身就增长 16–18 倍，增长率只能反映引擎与进程负载，而非本改动。

反复创建销毁编辑器会放大一项上游成本：`@tiptap/markdown` 把 tokenizer 注册到共享的 Marked 单例上，每次新建编辑器都会多一份，之后每次解析都要跑全部副本。在未闭合块探针上，单 manager 时该密集路径约 15 ms，创建 301 个编辑器后升到 3204 ms。给每个 manager 独立 Marked 实例可以消除该增长（同一探针 14.8 ms），在短公式密集输入上绝对值也更快（33 KiB 时 43.5 ms 对 293 ms，132 KiB 时 1571 ms 对 5514 ms），但在该构建内反斜杠/美元比值为 6.8 倍（132 KiB 时 1571.5 ms 对 229.6 ms），会触发用于约束本改动边际成本的相对门禁。这些数字来自不同进程与轮次，不是受控基准；本 PR 保留共享单例，并把这一取舍记录在此，而不是悄悄换掉。
