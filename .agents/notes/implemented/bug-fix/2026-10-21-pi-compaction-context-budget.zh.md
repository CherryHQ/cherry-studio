# Agent Note: Pi 压缩上下文预算

Status: implemented

[English](2026-10-21-pi-compaction-context-budget.md) | 中文

## 问题

Pi 按字符估算历史时，可能低估小上下文自定义模型中的多语言文本和工具输出。默认保留的近期历史会让压缩请求仍然过大。模型目录的输出上限若等于上下文，输出预留还会占满几乎全部对话空间，导致反复压缩。Pi 1.0 将系统消息规范化为转录中的消息，因此假设第一条消息就是摘要提示词，会绕过输入保护。

## 决策

Cherry 将目录输出上限对应的预留限制为上下文的四分之一。小上下文提前压缩并保留更短的近期历史；至少 100,000 token 的上下文继续保留默认的 20,000 token 近期历史。

锁定版本的 SDK 补丁按角色找到用户摘要消息，通过 Pi 的文本辅助函数读取字符串或文本块内容，同时保留系统消息和调用者的路由信息。小上下文摘要的输入、输出均受预算限制；大上下文摘要在 Pi 确认超限前保留完整输入和原有输出预算。重试将输入预算减半，最多尝试四次上下文溢出恢复。SDK 原有的临时故障重试策略和取消检查继续生效。持续溢出会报错，不会把无效摘要保存为检查点。

构建摘要时分别传入对话与历史摘要片段，不解析不受信任文本中的分隔符。输入裁剪先预留完整指令，再将剩余预算分配给各片段，同时保留每段的首尾；此规则也适用于分拆轮次前缀和分支摘要。如果完整指令与各片段的最少上下文无法放入预算，摘要会在请求之前明确失败，不会静默丢弃指令，或把丢失任务与进展要点的摘要保存为检查点。

Pi 的临时故障分类器排除确定性的上下文溢出，即便服务商把它包裹在通用错误文本中。这避免临时故障重试放大溢出尝试次数；真正的临时故障仍然使用原有重试预算和回调。

## 考虑过的替代方案

- 预留完整的目录输出上限，可能没有足够空间继续有效对话。
- 预先截短所有大上下文提示词，会丢失服务端原本能够接收的历史。
- 仅重试错误响应，会漏掉 Pi 已识别的静默溢出和零输出长度终止。
- 直接裁剪拼接后的更新提示词，可能同时丢掉历史摘要中的原始任务和新对话中的最新进展。

## 影响

此限制是保守的字符估算，不是精确分词。溢出恢复可能省略中间历史，但保留原始请求和最新进展。持续失败仍会明确展示，不会清空用户对话。升级 SDK 时，需要重新生成版本锁定补丁并运行集成测试。

## 验证

- Regression — `src/main/ai/runtime/pi/piCompactionRecovery.test.ts`：输出上限接近或超过上下文时，仍为下一轮保留空间；小上下文与大上下文溢出重试中的更新摘要均保留任务、进展要点和完整指令，文本含字面分隔符也不受影响；历史、轮次前缀和分支摘要均受预算限制；过大指令在请求前失败；系统消息在前的字符串、文本块输入，以及重试耗尽、取消和无关错误均保持各自约定。
- Regression — `src/main/ai/runtime/pi/PiRuntimeConnection.test.ts`：运行时设置在保留受信工作区与工具设置的同时，传入按模型计算的压缩策略。
