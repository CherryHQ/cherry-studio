# Agent Note: 为后台工作的重建等待设上限

Status: implemented

[English](2026-11-05-background-work-rebuild-grace.md) | 中文

## Problem

配置变更产生 `rebuild` 判定时，已脱离的后台工作（`run_in_background` shell、后台 agent 或 DSH 后台流程）仍可能占用热连接。`ensureConnection()` 原先通过 `waitForBackgroundWorkRelease()` 推迟重建——该 Promise 只在驱动报告工作释放或连接死亡时才会结算。脱离的工作没有宿主侧的存活探测，因此进程已经死亡却从未发出释放信号的工作（例如运行时未观察到的系统重启）会让等待永远挂起，之后每一次轮次都卡在准入阶段。2026-09-18 的生产事故中，一条已持久化的用户消息在准入前空等了 5 分 40 秒，直到手动 SIGTERM 拆掉连接。

## Decision

用 `BACKGROUND_WORK_REBUILD_GRACE_MS`（120 秒）为等待设上限。到期后等待结算为 `false`，由调用方决定：

- 连接自身执行中仍有活跃轮次（等待期间开始的自主生成、状态转换或已准入轮次）属于驱动报告的真实工作；此时强制重建会杀死它，因此重新启用宽限期，其自身释放仍会结算等待。
- 没有等待准入的轮次（预热式重新拉取）时，放弃这次推迟的重建，下一次真实轮次会重新对账。
- 其余情况下，待处理的用户轮次优先于无主占用：走常规拆除路径强制重建，该路径在重连前会结构性地清除占用。

宽限期内自然释放仍然优先，并会清除计时器，因此陈旧计时器不会触发到后继等待者。到期记录 `Background work did not release within the grace period`（含 `sessionId` 与 `graceMs`）；强制与放弃路径各有自己的日志。

## Alternatives considered

- **直接让待处理轮次报错**——放弃：保住了活跃工作，却留下永久卡死的僵尸连接，后续每次轮次都会再次推迟并报错，连接永远无法恢复。
- **宽限期后在旧连接上准入**——放弃：`rebuild` 判定意味着生成期冻结的事实已不同，轮次会在旧配置下运行。
- **会话重开时做驱动存活探测**——留作后续：区分死亡与存活的脱离工作需要新的运行时 API。有界等待把僵尸的破坏限制在一个宽限期内，随后通过拆除结构性回收。
- **在渲染层暴露推迟状态**——暂缓：状态机已有 `connection.pendingRebuild`，但尚无展示位置，属于产品决策。

## Consequences

待处理的用户轮次最多等待 120 秒的无主后台工作；确实需要更长时间的活跃工作会被拆除——与会话关闭、空闲 TTL 或应用退出已有结果一致。活跃的自主工作不会被宽限到期杀死，预热重建只损失自己的推迟。计时器已 `unref()` 并在所有自然释放路径清除，不会超出其等待者生命周期。推迟状态对渲染层仍不可见。
