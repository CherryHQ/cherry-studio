# Agent Note: 限制原生模型序列化内存

Status: implemented

[English](2026-11-15-native-model-payload-budget.md) | 中文

## Problem

包含大量图片的 Durable 并行任务在[追踪保留](2026-11-14-agent-trace-memory-recovery.md)和[观察保留](2026-11-15-native-observation-retention.md)修复后仍能复现主进程 V8 OOM。一次模型调用期间，完整原生请求、网关解码和提供商请求会同时存在。限制诊断和过期快照不能约束这些活动工作集。在 fetch 中等待已经太晚：原生 SDK 已经完成请求序列化。

## Decision

由生命周期管理的 ApiGatewayService 为原生 Pi 模型绑定共享可取消的加权额度。准入使用已有的 async-mutex 信号量；宿主不调度原生步骤。直接从载荷对象图估算 JSON 转义开销，不执行序列化，计费最多为 64 MiB。预估成本不超过 8 MiB 的请求绕过准入；更大的请求共享 64 个一 MiB 单位。单个超大请求可以占用全部额度，不裁剪内容。

通过 SDK 的异步 onPayload 钩子，在请求编码前获取额度。保留调用方载荷钩子及其返回 undefined 的语义。模型流结束后释放额度；提供商重建载荷前先释放旧额度，失败和成功均会释放。排队调用取消后立即拒绝，之后获得的信号量额度直接归还，不再发送请求。网关停止时取消待准入调用。

完整会话、图片和模型可见内容保持不变。额度只存在于运行时，不持久化。它限制大请求工作集的并发，不代表整个进程的 RSS 上限，也不改变上游服务支持的请求大小。

## Alternatives considered

- 在 fetch 中排队：序列化分配已经存在。
- 串行化所有模型调用：会无谓地延迟普通请求。
- 提高 V8 堆上限：图片历史的并发放大仍然存在。
- 删除或缩小历史图片：改变用户要求保留的模型上下文及审校质量。

## Consequences

包含大量图片历史的调用可能需要等待其他模型响应结束。原生工具和小请求继续保持并发。以吞吐量换取序列化并发受控，同时不改变模型依据。上游 HTTP 413 仍然是上游请求大小限制，不通过删除用户历史绕过。

## Verification

- Regression — ApiGatewayService.test.ts：超大请求依次准入，小请求继续执行；排队取消不会泄漏额度；停止会取消待准入请求，后续仍可重用。
- Regression — gatewayModelBinding.test.ts：两份完整的合成 12 MiB 请求通过真实原生 SDK 传输依次发送；未修改的绑定会并发发送两份请求。上游失败会释放额度；取消排队请求后不会发送该请求，后续请求仍可继续。
- 绑定保留完整合成请求文本，并通过定向网关集成测试，保持原有协议、凭据、思考和 usage 契约。

手动隔离实测恢复相同会话历史，并在开始阶段分派四个大量读取图片的子任务；运行 20 分钟后主动中断，期间未发生 V8 OOM，原始基线约六分钟即内存耗尽。工作区文件经过此前复现任务的修改，因此这是有边界的负载验证，不是内容完全相同的性能基准。该结果不能证明 Windows 安装包通过验收，也不能排除所有可能的内存耗尽。
