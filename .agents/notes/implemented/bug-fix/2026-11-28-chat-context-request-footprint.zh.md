# Agent Note: 根据待发送请求估算聊天上下文

Status: implemented

[English](2026-11-28-chat-context-request-footprint.md) | 中文

## 问题

持久聊天用上一条回复的 token 用量估算上下文。供应商可能在一次响应中汇总多个内部推理步骤的用量。换模型、切换分支、压缩历史或转换工具结果后，回放的历史也可能与上一次请求不同。这会让输入框显示虚高的占用，并可能提前触发自动压缩。

## 决策

持久聊天按待发送请求选中的内容估算上下文。持久化压缩估算待回放的历史，包括当前生效的摘要。每次调用模型前，运行时估算组装好的候选输入，计入可获得的系统提示和已启用工具定义，并与扣除输出预留后的模型输入预算比较。成功压缩后，估算缩减后的候选输入。这些路径复用消息 token 估算器，保留当前压缩边界、排除条件和溢出恢复。

聊天输入框展示当前对话路径和模型的估算值，数据来自同一套发送侧统计规则。只读预览估算会回放的历史和助手提示词，其缓存键跟随所选路径、模型和可获取的请求输入。无法确定输入时，占用显示为未知。

供应商用量和费用账本继续作为消耗统计的依据。压缩和占用展示从请求内容推导各自的计数。已有消息数据仍可读取。

## 考虑过的替代方案

- 收到服务端工具结果时丢弃用量。这能处理已观察到的虚高，但无法确定后续请求会带上哪些内容。
- 从供应商最后一次内部推理恢复计数。它可以描述那次推理，无法反映下一次回放的变化。
- 每次编辑草稿或执行工具后都请求供应商计数。这会增加网络延迟，部分适配器也没有该能力。

## 影响

输入框估算发送前可获取的回放历史和助手提示词。草稿和请求时加入的内容可能改变最终输入。本地计数只能近似估算供应商的消息封装、媒体编码和服务端隐藏输入。溢出恢复处理这些偏差，同轮计数复用稳定消息的估算值，媒体内容无需解码。

## 验证

- AC1 — `PersistentChatContextProvider.compaction.test.ts`、`inLoopCompaction.test.ts` 和 `middleware.test.ts` 验证历史回放和压缩决策独立于此前的累计用量。
- AC2 — `inLoopCompaction.test.ts` 验证上报用量相同时，增大的工具结果可以触发压缩，成功压缩后会报告更低的估算值。
- AC3 — `ChatContent.test.tsx` 验证切换模型和历史过期时的行为。接入本地模拟供应商的 Electron 分别显示 19 和 836 token，切换对话路径后恢复各自的估算。
- AC4 — `usage.test.ts` 验证服务端工具的累计用量保留缓存明细。Electron 对本地模拟供应商的两次响应各持久化 640,208 token。
