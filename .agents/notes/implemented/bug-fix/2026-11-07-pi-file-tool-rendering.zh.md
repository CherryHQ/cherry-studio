# Agent Note：渲染 Pi 原生文件工具参数

Status: implemented

[English](2026-11-07-pi-file-tool-rendering.md) | 中文

## 问题

回归用例 MP-51 批准了一次真实的 Pi 文件写入，并确认磁盘内容正确，但完成后的工具卡片没有文件链接。渲染器把 Pi 的 `write` 名称映射成共享 `Write` 卡片，却未转换原生的 `path` 参数。共享文件卡片要求 `file_path`；Edit 还要求 `old_string` 和 `new_string`，而 Pi 使用 `oldText` 和 `newText`。

## 决策

在现有工具响应展示边界转换 Pi Read、Write 和 Edit 的对象参数。保留原生字段，并补充共享卡片所需字段。持久化消息和运行时执行输入保持不变。包含 `edits` 数组的 Pi 原生编辑复用现有 MultiEdit 卡片，并分别转换每个差异片段；较早的单片段结构继续使用 Edit。

## 考虑过的替代方案

- 修改运行时输入会改变 SDK 契约和记录的执行证据。
- 在每个文件卡片中增加 Pi 分支会重复实现相同的转换。
- 删除 E2E 文件链接断言会掩盖真实的导航问题。

## 影响

已完成的 Pi 文件卡片可以复用共享组件显示文件链接和编辑差异。其他运行时和无关工具保留原参数结构，不引入新的执行或持久化格式。

## 验证

- 回归 — 原生 Read、Write 和 Edit 输入必须提供共享卡片所需的路径与差异字段，且不能修改原始输入；未标记运行时的工具保持不变。三个用例在修复前均失败。
- 回归 — 工具响应转换、共享 Agent 工具渲染器和执行时间线三个测试文件共 88 项测试通过。

- 回归 — MP-52 暴露了原生 `edits: [{ oldText, newText }]` 输入。新增的双片段转换用例在补充修复前失败，并验证每个差异片段及原始存储参数保持不变。

- 回归 — MP-52 使用真实服务商和 Pi 运行时通过：编辑差异、无关文件未被修改、刷新后的预览及 TextEdit 剪贴板内容均与编辑后的文件一致。
