# Agent Note: 通过正文分段请求限制翻译输出规模

Status: implemented

[English](2026-11-12-translator-chunks.md) | 中文

## Problem

[#24203](https://github.com/CherryHQ/cherry-studio/issues/24203) 报告翻译响应以 `max_tokens` 结束，导致 JSON 无效。关联运行记录了 4096 个输出 token，但文本块只有不完整的标题。这能证明响应被截断，不能证明该次响应仅由原文长度导致。将整篇正文放在单次请求中，也会让长译文与回传原文竞争同一输出预算。

## Decision

受信任的内联工作流将正文切分为每次最多 2000 个 Unicode 码点的片段，优先在换行处切分，并保留全部源字符。请求保留 `max_tokens: 4096`、零温度和现有结果字段。多段请求携带完整的只读原文及 UTF-16 片段偏移，让模型能结合跨段上下文理解 Markdown、已有译文和邮件历史。只有第一段可以翻译标题。

未修改的片段保留源文本。已修改的片段由本地代码保留原有边界空白；原文没有空白的硬切分界则保留译文新增的词间分隔符。单段响应维持既有处理方式。空结果用于移除现有清理规则选中的片段。所有片段必须成功，工作流才会组装一个翻译容器并执行一次 GitHub 更新。截断响应在提取文本或解析 JSON 前失败，错误指出段号、总段数和字符数，即使响应没有返回文本也是如此。

## Alternatives considered

只改进 JSON 报错仍然会将长正文放在单次请求中。提高输出上限需要假定提供商的限制，也无法为任意输入提供边界。孤立片段会丢失现有清理规则需要的上下文。自动重试会增加成本，却不能保证提供商返回完整结果；该 issue 允许改为明确报告出错片段。

## Consequences

长正文需要更多请求，并重复携带完整输入上下文。任务超时从五分钟增加到二十分钟，以容纳顺序翻译。字符上限不是 token 估算，也不保证响应不会被截断。翻译和清理仍由模型判断：全文上下文和片段指令保留了必要信息，但确定性的传输测试无法证明语言忠实度、真实模型对 Markdown 的保留效果或提供商可靠性。失败后不会发布部分结果。

## Verification

- Regression — `pnpm test:scripts scripts/__tests__/github-content-translator.test.ts` 使用受控 HTTP 响应执行实际工作流脚本，覆盖有界切分、结果组装、现有跳过路径和 GitHub 写入前的失败。该检查不验证真实提供商的翻译质量。
- Regression — 在隔离目录对分支提交 `26e897859` 运行最初的 31 项测试，结果为 16 项失败、15 项通过。另补充的两项译文词间边界用例，在修正片段空白处理前均失败。
