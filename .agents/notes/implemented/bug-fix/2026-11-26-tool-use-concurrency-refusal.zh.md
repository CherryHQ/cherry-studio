# Agent Note：归类上游的工具并发拒绝

Status: implemented

[English](2026-11-26-tool-use-concurrency-refusal.md) | 中文

## 问题

[#25031](https://github.com/CherryHQ/cherry-studio/issues/25031) 报告工作对话在拒绝并行工具调用的模型/通道上失败。服务商返回 HTTP 400 与 `400 due to tool use concurrency issues.`，而应用把原因归到传输层：会话里显示“响应传输中断，请检查网络稳定性或重试”，并提供一次注定失败的「重试」。这来自两个独立缺陷：共享分类逻辑没有这条拒绝的规则；而当 HTTP 状态只存在于被拍平的 `API Error: 400 …` 文案里时，分类结果停在 `unknown`，会话提示就在这时回退到「传输中断」的措辞。

## 决策

在共享分类逻辑中用一条很窄的文案匹配（`tool use concurrency`、`parallel/concurrent tool calls are not supported`）把这类拒绝识别为新分类 `tool_concurrency`，并在没有结构化状态时从被拍平的 `4xx`/`5xx` 前缀里恢复 HTTP 状态——只对标记为 `response-stream` 的错误或消息以 `API Error:` 开头的情况生效——让服务商拒绝按状态分类、而不是走兜底。诊断说明服务商拒绝了并发工具调用、原样重试不会成功，并把用户引向服务商设置。当一轮对话以错误结束却没有任何服务商细节时，会话提示改为报中性的未知诊断，不再断言传输中断；带服务商错误体的情形仍然原样透传。

## 考虑过的替代方案

- 沿用通用的 `bad_request` 标题：会丢掉唯一可操作的事实——重试没有意义，需要改变工具调用的形状。
- 继续留在 `stream`：传输层是健康的，「检查网络、重试」的建议是反的。
- 探测模型的并行工具调用能力并在 agent 循环里串行化：这会改变每个模型的请求行为，仓库里没有现成的能力来源，属于产品决策、应由后续 issue 承载，不在本次修复内。

## 影响

桌面端对这类拒绝有了独立且不可重试的诊断；远程失败 schema 不变，仍报 `invalid_input`，没有引入新的协议取值。状态恢复刻意收窄：该数值必须位于文案开头且后面紧跟非单位词，文本恢复只作用于 `response-stream` 错误与 `API Error:` 信封，AI SDK 的重试包装错误完全不参与其中。即使在响应流消息里，`500 ms` 这类普通数量也不会被读成状态码。没有被标记的正文保留自己的文本，因此服务商设置可以在遮盖密钥后展示 `401 rejected <key>`，而不是把它折叠成一条通用诊断。识别该分类并不阻止应用继续发送并行工具调用；issue 中提到的模型能力标注未在本次实现。

## 验证

- 回归 — 共享分类测试覆盖带显式 400 的报告文案、同一文案但无状态、被拍平的 `API Error: 400 …` 信封，以及匹配器接受的各种措辞变体；普通 400 仍为 `bad_request`，stream、内容策略与限流信号保持原有优先级。
- 回归 — 渲染层分类与会话提示测试断言新的诊断 key、服务商设置跳转目标，以及视觉模型的能力拒绝仍报 `bad_request` 而不是按恢复出的状态归类。它们同时锚定恢复边界：带 `response-stream` 标记的消息会恢复被拍平的状态，同一段文本没有该标记时保持 `unknown`、让服务商设置保留遮盖后的详情，而普通的 `401 rejected <key>` 不会被变成鉴权诊断。
- 回归 — 提示测试断言警告标题、详情中的上游原文，并且不提供重试动作；投影测试断言以错误结束但没有 `data-error` 部分的一轮对话不再报传输中断，带 `data-error` 时原样透传。
- 回归 — 未对真实服务商复现：该拒绝需要上游聚合服务真的拒绝并发工具调用，因此证据止于上述单元测试层级，本文不声称已在设备上复现该真实拒绝。
