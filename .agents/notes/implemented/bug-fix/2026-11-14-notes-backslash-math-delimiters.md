# Agent Note: Notes backslash math delimiters

Status: implemented

English | [中文](2026-11-14-notes-backslash-math-delimiters.zh.md)

## Problem

Notes in 2.x use TipTap RichEditor and `@tiptap/markdown` (marked), whose math tokenizers recognize only `$$` and `$`. The 1.x markdown-it pipeline supported `\[…\]`, so existing notes using backslash delimiters lose formula rendering in the rich editor.

The serializer also escaped both `[` and `]` in ordinary text. Adding a backslash math tokenizer alone would make newly saved ordinary brackets reload as formulas: `[x]` became `\[x\]`.

## Decision

[Enhanced math](../../../../src/renderer/components/RichEditor/extensions/enhancedMath.ts) adds two extensions that contribute only tokenizers. Their independent token types map to the existing `blockMath` and `inlineMath` nodes; the dollar tokenizers are not rewritten.

Single-line `\[…\]` and `\(…\)` become `inlineMath`. A `\[` on its own opening line, with 0–3 leading ASCII spaces, pairs with `\]` across lines to produce `blockMath`. Notes do not implement chat's display promotion: newlines inside inline delimiters, `\tag`, and `\begin{…}` do not trigger splitting into blocks. The one exception is a formula the user edited into latex its own delimiter cannot express, which is written as block math only when it is the sole child of a paragraph under the root or a blockquote (see Consequences). Automatic conversion through input rules is outside this repair.

Two attributes carry the original spelling: `delimiter` and `markdownSource` (a `{ raw, latex }` pair). Both render into HTML (`data-math-delimiter`, `data-math-source`, `data-math-source-latex`) and `parseHTML` reads them back, so the pair survives an HTML round trip instead of being lost by the emphasis fallback. While the latex still equals `markdownSource.latex`, serialization replays `raw` verbatim, including leading block indentation; once the latex is edited the stale snapshot is no longer replayed and the canonical form for the original delimiter is written, except for the promotion case described under Consequences, which writes the block form and therefore turns `\(…\)` into `\[…\]`. Dollar syntax and plain-text copying retain their existing behavior.

The existing [markdown patch](../../../../patches/@tiptap__markdown@3.26.1.patch) stops escaping `]` only for text that is not inside a link label; `[` is always escaped, and link labels keep escaping `]`. Ordinary `[x]` therefore saves as `\[x]`, which has no closing math delimiter of its own, while a link label such as `[x\]y](url)` stays escaped and keeps its text.

Pair scanning validates its cache: pairs are only reused when the current source is a verified suffix of the source they were built from and starts at a scanner character boundary (the immediately preceding run of backslashes has even length), because marked can reuse one token array for different sources (blockquotes with lazy continuation lines).

## Alternatives considered

- Replacing the dollar tokenizers would expand the compatibility surface without being necessary for backslash syntax.
- Promoting inline math to display blocks as chat does, or adding input-rule conversion, would change editing behavior beyond loading and saving existing notes.
- Leaving serializer escaping unchanged would silently turn newly saved ordinary brackets into formulas on reload.
- Conditionally escaping `[` only around `](` would lose existing protection for reference-link forms such as `[x][id]` and `[x][]`; a runtime override of a private serializer method would bypass the repository's existing patch mechanism.

## Consequences

Ordinary bracket text already saved by 2.x as `\[x\]` is indistinguishable from backslash math and still loads as a formula. The serializer change protects new writes; it cannot disambiguate historical bytes.

Edited formulas are written back with their own delimiter in canonical form (`\(<latex>\)` or, for a block, a `\[` line, the latex, and a `\]` line; the single-line `\[<latex>\]` case follows the inline form), except for the promotion described below. There is no dollar fallback: an edited latex containing its own closing sequence, a newline, or anything else the delimiter cannot express still reloads truncated. Enumerating conditions under which a dollar rewrite is lossless proved unreliable (blank lines containing spaces, a heading interrupting the paragraph, CR normalization, the upstream `trim()` on block latex, adjacent text after the closer), so a lossy rewrite is not attempted at all. One case is still rescued: a backslash inline formula whose original snapshot is no longer replayed, and whose new latex needs the block form (it contains a line break, its own closing sequence, or leading or trailing space), is promoted when it is the only child of a paragraph whose parent is the document root or a blockquote and the latex contains neither a `$` nor any line starting with `\]` after at most three leading spaces; the promoted form can express newlines and the inline closer — note that this rewrites a `\(…\)` formula as `\[…\]`. In a list item, a table cell, a sentence with neighbouring nodes, or when the latex contains a `$` or such a `\]` line, the original delimiter is kept instead, and the reload loss described above stands rather than restructuring the document. In those two refused cases the inline delimiter is kept, so the reload re-interprets the latex as Markdown: the inline delimiter cannot pair across a line break, so without a closer before it the opener produces no inline formula at all and the remaining text can lose an escape (a `\]` line reloads as `]`), survive as plain text, or even become a new formula when the latex carries dollar delimiters of its own (`$$z$$` inside the latex becomes block math). That loss is inherent to a delimiter that cannot express a newline and is not repaired here; what the promotion refuses to do is write a *different* formula that then persists as if it were the user's edit.

Raw preservation covers the text received by the tokenizer, not the original file's CRLF, container prefixes, or table encoding. The source view (CodeEditor) does not render formulas. The bracket closer scan skips a `\(…\)` region that has a matching `\)` on the same line, so an escaped ordinary `[x]` cannot pair with a `\]` that lives inside a paren formula (that would have reloaded as a bracket formula swallowing the surrounding text). Dollar formulas are excluded regions too, recognized exactly like the upstream tokenizer does (`^\$\$([^$]+)\$\$` from a `$$`, otherwise `^\$([^$]+)\$(?!\$)`, scanning `indexOf('$')` forward), so a `\(`, `\)` or `\]` inside `$…$` or `$$…$$` neither opens a paren region nor closes a bracket formula. The residual is the mirror case: a bracket formula whose latex contains a paired `\(…\)` with its own `\]` closer placed inside that region is not recognized as a formula.
A `\]` that Marked classifies as part of a code span, a link (inline or reference form), an autolink or raw HTML never closes an **inline** formula, and an inline formula never pairs an opener with a closer across such a region; a closer at the start of a line can still close a **block** formula, except that a dollar region spanning the scanned source can mask such a closer — which is why the promotion described above refuses latex that contains a `$`. The ranges come from Marked's own inline lexer run over the same source, with each token's `raw` accumulated into offsets, so a code span that closes on a later line protects as much as one that closes on the same line, an unpaired backtick stays ordinary text and cannot swallow the closer, and a link target is protected only where Marked actually reads one. The scan is requested only when the text contains `\[` or `\(` together with a character that can start a Marked inline construct it would need to respect — a backtick, `<`, `@`, `www.`, a `http`/`https`/`ftp` scheme, or an unescaped `[` — and the result is cached per source with a re-entrancy guard; whether a bare host or address is protected depends only on Marked emitting a link token for it, and when that guard does not fire no Marked-derived region is built (dollar and paired-paren regions still apply, and a URL scheme only fires when it carries `://`). The HTML fallback keeps the formula metadata now: block and inline math render `data-math-delimiter` and `data-math-source`, and the attributes read them back, so a fallback round trip no longer rewrites the formula to dollar syntax. The patch's nested-span depth pairing uses the same rule the schema uses to build the node — `span` with `data-type="inline-math"` or `div` with `data-type="block-math"`, taking the first `data-type` the HTML parser would keep, entity-decoded, with attribute boundaries limited to HTML's ASCII whitespace and only outside quoted attribute values — so it only affects math nodes, and ordinary `<span>` content (including a plain span that carries `data-latex` or wraps a math span) keeps its links and marks. That fallback still has a pre-existing nested-paragraph defect: dollar math reproduces it on base commit `d7e53eaf`. A separate dollar-math test pins that defect for an independent HTML fallback repair; it is not caused by backslash delimiters.

Image alt text containing `]` has a pre-existing round-trip defect in the Image serializer, outside this repair.

Four further limitations are inherited from the base editor and are only recorded here, because they show up as a first-round difference in the shared tests: a block formula in an ordered list is written back with indentation that reloads as plain text (the `$$` form reproduces it on `d7e53eaf`), an autolink or raw anchor whose href contains `\]` keeps the backslash on the first save and loses it on reload (also reproducible with `$$`), a trailing space before a link's closing bracket moves outside the link, and a link that contains a code span trips the `enhancedLink,code` schema and is re-serialized. Tests that cover them assert the stable second and third rounds rather than claiming all three are identical.

Text that is not parsed as math keeps its content but not always its delimiter bytes: with `]` no longer escaped outside link labels, a `\]` written by hand inside a paragraph is written back as `]`, so a later repair cannot recover it from the file. This is the same trade as the historical bytes above and only affects text the contract does not classify as math.

A standalone line-start `\[` with 0–3 leading ASCII spaces becomes block math when a matching `\]` is found in the source the tokenizer currently scans — the remaining source of the block container being parsed, not the whole document. Two delimiters split across separate blockquote or list containers therefore do not pair, while both halves of one container do. The line start itself comes from the lexer, not from the token array: the extension wraps `blockTokens` once per lexer instance and keeps a stack of the source each call started from, so the character preceding the current suffix in that source decides — newline or nothing before it. When that root is missing or the current source is not a suffix of it, the check falls back to the token array instead (empty tokens, or a last token whose raw ends with a newline). The check reads a single character, and it stays correct when marked reuses one token array for a different source whose content is a suffix of the previous one, including the lazy blockquote continuation case. A block opener takes precedence over a dollar inline formula or code span that crosses that line, including inside lists and blockquotes, while a block closer can still be masked by a dollar region in the scanned source; no dollar-context simulation protects these candidates, and the protected regions are not hand-written rules at all: they come from Marked's own inline lexer run on the same source through the configured instance, walking the returned tokens and accumulating each token's `raw` length to recover offsets, so the code span, link, autolink and raw HTML ranges occupy exactly the boundaries Marked renders — in the Marked version vendored here, autolinks and bare URLs both come back as `link` tokens, so the remaining names in the set are defensive rather than separate token types. That lex pass only happens when the source contains `\[` or `\(`, its result is cached per source with a bounded entry count, and a module flag makes the extension decline to match while it runs so the pass cannot re-enter itself. Dollar formulas are still matched with the upstream regexes and only start outside those regions; a second traversal then matches `\[`/`\]` and `\(`/`\)` while skipping anything inside them, keeps starts that were already open before a region, and clears the same-line formula stack and moves the line start when a skipped region contains a newline. The consequence is deliberate: a `\]` that Marked leaves as plain text closes an inline formula, while one that belongs to a code span, link, autolink or raw HTML does not; and, while an inline formula never pairs an opener with a closer across such a region, Marked-derived regions do not constrain a block closer: it still has to follow the line-start rule, and it can be masked by a dollar region in the scanned source — a dollar or code span that crosses a block opener is interrupted by that opener. With that split, `\[a] [a][b]` followed by `(url\]url)` stays plain text with the link intact even though Marked reads the destination as `url]url`. Restricting inline pairing that way is what keeps inline formulas idempotent: one is only created when its own bytes re-parse into the same nodes. The paren pairing stays same-line. Dollar and paren regions apply to both the inline and the block scan, while the Marked-derived code, link, autolink and HTML ranges restrict inline pairing only: a block pair is decided by a line-start `\[` and a line-start `\]` inside the same scanned source, unless a dollar region in that source masks the closer; that is also what lets a promoted formula keep its latex when that latex happens to contain a code span or a link. Compact lists retain an upstream limitation: text following a block may become a direct `listItem` child, making the node invalid. Multi-backtick code spans also retain an upstream serialization limitation that can lose code marks on reload. A nested self-closing math span also loses the text that follows it through the HTML path; reverting the patch hunks and calling `pasteHTML` directly reproduces it on base, so it is upstream.

Pair scanning is cached by token array, with suffix and character-boundary checks before reuse; an invalid boundary rebuilds the scan. Boundary validation only walks the adjacent backslash run backwards. With equal node counts, same-process measurements place backslash and dollar paths in the same order of magnitude: in the two most recent runs the backslash and dollar medians were 346.6–373.9 / 251.0–258.5 ms at 33 KiB and 6844.6–6876.1 / 4197.9–4327.6 ms at 132 KiB, with observed ratios of 1.38–1.64x. The performance test therefore pins absolute ceilings for the pathological inputs (unclosed opener, unclosed paren, opener late in a 132 KiB document, dense short formulas) plus a dollar-relative gate of at most 3x at equal node counts, with the dollar side floored at 150 ms so that a very fast baseline cannot turn scheduler noise into a failure — the effective condition is `backslash <= 3 x max(dollar, 150 ms)`. Alternating the two paths and keeping the smaller of two medians reduces, but cannot eliminate, the effect of process load on one side. It does not pin a growth ratio between sizes: over the same 4x size step the dollar path itself grows 16–18x, so a ratio gate would measure engine and process load rather than this change.

An editor that is created and destroyed repeatedly amplifies an upstream cost: `@tiptap/markdown` registers tokenizers on the shared Marked singleton, so each new editor adds a copy and every later parse runs all of them. On the unclosed-block probe the dense path grows from about 15 ms with one manager to 3204 ms after 301 created editors. An isolated Marked instance per manager removes that growth (14.8 ms on the same probe) and was also faster in absolute terms on the dense formula input (43.5 ms against 293 ms at 33 KiB, 1571 ms against 5514 ms at 132 KiB), but under it the backslash path measured 6.8x the dollar path in the same build (1571.5 ms against 229.6 ms at 132 KiB), which trips the relative gate that bounds this PR's own marginal cost. Those figures come from different processes and rounds, so they are not a controlled benchmark; the shared singleton is kept in this PR and the choice is recorded here rather than silently traded away.

- Regression — scoped ESLint, Oxlint, formatting checks, and `git diff --check` passed in the recorded task-2 verification.
- Regression — reverse application of the existing patch exited 0; the replacement patch dry-run exited 0 without fuzz.
- Regression — offline `pnpm install --frozen-lockfile --prefer-offline` exited 0 against the final patch (SHA-256 `040402bf…`) and reported the lockfile up to date; `shasum -a 256` of the patch equals the hash in all three `pnpm-lock.yaml` references.
