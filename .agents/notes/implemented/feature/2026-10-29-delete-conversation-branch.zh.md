# Agent Note: 删除对话分支

Status: implemented

[English](2026-10-29-delete-conversation-branch.md) | 中文

## 问题

从同一条消息尝试另一种措辞或模型就会多出一个分支，分支列表因此随着每次尝试不断增长。分支可以继续扩展，却无法删除，清理空间只能逐条删除消息或删掉整个对话。删除一个不再需要的分支时，不能影响共享前缀和其他任何路径。

## 决策

分支管理在**持久化子树恰好只通向一条完整路径**的节点上提供删除操作。删除会移除该路径的独占后缀——叶节点以及它在最近分叉点下方的线性祖先——同时保留最近的共享祖先和所有存活的其他路径。选中该后缀中的线性祖先会删除同一范围，用户不必先找到末端消息。仍为空的预留分支通过既有的 `DELETE /messages/:id?awaitingInputOnly=true` 路由单独删除，且不向上裁剪其祖先，因此尚未输入任何内容时的既有分支清理流程仍然可用。

该规则由 `MessageService.deleteBranch` 在单个写事务中执行。它会拒绝：唯一的对话路径、虚拟根、子树含多个叶节点的选择，以及删除范围内仍在生成或仍在等待工具批准的消息。任一检查失败时不写入任何数据。当被删除范围持有话题的活动节点指针时，指针回退到一个存活的叶节点；否则保持不变。存活节点不会被重新挂载、重新分组，也不会被剥离上下文元数据。

渲染层根据话题树计算同一范围，用来决定是否显示该操作，并在发送 `DELETE /messages/:id/branch` 之前要求显式确认。服务端会重新校验全部约束，包括树预览不携带的批准状态。

## 考虑过的替代方案

- 只删除选中节点：分支会通过其父节点继续存在，列表永远不会变短。
- 删除整个选中子树：选择位于分叉之上时会一次删掉多个分支。
- 回复组端点：会删除同一轮的所有同级回答，包括用户想保留的替代回答。
- 删除对话：会移除共享前缀和其他所有路径。
- 归档或隐藏：不再需要的消息仍留在存储中，而不是被删除。
- 批量清理：在“删除这个分支”之外额外引入了选择与范围规则。

## 影响

删除具有破坏性且不可撤销，确认文案已明确说明。系统不持久化分支身份，因此“原始对话”指用户没有选中的每条路径；其他分支保留各自消息，分叉点以上的共享前缀不受影响。如果树 API 在完整路径可见之前截断了选中子树，面板无法证明范围是独占的，此时不提供该操作；在该状态下删除空的预留分支仍然可用。客户端判定只是便捷交互，数据库事务才是待处理任务、等待批准、话题归属和“最后一条路径”规则的权威。
