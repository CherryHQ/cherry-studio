# Agent Note: Agent browser pane recovery and page reset

Status: implemented

English | [中文](2026-10-31-agent-browser-pane-recovery.zh.md)

## Problem

The Agent browser pane (`AgentBrowserView` inside the docked right pane) renders a `<webview>` guest owned by `AgentBrowserRuntimeService`. Before this change that guest had one lifetime: it was created when the pane first attached and was replaced only when the agent navigation target changed. Nothing in the pane could replace it, and the pane's own error surface only handled `did-fail-load`, which a dead or frozen renderer never reports.

Two outcomes were therefore unrecoverable from the UI. A crashed guest left the pane blank while every later browser tool call in that Agent session was routed to the dead `WebContents` in `BrowserGuestRegistry`. A guest whose renderer stopped responding left the pane painted with the last frame, and the address bar, back/forward and reload all drove a renderer that would not answer. In both cases the reported workaround was restarting the application, which also destroys the session's chat state. Issue #23244 records the user-facing report (v2.1.8, macOS arm64).

## Decision

`AgentBrowserRuntimeService.recover(sessionId)` replaces the current guest in place. It snapshots the location committed by the current guest (falling back to that guest's own entry `sourceUrl` while it has not committed one yet), keeps `sessionId`, `securityProfile`, owners, pane anchor and overlay state, clears `failed`, sets `loading: true` and bumps `guestRevision` once. `AgentBrowserRuntimeHost` keys the `<webview>` on `resource.guest` and `guestRevision`, so the revision bump unmounts the dead element and mounts a fresh one at the same URL and partition; removing the element destroys the native `WebContents` immediately (measured: same tick), so no stale target survives the swap. A second `recover` while the replacement is in flight (`guest === null`) is a no-op.

Three entry points invoke it:

- `BrowserOverlays` shows the pane's recovery alert. `WebviewHost` exposes the guest's own lifecycle events through separate callbacks — `onRenderProcessGone` for a dead renderer, `onDidFailLoad` for a failed document — and only the first one reaches the recovery state: `AgentBrowserRuntimeHost` forwards it to `reportGuestHealth(…, 'render-process-gone')`, which latches `recoveryReason` and shows the alert. A failed initial document sets `failed` on the pane's pre-existing error surface instead and never touches `recoveryReason`, so the two conditions stay distinguishable. The alert is informational: it does not replace the guest by itself, because the user loses any page state such as form input on replacement.
- `SessionBrowserView` adds a `Reset page` control to the pane toolbar, next to the shared header actions. It is enabled whenever a guest exists — not gated on `ready`, because the case it exists for is a page that never becomes ready — and disabled only during the replacement gap. This is the only control that can rescue a frozen page: see the measurement below.
- Main reports native health for the agent guest through the `browser.guest.ensure_requested` payload with `kind: 'health'` — accepted only while the reporting `webContentsId` is the current guest — and that is the path carrying `unresponsive`/`responsive`. `GuestSession` treats `render-process-gone` as terminal: it invalidates the annotation document, stops observing, aborts an in-flight attach, rejects pending commands and cancels both mutexes, so a browser tool call that was waiting when the renderer died fails instead of hanging. `BrowserSessionService.acquire` refuses a guest that is destroyed or already crashed, so a crashed guest cannot be re-bound to the session.

The `unresponsive`/`responsive` plumbing is delivered and unit-tested but no behaviour depends on it: measured on Electron 44.9.3, a deliberately blocked pane guest never emitted `unresponsive`, even with the window visible and focused for 132 s. The pane therefore does not claim to detect a hang; the user decides, and `Reset page` performs the same replacement a crash recovery does.

## Alternatives considered

- Automatic replacement on `render-process-gone`: rejected. It silently discards page state (typed form input, scroll position, single-page-app state) without the user asking, and the pane already had a manual affordance.
- Automatic replacement on `unresponsive` with a watchdog: rejected as unbuildable on this platform, not merely risky. The event is not delivered for the pane guest (measured twice, 12 s and 132 s); a watchdog would have to guess from CDP timeouts, which cannot distinguish a slow page from a dead one.
- Reload the surviving `WebContents` after a crash: rejected. `reload()` on a crashed target recovers a crashed renderer but cannot recover a frozen one — the target never replies — so it would leave the reported symptom unsolved and hide the difference between the two states.
- Route recovery through the existing `did-fail-load` surface only: rejected. A dead renderer emits `render-process-gone`, not `did-fail-load`; the pane stayed blank while the error surface believed the page was fine.
- Destroy and recreate the whole pane/runtime on reset: rejected as broader than needed. Replacing the guest keeps the session, owners, overlays and commit-time URL, so recovery does not touch chat state.

## Consequences

While a pane guest is dead, the pane keeps the user's page and the recovery alert, and every browser tool call for that session now fails fast with `debugger_unavailable` instead of waiting for a guest the renderer will not create — `BrowserGuestRegistry` records the crashed binding separately from "no guest yet", so the two cases are distinguishable. A new guest installed into the pane (opening an HTML artifact, switching the security profile) starts healthy and without the previous guest's recovery state: the crash latch and its alert belong to the guest that died and are cleared when a different guest is installed, while a plain unmount (no guest present) keeps the alert. Consumers that reuse the same `WebContents` (the managed MCP tab's own toolbar reload and navigation) keep a recovery path: `GuestSession` re-arms itself on the next document load of that guest, so a reloaded page accepts tool calls again instead of rejecting them for the rest of the session, and it reinstalls its `will-download` listener as part of that re-arm — once, not once per recovery — so downloads that follow the reload are still reported. A transfer already in progress when the guest crashes keeps being observed and still reports its completion, keeping the session busy until it finishes. Recovery always lands on the location committed by the current guest, or on that guest's own entry URL when it crashed before committing one: an in-progress navigation is lost, and an HTML artifact that dies before its first commit recovers to the artifact rather than to the page it replaced. An agent-driven action in flight during recovery fails and must be retried by the model. `Reset page` is available on healthy pages too, where it discards page state — it is a reset, not an undo. Frozen-page diagnosis stays manual: the pane shows no "unresponsive" state, because the platform does not report one.
