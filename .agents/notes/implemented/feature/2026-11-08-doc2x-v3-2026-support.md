# Agent Note: Doc2X v3-2026 document processing support

Status: implemented

English | [中文](2026-11-08-doc2x-v3-2026-support.zh.md)

## Problem

The Doc2X file processor had no user-selectable model contract for the provider's v2 and v3-2026 PDF APIs. Its export request sent a v2 formula field for every model, and the v3-2026 response's structured layout data was unavailable to the Markdown artifact path. This prevented model selection and lost layout information that improves tables and repeated-page boilerplate in document output.

The change crosses the shared processor preference schema, renderer settings, main-process remote polling, persistence of task context, and the provider response schema. Existing users also need the current v3-2026 preset behavior to remain the default unless they explicitly choose another model.

## Decision

The document-to-Markdown capability supports the following Doc2X contract:

- `v3-2026` remains the preset default, and settings allow users to choose `v2` or `v3-2026`.
- `formulaLevel` (0, 1, or 2) and `mergeCrossPageForms` (cross-page table merging) are optional capability overrides. They are sent only on v3-2026 export requests; v2 keeps the documented request shape.
- The selected model is sent in preupload requests. The model and export options travel through remote polling and are included in the whitelisted persisted remote state so a restart does not silently change an in-flight task's export behavior. Missing fields in older state fall back to the restored capability configuration.
- The response schema accepts `version`, `inplace_pages`, page Markdown, and extensible `layout.blocks` data. `page.md` remains the primary page body. Layout blocks remove marked boilerplate, preserve reading order for structured reconstruction, replace Markdown tables with `table_data.html` when available, and render a figure URL when no Markdown fallback exists.
- v2 and legacy responses continue to use the existing ZIP artifact path. v3-2026 responses with structured layout data use Markdown artifact persistence when export controls keep their defaults; non-default formula or cross-page table options keep the provider ZIP path so those options affect the saved output.
- A standalone live E2E script covers upload, parse polling, export polling, and provider export ZIP download for both models. The v3 product path consumes structured Markdown from the parse response; the ZIP assertion verifies the provider export contract. The script requires `DOC2X_API_KEY` and runs manually rather than in CI.

## Alternatives considered

- **Reconstruct every v3 page only from layout blocks.** Rejected because it discards provider Markdown content such as images and code; layout is an enhancement layer instead.
- **Always send v3 export fields.** Rejected because the v2 API has a separate documented request shape and existing v2 behavior must remain compatible.
- **Make v2 the new default.** Rejected because the shipped preset already defaults to v3-2026; changing that default would silently change existing users' output.
- **Put live provider calls in the regular Vitest suite.** Rejected because the check needs a real credential, external service availability, long polling, and remote artifact downloads. Deterministic unit tests cover transformation and request contracts; the script covers the live provider contract.

## Consequences

Users can choose the Doc2X model and v3 export controls while existing explicit overrides remain valid. The v3 Markdown path removes provider-marked boilerplate and retains provider Markdown, tables, and figures where available. Non-default v3 export controls use the provider ZIP so formula and cross-page table choices are applied. The v2 path continues to return a downloaded ZIP artifact. Persisted remote state contains only provider task identifiers, public endpoint and phase data, and non-secret Doc2X options; API keys and signed URLs are never persisted.

Provider additions to block fields or types remain parseable through the extensible block schema, but new semantics may require a later renderer decision. Live E2E evidence depends on provider availability, a valid credential, and the public PDF fixture. Formula and cross-page settings can affect output quality and provider cost or latency; their defaults preserve the existing v3-2026 behavior.
