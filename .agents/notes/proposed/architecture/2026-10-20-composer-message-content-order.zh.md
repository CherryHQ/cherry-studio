# Agent Note: 在用户消息中保留 Composer 内容顺序

Status: proposed

[English](2026-10-20-composer-message-content-order.md) | 中文

## 问题

用户编排了 `text A → image A → text B → file B → text C`，模型收到的却是汇总后的文字和追加在末尾的附件。附件位置本身属于用户表达的含义：移动位置会改变“这张图”的指代。

在已检查的源码版本 `6550a6c9f4c` 中，`createComposerUserMessageParts` 生成一个携带 Composer 快照的文字 part，`ChatComposer` 和 `AgentComposer` 都在发送时追加文件 parts。快照保留了每个文件 token 的 UTF-16 `textOffset`，但 `buildAgentUserContent` 先合并文字再追加文件路径，`ClaudeCodeRuntimeDriver.materializeUserContent` 则分别汇总文字、图片、降级路径和不可用附件。仅修复其中一个阶段仍会丢失顺序。

当前共享附件路由已在原位替换文件，并在整个请求范围内分配提取预算，应保留这一行为。编辑、展示、复制和附件有效性判断也依赖 Composer 快照，因此仅改变发送数组可能导致附件重复或丢失。

本提案覆盖 Chat 和智能体 Composer 的单条用户消息内容顺序，包括排队发送、编辑重发、重试和智能体 steer。不改变不同消息之间的顺序，不增加附件能力，也不承诺模型能理解位置指代。相关报告：[Issue #21554](https://github.com/CherryHQ/cherry-studio/issues/21554)。

## 提案

### 消息契约中的唯一顺序

新 Composer 消息持久化 `MessageData.contentFormat: "ordered-parts-v1"`，`parts` 按阅读顺序排列：

```text
text("text A") → file(image A) → text("text B") → file(file B) → text("text C")
```

已有消息可以没有该标记。发送和编辑 schema、队列载荷、持久化以及 `CherryUIMessage.metadata` 必须透传标记；schema 校验必须拒绝不支持的标记值。使用现有 JSON 存储，无需 SQLite 迁移。对于带标记的消息，`parts` 决定附件成员和顺序；标记用于选择该契约，Composer 元数据不能覆盖它。

非文件 Composer token 保存在其所属文字片段上，使用片段内的局部偏移。文件由实际 file part 表达，保留 `providerMetadata.cherry.fileTokenSourceId` 和现有文件元数据，不再作为文字 part 的内联文件 token 重复存储。若保留非文件 token 必须使用空文字 part，则允许保留只包含 token 的片段。

### 在发送边界构造有序 parts

计算片段前，先用现有 Composer 规范化逻辑对完整草稿处理一次。附件实体化后，由渲染进程中的一个组装函数通过 `fileTokenSourceId` 将 `file:<sourceId>` token 与 file part 配对，按 `textOffset`、再按 `index` 排序，并在对应 UTF-16 偏移处切分规范化后的草稿。复用现有文件构造和序列化辅助函数。不得按文件名、附件数组下标或处理完成顺序配对。

不得单独裁剪文字片段，也不得在片段之间插入分隔符。保留中文、emoji、Markdown 空格和换行。同一偏移处的多个附件按 token 顺序排列；对同一个物理文件的多次引用仍是独立 token 实例。非文件 token 保留相对位置，包括与文件处于同一偏移的情况。

根据提交时的草稿快照决定附件成员，不读取之后变化的 Composer 状态。已删除的 token 不能重新引入附件。新消息若缺失 token 与 part 的关联或关联存在歧义，必须进入现有发送失败流程，保留草稿或队列载荷，不能猜测位置或静默丢弃内容。队列提交和重试复用已捕获的载荷，仅在成功发送后清除。知识范围和其他隐藏控制 parts 在有序可见内容之外保持现有语义。

### 在模型转换中保留顺序

Chat 附件路由继续在文件原位替换为原生内容、提取文字或现有失败说明。保留请求级提取预算、工具允许列表、能力检查、取消行为，以及目前会阻止提供商请求的错误。带标记消息的有效性检查以实际 file parts 为准，因此删除重复的 Composer 文件 token 不会使附件失效。

Claude Code 按转换后的内容序列遍历，不再分组汇总文字和附件。受支持的图片在原位生成 image block，其他文件在原位生成现有文件名和路径表示；OCR 结果和允许降级的不可用文件说明也留在原位。通过现有文件服务解析托管路径，并保留可读性检查。一个输入附件生成替换内容时，共享预处理必须保留来源关联；不得逐文件独立预处理，从而重置预算或 handle 分配。

Pi 保持当前文字和路径能力，在对应文字片段之间输出每个文件引用。本改动不赋予它原生图片能力。普通 prompt、steer 和历史重建使用同一套有序转换。

请求级附件清单可以保留在用户内容之后，它属于补充的工具元数据，不能代替附件的内联位置。Delivery 包装和不可信内容处理继续为所有源自用户的文字保留安全边界。先完成有序内容转换，再应用包装；不得将转换后的文字重新用于 Composer 偏移计算。

### 往返编辑与已有消息

编辑带标记消息时，直接拼接文字片段，不额外添加分隔符，并在 file part 所在位置插入文件 token。将非文件 token 的偏移恢复到完整草稿坐标，保留稳定附件身份，并在保存或发送时重建有序消息。移动、删除和新增附件都会更新成员及顺序。保留已有助手消息的工具锚点。

消息展示、复制、Markdown 导出和文字提取按 part 顺序遍历带标记消息。每个文件在原位展示一次，不提升到统一附件区，也不同时以文件块和 Composer chip 重复展示。纯文字投影可以使用现有附件标签或路径，但必须保留位置。仅携带元数据的空文字 part 不得产生可见空白块。

没有标记的消息保留其存储顺序和旧附件有效性规则。不重写历史数据库，也不根据文件名猜测旧插入位置。只有用户明确编辑旧消息时，才恢复可靠的现有 Composer token 身份和偏移；未匹配的附件使用新身份保留在可编辑草稿末尾。新提交采用有序格式。没有标记但已经提供交错 parts 的 Gateway 消息保留输入序列。

### 职责与交付

共享消息类型和 schema 负责格式标记。渲染进程 Composer 工具负责草稿到 parts 的组装及编辑恢复。主进程附件路由和 runtime 适配器消费有序 parts，不理解 Composer 布局。共享消息展示和导出负责各自投影。

通过 Spec-first stack 交付：本双语契约；契约、Composer、持久化和编辑实现层；runtime、展示和验证实现层。中间层保留 proposed 状态。只有下面所有验收条件都有实际证据后，最终层才能将三件套移到 implemented。修改仅限于现有分组或元数据规则会违反本契约的消费者。

## 考虑过的替代方案

- **仅排序附件。** 所有文字仍在附件之前，无法保留文字与附件的对应关系。
- **各 runtime 独立根据偏移重建。** 这会让 runtime 耦合 Composer 内部结构，重复兼容逻辑，并使持久化消息和编辑行为不一致。
- **只改变 parts，不增加格式标记。** 现有有效性和展示逻辑使用 Composer 文件 token 决定附件成员；隐式改变语义可能隐藏有效文件或恢复失效附件。
- **保留一份并行的有序内容列表。** 两个权威来源需要在编辑、持久化和重试过程中同步，而已有 `parts` 数组已经能够表达顺序。
- **根据名称或数组位置推断历史关联。** 同名文件和缺失身份使这种做法不安全。保留旧消息，仅升级用户明确编辑的草稿。

## 验收条件

- AC1 — Chat 和智能体严格按照 `text A → image A → text B → file B → text C` 持久化并提交内容，同时覆盖文件在开头、纯文件、相邻文件和同偏移 token (verification: 渲染进程组装和 Composer 发送测试)
- AC2 — 中文、emoji、换行、Markdown 硬换行、缩进及非文件 token 在组装和编辑往返中保真，不添加分隔符、不裁剪片段、不改变 token 位置 (verification: 渲染进程草稿和消息编辑测试)
- AC3 — 同名文件和重复引用保留独立身份；异步实体化乱序完成不会改变 parts 顺序；新发送关联缺失或歧义时保留未发送草稿或队列项，且不调用发送边界 (verification: 渲染进程 Composer 和队列测试)
- AC4 — 保存重载、排队发送、重试、编辑重发和智能体 steer 保留格式标记、顺序及准确附件成员，已删除文件不会重新出现 (verification: schema、真实数据库持久化、渲染进程消费者和 runtime 输入测试)
- AC5 — Chat 提供商输入与 Claude Code SDK 输入在来源位置保留原生图片、提取或 OCR 内容、文件路径和允许的失败说明；现有预算、能力失败、路径解析和附件允许列表保持原有契约 (verification: 主进程附件路由及提供商/runtime 适配器测试)
- AC6 — Pi prompt、steer 和历史重建保留交错文字与路径引用；各 runtime 适配器中的 delivery 内容保持现有信任边界 (verification: 主进程智能体内容、Pi、Claude Code 和 delivery 测试)
- AC7 — 展示、编辑、复制和导出保留带标记消息的顺序，每个附件只展示一次；旧消息仍可读取，不猜测有歧义的旧附件关联，没有标记的交错 Gateway 输入保留原顺序 (verification: 渲染进程展示/导出、主进程转换和旧格式 fixture 测试)
- AC8 — 在受跟踪的 Electron 实例中演示 Chat 和智能体交错内容发送、重载、附件移动或删除、编辑重发及排队提交，持久化 parts 和捕获的适配器/提供商输入与 Composer 一致 (verification: Electron 证据；提供商或模型理解能力不属于本验收声明)
- AC9 — 最终实现仅包含已核实的变更范围，更新语义受影响的参考文档配对，并记录精确的定向检查及尚未覆盖的平台/提供商限制 (verification: 变更范围、文档影响检查、改动文件格式/lint、受影响类型检查、定向测试和文档门禁)

## 风险

遗漏格式标记的透传可能让有序消息回退到旧有效性规则，导致文件丢失。功能完成前，必须对持久化、投影、队列和编辑边界进行往返测试。

切分文字会暴露那些使用换行合并文字或只读取首个 Composer 快照的消费者。应审查受影响的发送、编辑、展示和导出链路，而不是再增加一个全文权威来源。

Claude Code 当前按路由类别汇总附件。替换实现必须在重新组装内容时保留文件身份、全局预处理决策和 delivery 安全边界。SDK 调用证据只能证明 Cherry Studio 生成的载荷，不能证明远端模型如何理解。

旧版本应用不理解格式标记，可能错误展示或重发新消息。本提案保证更新后应用能够读取旧消息，不保证旧二进制能正确编辑新消息。不包含历史数据重写或自动降级。

本 Spec 尚未完成实现或运行时验证。验收条件在实现层提供证据之前均为待完成。
