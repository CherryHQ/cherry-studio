# Agent Note: Pi Durable SQLite 图片去重

Status: proposed

[English](2026-11-16-pi-durable-image-storage.md) | 中文

## 问题

Pi Durable 1.5.2 将原生记录序列化为 JSON 存入 SQLite。因此，内嵌图片保留了 Base64 编码开销，还可能在提交、历史条目、任务和文档内容中重复出现。目前尚未针对用户数据库测量实际重复量和总磁盘节省量。上下文压缩不会删除保留的历史，重新写入相同记录也不会移除其中的图片负载。

本提案负责 Durable SQLite 存储内部的图片物理表示。[运行时契约](2026-10-17-agent-runtime-contract.md) 继续负责运行时边界。[桌面集成](../../../../src/main/ai/runtime/piDurable/README.md) 保留现有原生身份、分支、恢复和投影契约。产品会话消息仍是投影，不替代原生恢复数据源。

基线检查使用已发布的 `@earendil-works/pi-durable@1.5.2` 包：`storage/sqlite/rows.js` 使用 JSON 编码，`commit.js` 写入记录和文档修订，`storage.js` 还原读取结果。未在该 SQLite API 中发现图片资源钩子。仓库现有依赖补丁必须完整保留。

## 提案

### 存储归属

在 Pi Durable 上游的 SQLite 存储实现中增加此能力。Cherry 使用兼容版本；若尚无发布版本，可以将经过审阅的源码变更及等价测试纳入现有依赖补丁。不要添加在原生提交前替换图片的 Cherry 专用包装层，也不要导入 SDK 私有模块。其他存储实现保持现有逻辑契约和表示方式。

在同一个原生 SQLite 数据库中使用二进制 BLOB 表，以解码后图片字节的 SHA-256 为键。在一个 backend 内去重，覆盖其中的根会话、子会话和分支。MIME 类型和其他图片元数据保留在各引用处，确保相同字节搭配不同元数据时仍可正确往返。独立 backend 之间共享资源存储不在本次范围内。

在编码后的记录中保存带版本的引用，并在每个存储读取边界还原。公开记录、模型请求、观察结果、归档和逻辑导出继续包含原始图片内容。编码必须能区分自身引用和任意用户 JSON，不能占用用户值。规范 Base64 必须精确往返；不支持或不规范的编码保留内嵌形式，不静默归一化。普通文本中嵌入的图片不在范围内。

覆盖原生结构化图片负载的所有持久化位置：提交、历史条目、任务状态及结果、文档基线或增量。文档重建、复制和增量应用必须操作与之前相同的逻辑值。不要改写碰巧类似 Base64 的任意字符串。按记录分页批量读取图片，并限制临时解码缓冲区；不要预先还原整个 backend。

### 原子性与兼容性

在同一个 SQLite 事务中提交图片字节、记录引用和引用归属。被拒绝的批次和事务回滚不能留下指向缺失资源的已提交引用。资源缺失或损坏必须明确报告存储失败；不能替换为空内容，也不能重新执行工具来生成资源。

追加原生 schema 迁移，不能改写已有迁移。新读取器同时支持旧内嵌记录和新引用。在独占 backend 的条件下，以有界、可恢复的事务转换已有负载，保留记录 ID、提交序号、文档版本、分支祖先和待恢复执行状态。迁移必须与桌面端严格的 `openExisting` 路径协调，不能静默创建或替换缺失的库。不支持新格式的旧运行时打开迁移后数据时必须明确失败；降级需要恢复兼容备份。

### 备份与回收

每个 backend 仍使用一个 SQLite 文件。图片资源与记录共享一致的 SQLite 备份边界，或现有暂停写入并完成检查点的备份边界。恢复不能依赖原始附件文件或外部图片目录。逻辑导出还原图片，使通过其他受支持存储格式导出和导入时保留内容，不隐式依赖原数据库。

跟踪所有保留的编码记录和文档修订中的引用，不能只检查当前模型上下文。替换任务或提交记录、删除修订时，在事务内更新资源引用。只有所有保留记录都不再引用某个 BLOB 时，才允许回收，并与提交串行协调。上下文压缩、任务完成、关闭面板或删除一个分支均不代表资源不可达。删除 backend 时随数据库释放资源。物理空闲页回收属于独立维护；本提案不安排定期重建数据库，也不引入历史过期策略。

## 考虑过的替代方案

- 独立的内容寻址图片文件：同样能去掉编码开销，但需要协调文件发布、SQLite 提交、备份清单和孤儿回收。等证据证明跨 backend 共享或文件系统存储有必要时再考虑。
- 不去重的 BLOB：去掉编码开销，但不同记录仍保留重复负载。
- 从产品消息重建，或只保留压缩后的上下文：改变恢复和历史分支语义，而且重新导入全部图片时仍未解决重复负载。
- 压缩整个 JSON 记录：可能减少字节，但保留了重复图片归属，并改变无关内容的编码。

## 验收标准

- AC1 — 提交、历史条目、任务、文档修订和同 backend 分支中重复的相同结构化图片字节只占用一份资源，MIME 元数据和逻辑值保持往返不变。（验证：上游 SQLite 存储契约测试）
- AC2 — 类似资源引用的普通 JSON、不规范 Base64、混合文本与图片结果、文档增量和分页读取保留原有含义，不进行无界的整库还原。（验证：上游编解码及存储契约测试）
- AC3 — 批次拒绝、事务失败和进程中断不能发布悬空引用；资源缺失或损坏时明确失败，不伪造内容或重放工具。（验证：上游 SQLite 故障注入与进程重启测试）
- AC4 — 含数据的旧库在转换中断后可继续迁移和恢复，保持相同的原生 ID、分支检查点和待处理输入；不支持新格式的旧读取器拒绝该格式。（验证：上游迁移夹具与桌面原生上下文集成测试）
- AC5 — 在新目录备份恢复后，无需源附件即可保留根会话及子会话图片和恢复能力；逻辑导出与导入完整保留所有图片。（验证：桌面备份集成与上游存储互换测试）
- AC6 — 替换或移除最后一条归属记录后允许资源回收，而历史修订、保留分支和并发写入阻止过早删除。删除整个 backend 后不遗留独立资源。（验证：上游回收与桌面 backend 生命周期测试）
- AC7 — 可重复运行的图片密集夹具分别报告转换前后的数据库与 WAL 字节数、资源数量、写入及读取延迟和峰值内存；编码记录中不再存在重复负载，资源字节数等于唯一解码负载的总量。（验证：上游基准夹具与桌面集成证据）

## 风险

本方案改变上游持久化格式，需要针对 Spec 当前提交的明确批准后才能实施。必须验证上游各适配器的 SQLite 驱动 BLOB 支持、批量参数编码和所有读取路径；仅 Node 验证成功并不足够。哈希和还原增加 CPU 与内存成本。去重降低表示开销和重复字节，但保留的唯一图片仍随历史增长。它不降低模型请求的 Base64 大小，也不保证产品消息数据库缩小。本提案不代表已经修改运行时、执行迁移、提交上游或测得磁盘节省量。
