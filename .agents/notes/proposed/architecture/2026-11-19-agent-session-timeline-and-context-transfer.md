# Agent Note: Agent session runs, ordered items, change cursor, and context transfer

Status: proposed

English | [中文](2026-11-19-agent-session-timeline-and-context-transfer.zh.md)

## Problem

Agent sessions need three things the current model cannot express together: an orchestrator that moves a conversation to another harness or model, history reads and rendering that touch only what changed, and a run timeline in which a steer forms a stable boundary.

At Cherry `a83cd16c826bbd01b28ebe968e0015f5edd7b8ee`:

- One assistant row is one product reply spanning many native messages. [RootMessageProjection](../../../../src/main/ai/agentSession/RootMessageProjection.ts) maps native sources to rows through `checkpointMapping.root` entries of `{ messageId, offset, count }`; [ChildThreadProjection](../../../../src/main/ai/agentSession/ChildThreadProjection.ts) keeps an index-based `composition`.
- A steer rolls the reply. At native placement, `reserveSteerContinuation` in [AgentSessionRuntimeService](../../../../src/main/ai/agentSession/AgentSessionRuntimeService.ts) settles the current reply and opens a continuation row under the steer. The renderer keys parts by array index (`${message.id}-part-${index}` in [MessagePartsRenderer](../../../../src/renderer/components/chat/messages/blocks/MessagePartsRenderer.tsx)).
- [MessageProjection](../../../../src/main/ai/messages/MessageProjection.ts) coalesces for 80 ms, deep-compares whole messages and sends the full order. Agent history pages refetch on each data change ([useAgentSessionParts](../../../../src/renderer/hooks/useAgentSessionParts.ts)). Markdown re-splits the whole text on every update and memoizes blocks by content ([parseLatexMarkdownBlocks](../../../../src/renderer/components/markdown/parseLatexMarkdownBlocks.ts)).
- Changing the model within a harness keeps native history: pi-ai `transformMessages` adapts Pi and Pi Durable messages, and the Durable connection rebuilds on the same conversation. Changing the harness is unsupported: drivers reject a branch bound to another runtime ([durableContext](../../../../src/main/ai/runtime/piDurable/durableContext.ts)), and the proposed [session runtime binding](https://github.com/CherryHQ/cherry-studio/blob/a74bb2dd95182cc9f063cac9798b4bdbb2590a8b/.agents/notes/proposed/architecture/2026-11-12-session-runtime-binding.md) makes the binding immutable.
- Product history reaches a harness only through [readSessionHistory](../../../../src/main/ai/agentSession/sessionHistory.ts), which DeepSeek import relies on. It runs only when no prefix row carries native identity, sends the whole path without a total budget, and records nothing about what was delivered.

This note specializes the [runtime contract](2026-10-17-agent-runtime-contract.md). It partially supersedes the steer, part identity and cursor sections of [message-list subscriptions](https://github.com/CherryHQ/cherry-studio/blob/f65c54cd6069caf5b1efa3c99ea1fe08ce543645/.agents/notes/proposed/architecture/2026-11-09-message-list-subscriptions.md), the renderer cut model of [native steer](https://github.com/CherryHQ/cherry-studio/blob/ab83909a7c637c81c6d59221f76d1aad919d2add/.agents/notes/proposed/bug-fix/2026-11-09-agent-native-steer.md), and the immutability rule of session runtime binding. [Tool result boundaries](../../implemented/architecture/2026-11-09-tool-result-projection-boundaries.md) is unchanged: its publication revision stays a delivery sequence, separate from the storage cursor below.

### Publication ownership

- [TopicMessageProjection](../../../../src/main/ai/streamManager/TopicMessageProjection.ts) and [ChildThreadProjection](../../../../src/main/ai/agentSession/ChildThreadProjection.ts) supply accepted message views to `MessageProjection.updateAccepted()` for structural changes. Each owner captures mutable native values at admission and preserves untouched part identities.
- [ThreadMessageProjection](../../../../src/main/ai/agentSession/ThreadMessageProjection.ts) applies child observations in order. `accept()` signals completion. Updating two existing messages in a batch must not enumerate the history to return changed rows. The connection discovers child relationships. Relation-only observations do not invalidate the message view or schedule archive reconciliation.
- [MessageProjection](../../../../src/main/ai/messages/MessageProjection.ts) batches addressed edits and publishes revisions. The renderer applies live edits by part ID and uses the structural reducer for message membership, ordering and reconciliation.
- Root pages read the existing topic projection. After a successful history read they release only the terminal attempts covered by that read. Active attempts, pending placeholders and unresolved writes keep their live content. Temporary conversations own their completed replies. Only speech consumers subscribe to text edits.

Pi and Pi Durable already forward text-only edits by part. When a `message.parts` batch includes a `put`, the shared feed reads the source message to produce a `message.reconcile` and Main clones its parts. Channel delivery already receives Agent part changes through `sink.part(change)` and applies them to its text reader. Preserve that downstream path when fixing the feed. [ThreadFeed.projectionEvents](../../../../packages/agent-runtime/src/observation.ts) · [ThreadProjection.accept](../../../../src/main/ai/agentSession/ThreadProjection.ts) · [AiStreamManager](../../../../src/main/ai/streamManager/AiStreamManager.ts) · [ChannelAdapterListener](../../../../src/main/ai/streamManager/listeners/ChannelAdapterListener.ts)

Pi Durable captures committed archives before closing native storage so retained handles can finish their archive reads. Each subsequent `archive()` call on a retained handle clones the entire cached archive. Releasing the last handle after shutdown leaves the cached archive reachable from the runtime. [Pi Durable runtime](../../../../packages/agent-runtime-pi-durable/src/runtime.ts)

## Proposal

### 1. Run owns execution and Timeline owns content

A run begins when the harness places its triggering input and settles at its native terminal. The existing assistant row is its physical record. Its ID is the run ID, and its status, statistics, model and branch ancestry stay on the row. An input accepted into a queue retains its persisted input ID and queue state. Upon placement, it joins the active run as a steer or starts its own run. `replyId` records execution ownership and `parentId` records ancestry. Steer reserves no continuation row. Late evidence applies to its original run. A background wake that begins a new native execution after settlement receives a new run ID.

The timeline contains input references and output parts. An input item references its existing row. The part table from #24051 is the sole durable output body. Each new output part has one owner run and one position. Read adapters may assemble `parts[]` for history consumers such as export and model context. Rendering groups items independently of their durable ownership.

Root and child use the same contract. Each child archive has its own order and revision. Migration keeps existing message IDs, branch and fork anchors, attachment references, and saved part IDs. It identifies legacy run membership using existing reply and composition evidence; when evidence is incomplete, preserve the existing boundaries. Read an existing branch from its selected ancestry and preserve its recorded boundary. Preserve the original tool-result owner while resolving old archive references to part IDs.

#### Execution, content and display have different lifetimes

At `931d854cb87d30bc45d99fcfeba488ac2eb05b27`, #24051, #24100 and #25406 provide independent part storage, completion writes, addressed publication and keyed subscriptions. They do not complete the Run cutover: `AgentSessionTurn` still combines execution and reply delivery, and `reserveSteerContinuation()` still reserves another assistant row. Treat these as delivered prerequisites, not evidence for AC1.

| Unit | Identity and lifetime | Changes that notify it |
| --- | --- | --- |
| Run | The existing assistant row ID, from native placement of its trigger through native execution terminal | Execution status, pending interactions and usage |
| Input | The persisted user row ID; acceptance, queueing, placement and outcome are separate facts | Its own delivery/placement/outcome |
| Part | The existing persisted part ID and owner Run; position is fixed on admission | Its addressed body/state edit |
| Display segment | Derived contiguous timeline items; a Run can appear on both sides of an input | Segment membership and presentation classification |
| Delivery attempt | Existing `turnId`/attempt guards for stream attachment and callbacks | Transport attachment and stale-callback handling |

`runId` is the domain name for an assistant record's existing ID; it is not another generated ID, table or service. Existing `turnId` must not define durable execution ownership. Keep it only where a real delivery attempt needs correlation; remove redundant aliases when callers migrate. Reserve a pending assistant record before dispatch if the existing admission path needs one, but do not describe reservation as a running native execution. Unknown admission recovers through the existing input/context identity rather than allocating another Run.

One native execution may accept multiple inputs and emit multiple native assistant messages. Individual input outcomes, model-message ends, part finishes and successful history reads cannot settle its Run. The adapter reports whether placement joins an active execution or begins a new one; the composer mode, `followUp` spelling or session-wide busy flag cannot decide that boundary. Background wake starts a new Run only when native evidence establishes a new execution after the previous Run settled. Compaction and approval wait retain the current Run.

#### Placement and settlement transition contract

| Existing fact | Required Run operation | Timeline and persistence |
| --- | --- | --- |
| Input accepted or queued | Retain the input ID; no active-Run association is inferred | Save existing acceptance/queue state; no placed `pos` is fabricated |
| Trigger placed into a new execution | Activate its reserved Run, or create one under the existing recovery path | Bind input `replyId` and its position before publishing that placement |
| Steer placed into the active execution | Link this input to the same Run; reserve no continuation | Keep every existing part owner/ID/position; later new parts receive new positions |
| Queued follow-up placed after native terminal | Start a new Run | Retain the queued input ID and allocate its actual placement |
| Part finished or an input outcome arrived | Update that part/input only | Reuse completed-part commits; do not settle Run status or repeat usage settlement |
| Compaction, approval wait, or observer detach | Preserve the executing Run | Update existing controls/markers; detach never cancels execution |
| Stop requested | Invoke the existing native Stop path for the active execution | Retain received parts; do not invent a successful native terminal |
| Native terminal, or existing confirmed connection-failure outcome | Settle the matching Run once after required writes succeed | Flush unfinished received parts and settle statistics; stale/duplicate callbacks cannot settle another Run |

Use the existing synchronous transaction for the placement's input link, position and required checkpoint association. Publish after commit. Do not add an event archive or a second admission state machine. The adapter's placement/terminal contract must identify the executing context and existing execution owner; if native evidence is ambiguous, use the current recovery/error path instead of guessing from the newest user row.

The runtime cutover removes `reserveSteerContinuation`, `reserve-steer`, and the `steer-transition` source/reply pair for same-execution steer. `AgentSessionRuntimeService` remains the lifecycle owner. Separate the Run's native lifetime from the existing stream delivery state; a view handoff closes or replaces observation, not execution. A source registered before steer continues to route late updates to the same Run and part. Output ownership, usage, approvals and tool-result lookup must not follow the newest display segment.

Renderer derives display segments from input and part positions. A segment key comes from its stable leading item, never a transport revision or an array index. An existing part stays under its compatible parent when a later input is added; later new output forms a segment after that input. An already-open text part or tool retains its original position while updating. This decision does not promise that every byte arriving after a click appears below that click. Immediate local input display, if enabled, needs a preallocated input identity and an explicit unplaced state; native placement remains authoritative. Do not manufacture a continuation assistant record or move a running tool to simulate it.

#### Table relationships and fields

The following names use the TypeScript schema convention. **Existing** fields describe the current stack. **Required** fields are part of the Agent timeline cutover. **History** fields ship with incremental history reads.

```text
agent_session.id
  ├─ 1:N agent_session_context.sessionId
  └─ 1:N agent_session_message.sessionId
             user.replyId ──────────────► assistant.id (Run)
             user.inputContextId ───────► agent_session_context.id
             message.parentId ─────────► message.id (branch ancestry)

agent_session_message.id
  └─ 1:N agent_session_message_part.messageId
             agent_session_message_part.id
               └─ 1:0..1 agent_session_tool_output.partId (proposed)
```

`inputContextId` records the native binding of an input, including one still queued. Main knows the live Run's executing context from native placement. Historical queries may derive it from an immutable, unambiguous triggering-input association. The existing reverse `replyId` lookup supplies neither uniqueness nor immutability. Leave attribution unknown where the evidence is incomplete. The Timeline cutover and fresh-context initialization require no assistant context column. Recovery reads pending assistant rows by session and linked inputs by `(sessionId, replyId)`. For legacy replies it can read the parent by primary key. An explicit reply link takes precedence.

Main verifies same-archive ownership for the input-to-Run link, part owner and anchor. The input rows and output part rows share a single position allocator; their separate per-table indexes cannot enforce uniqueness across tables. For result lookup, the part determines its archive through its owner. A tool result change that is visible to history advances the owning part's revision in the same transaction.

### 2. Ordered items and durable commits

| Field | Assigned | Use |
| --- | --- | --- |
| `pos` | Once at input placement or first part admission | Timeline order within the archive |
| `rev` | Once per visible history transaction, shared by its changed rows | Committed history cursor |

One Main owner allocates positions for an archive, starting from the committed high-water mark. Keep a new part's ID, position and contents in the live Timeline. Opening a part and appending text use no SQLite. While the Run is active, completion saves the changed part, its position and associated tool result or file references in one transaction. Terminal and Stop save the remaining received parts and settle the Run using the same IDs and positions. Publish committed history after the transaction succeeds. A failed save leaves the live content available to the existing retry or terminal path.

Timeline order is fixed when items are admitted. An open part remains above a later steer while it grows, even if the steer commits first. The part keeps its previously allocated position when it saves. Windows attaching or reconnecting to the same Main process read its live Timeline. After a Main restart, saved entries retain their order and IDs. Uncommitted parts may be lost. If native recovery supplies their content, it enters through normal admission and can receive a new ID and position. Legacy rows receive positions in their established display order using existing evidence.

Root publication requires the archive position on `part-open` (text or reasoning) and `part-add` (tool or data). Subsequent edits address the existing part by ID and cannot specify placement. For example, a compaction boundary C admitted between new text blocks A and B retains its place in `[A, C, B]` when A receives a suffix. The root checkpoint records each source's part IDs, including nonadjacent IDs in display order. Previous offset/count checkpoints use the stored row sequence. The current child projection supplies its own predecessor when composing native fragments.

### 3. Stable part identity and result ownership

Assign one part ID at first admission and retain it on subsequent live and persisted updates. The native key identifies the source block using its context, canonical native source and block key. Use a tool-call ID or explicit data ID when reported. A native index is valid inside a source whose block ordering is stable. When an adapter proves a provisional-to-committed replacement, use the existing ID and position. For an unproven mapping, reconcile that source at the adapter boundary or request a new baseline. Across Main restarts, the identity guarantee applies to committed parts. A product message index and a display group ID carry no storage identity.

The same part ID addresses the current tool result in Main, SQLite and renderer invalidation. Migrate the existing latest-only sidecar association from its original message and tool-call owner; payload stays in the existing sidecar. A pending lookup uses the accepted live result. After atomic handoff it uses the committed result. An output replacement invalidates only that part. New writes use stable source associations; legacy offset/count compositions remain readable for existing history and recovery.

#### Context binding and projection ownership

`agent_session_context` owns the native binding and native fork recovery. The Timeline owner maintains source-to-part associations, positions and removal state. New Timeline writes use those associations in place of the root array ranges and child composition. Read old `checkpointMapping.root` and `checkpointMapping.child` for legacy recovery. A fork publish owns only `checkpointMapping.fork` and preserves other recovery sections in the same transaction. The current [fork publish](../../../../src/main/data/services/AgentSessionContextService.ts) replaces the whole mapping, so this preservation needs a regression test.

New forks start only at supported boundaries after successfully completed Runs. A same-harness native fork requires a checkpoint for that exact boundary. Renderer offers Fork only at eligible boundaries, and Main rejects steer messages and positions inside a Run before preparing a fork.

Fork and edit share one Run history projection over the selected branch's existing assistant IDs, input `replyId` links and admitted `pos` values. Group each Run with its original input and placed steers, and order Runs by their first admitted input. Message ancestry selects the branch but does not define execution order or native cutoffs. Fork copies whole Runs through the selected boundary and excludes bound, unplaced inputs; positionless legacy rows without admission evidence remain readable. Edit rejects in-Run steer inputs, takes the preceding Run's checkpoint, and atomically reconnects the selected path in Run order before replacing the target Run and later descendants. Preserve earlier Run IDs, linked inputs, checkpoints and sibling branches.

The Main history resolver owns admission classification, predecessor selection and cutoff membership. Its public surface exposes resolved targets and readonly, opaque fork/edit plans rather than an ordered row array. Edit capability checks consume the same resolution as native preparation. The product commit accepts only the read phase's version-bound edit plan and rejects changed history before applying its planned parent changes and replacement boundary. Known unplaced or withdrawn inputs stay in product history but cannot supply a native predecessor or enter a fork prefix; an admitted steer cannot produce an edit plan. Resolve an addressed nonactive branch against its own path. Fork selects retained IDs from metadata before loading parts and archived tool results. Native recovery persists confirmed placement independently of Run success, so an error or paused Run's admitted input is not mistaken for an undelivered queue entry. No new Run table or parallel event store is required.


An explicit native source replacement resolves its alias to the existing `partId` and position. A user deletion persists a suppression record for the canonical source in the deletion transaction, so replay cannot restore its content. Retain that record until the source can no longer be replayed. A history cursor reset refreshes the read view. Replay suppression separately protects the Timeline writer.

After the deletion commits, Main notifies the live Timeline owner of the affected part IDs. The owner releases their body references, accepted results and indexes, then publishes removal to subscribed renderers. The current root projection releases its live payload on successful commit, polls the context row for removals and can reload stored parts for comparison. The cutover delivers removals directly. Validate the released references with heap retainers in Electron. [RootMessageProjection](../../../../src/main/ai/agentSession/RootMessageProjection.ts)

### 4. Incremental acceptance, publication and recovery

The Main timeline owner accepts normalized source changes. Its single application produces the changed item or text suffix and any durable work. Adapters that receive cumulative native messages derive ordered `message.parts` edits for the affected source at ingress. `message.reconcile` carries a single native source for initial installation, authoritative correction, metadata changes, or a confirmed source alias. Neither the persistence writer nor the publisher rescans a reply to infer its changes.

The live ingress addresses a single part ID. Text and reasoning use `open`, `append` and `finish`. `put` accepts only other part types. Opening creates an empty part once, appending adds only the suffix, and finishing keeps the accumulated body. The kind of an existing part is fixed. A known native block can receive an authoritative `correct` at its existing address. Recovery handles changes whose source or order must be re-established.

For a pure text append, the native preview producer supplies the changed source block identity and the suffix before building any cumulative view. Main resolves that identity to a stable part ID. The live append handlers receive only the suffix and the affected part or its key. Build scoped snapshots for initialization, attachment or recovery. In `.oxlintrc.json`, apply `no-restricted-imports` overrides to the append producer and handlers. Reject imports of whole-view types, snapshot builders, history readers and whole-message diff code, including their re-exports.

These signatures show separate call sites in Pi, Main and the renderer. The scheduler places inputs. The Timeline owner records `runId` and `pos` on admission and accepts the existing part operations. A generic `insert(item: TimelineItem)` would also accept a complete text or tool part and bypass the live writer.

```ts
declare function restoreCommitted(entry: PiContext[number]): void
declare function publishParts(patches: readonly PublishedPartPatch[]): void
declare const reader: ProjectionPartReader

restoreCommitted({ id: sourceEntry.id, message })
publishParts([{ type: 'part-append', partId, text: suffix }])
const part = reader.read(partId)
```


The renderer applies one ordered batch before notifying subscribers by item or run ID. Only an affected part subscriber sees a text append. Inserts and removals also notify order consumers. Main coalesces pending operations by part for delivery without recomputing the current view. A complete, scoped baseline is used for attach or recovery. Live batches carry their own revision and publication identity; a gap, unknown target or stale publication triggers existing baseline recovery.

History reads take a consistent snapshot and its committed cursor. Subsequent reads return changed rows after that cursor and advance at a complete commit boundary. The cursor includes the view scope and an archive reset version. Deletion advances the reset version in the same transaction; a branch switch changes the view scope. A reader with an old cursor therefore gets a baseline even if it missed the invalidate notification.

#### From native events to the same part operation

The adapter identifies the native source, its block and the change. Main associates the source with its Run and assigns or reuses the product `partId` and `pos`. Register a new source before publishing its first visible block. A block that starts with text produces an `open` followed by one `append` for the initial text. An empty block remains addressable. The proposed live writer and observation batch reuse the existing event types. [Runtime contracts](../../../../packages/agent-runtime/src/contracts.ts)

```ts
type LivePartInput = NativePartUpdate | Extract<MessageObservation, { type: 'message.parts' }>
type ProjectionEvents = readonly LivePartInput[] | readonly Exclude<ObservationPayload, LivePartInput>[]
```

A native suffix can pass straight through as `message.text-append`. A producer that has ordered edits for one source sends its existing batch. `RuntimePartEdit` already restricts `put` to non-text, non-reasoning values. Give the writer only the capabilities its operations need. History reads and snapshot construction belong to attachment and recovery. Source installation and alias replacement have a separate entry point. Apply an authoritative correction to the addressed block when the SDK identifies it. Reconcile one source when the SDK only supplies its complete value. Control observations keep their position relative to content.

### 5. Initialize a fresh context from session messages

A harness change or an explicit request for a fresh context creates a new native thread in the target backend. Switching A → B → A creates A₁ → B₁ → A₂. A model change within a harness keeps its existing context. One session may retain several root contexts for its branch history.

1. **Choose the cutoff.** Main serializes the switch with input admission and branch changes. Begin at a settled point with no active Run, background work, unresolved approval or question, or unconsumed input in the old context. Capture the selected ancestry and its cutoff before the new input.
2. **Build bounded reference history.** Read `agent_session_message` and its parts on the selected ancestry through that cutoff, including settled rows produced in earlier native contexts. Share formatting with the existing [DeepSeek import](../../implemented/feature/2026-11-17-deepseek-agent-import.md) path. Admit only settled conversation content. Exclude reasoning and hidden data, represent completed tools as bounded excerpts, and retain necessary managed attachment references. Select entries within the target model's total reference budget and a byte budget before hydrating bodies. Prefer the last user message, last assistant message and first user message, then newest to oldest. Omit oversized results when a bounded excerpt is unavailable, and identify the omitted count and `pos` range. This read never loads the entire branch or full sidecar results to trim them afterward.
3. **Initialize once and commit the binding.** Pi Durable writes `cherry.reference-context` separately before the first submission. Pi and Claude Code prefix the reference to the first input. Main stages the input's target binding before submission so recovery can resolve native admission. Once initialization and the first input's admission are confirmed, publish the new root binding at the first input's branch anchor and retain the old anchors and checkpoint mappings. A failure before admission leaves the old binding active. When admission is uncertain, reconcile against the recorded input and target before retrying. Subsequent inputs to the new context use its native history.
4. **Release the old runtime.** After the binding commits, drain the admitted old-context updates, close its connection and drop its subscriptions and live projection references. Release only resources owned by that context. The switch retains the old native transcript and checkpoint mappings for resume, recovery and native fork or edit-and-resend on earlier branches. Preserve child ancestry and shared backends. Physical cleanup is a separate operation and requires backend support and proof that no retained context, task or checkpoint still uses the backend.

The reference supplies model context only. It adds no product transcript rows or restored native tool state, tasks or checkpoints. Each target is fresh, so initialization uses the binding and input identity without an `agent_session_context_transfer` table, Run coverage tracking or a new history copy in Cherry SQLite. At an eligible Run boundary, a same-harness fork uses its native checkpoint. A cross-harness fork initializes a fresh thread from the selected branch prefix through that boundary. New child tasks still receive their task prompt, and child forks stay within the parent's backend.

## Alternatives considered

- Run, attempt or turn tables, or one row per native assistant message: they duplicate an assistant row that already carries status, statistics and model, or multiply rows that item-level identity already correlates.
- Character cuts at steer time, segment rotation of an open part, or regrouping ongoing tools after the boundary: each adds cut or move state with reload obligations. Current T3 fixes positions at first write instead.
- The transport revision as the storage cursor, or T3's full event log: the transport revision is scoped to one publisher and subscription, and T3 compacts superseded events itself, so a row `rev` gives the same cursor without a log.
- Persisting an empty row before a part completes: it preserves an uncommitted part's identity across a Main crash at the cost of a separate synchronous write per part and recovery for rows without content. Recover committed bodies and keep new parts in memory until their first body write.
- Deriving public IDs from raw native message IDs: a provisional source can be replaced when it commits, so direct derivation can rekey a mounted part. Preserve the admitted ID and reconcile replacements at ingress.
- Converting product history into native Durable entries, or native-to-native converters: session messages already reach every harness through one builder.
- An LLM-written summary by default, as in [#24704](https://github.com/CherryHQ/cherry-studio/pull/24704): it costs a model call and varies in quality. It stays a compatible optional strategy.
- Reuse an earlier context and send a delta: it keeps that thread's native continuity, at the cost of tracking Run coverage and reconciling deliveries. The first version needs only fresh-context initialization.
- Typing a whole projection more narrowly at each consumer leaves its contents reachable from queued objects and allows the implementation to rebuild the complete view. Pass the actual operands to the existing owner and reserve complete views for callers that request them.

## Acceptance criteria

- AC1 — A placed steer joins the active native execution through the same assistant-row Run ID and `replyId`, without allocating another assistant record or delivery-owned execution. Multiple steers, compaction and approval wait preserve that owner; individual input outcomes do not settle it. The matching native terminal settles the Run and usage once, and a later queued execution gets a new Run (verification: adapter contract, runtime state and SQLite tests; Main runtime owner)
- AC2 — Inputs and parts render in `pos` order. A part admitted before a steer stays above it while streaming and after it commits, even when the steer commits first. Attaching a second window, reloading a window or reconnecting to the same Main process reproduces the live order (verification: unit and Electron; projection and renderer owners)
- AC3 — An admitted part keeps its ID on reconnect and snapshot replacement in the same Main process. A committed part keeps its ID on restart and on a replay with a known native source on Claude Code, Pi and Pi Durable. New writes add no offset/count composition and legacy rows stay readable (verification: harness contract and setupTestDatabase unit; runtime owners)
- AC4 — Every committed row change raises `rev`; a reader at cursor N receives exactly the rows changed after N, and deletion or branch switching returns a fresh snapshot (verification: setupTestDatabase unit; Main data owner)
- AC5 — Appending to an open text or reasoning part publishes one part-addressed append without other parts or the order. On mounted root and child views the addressed block displays the new text. Tool progress with unchanged layout updates the addressed tool card. ## Risks

- An abrupt Main exit can lose open parts that have yet to commit. Native recovery can supply new items without the original live IDs and positions.
- A part streaming above a steer pushes the steer down while it grows. This is the accepted T3 behavior; revisit it only with Electron evidence.
- Some adapters change native identifiers on commit. Require stable keys or proven aliases and exercise replay in each adapter.
- The budget can omit relevant history. A fresh context begins with the selected reference facts and its own execution state. The original thread remains the source for native recovery or checkpoint operations on the earlier branch.
- Existing user archives need populated upgrade tests before the storage cutover. Regenerate unpublished migration changes against the current parent and preserve the shipped chain.
- Several root contexts per session change recovery, fork and deletion paths that assume one binding.
