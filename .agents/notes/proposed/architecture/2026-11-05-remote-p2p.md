# Agent Note: Client-owned P2P transport for remote access

Status: proposed

English | [中文](2026-11-05-remote-p2p.zh.md)

## Problem

Paired Desktop and Mobile devices need a path across networks when a direct WebSocket endpoint is unreachable. WSS Relay supplies that path, but relaying a long session consumes intermediary bandwidth even when the endpoints could communicate directly. P2P should reduce that traffic without coupling remote access to account credentials or adding a P2P service to each Relay deployment.

The shared [remote-protocol](../../../../packages/remote-protocol/README.md) and [remote-transport](../../../../packages/remote-transport/README.md) packages are maintained in this repository. Business methods, device identities, pairing and grants already belong to the endpoints. This proposal keeps those owners and adds an optional transport.

Relay integration is tracked in [Desktop PR #23505](https://github.com/CherryHQ/cherry-studio/pull/23505) and [Mobile PR #1600](https://github.com/CherryHQ/cherry-studio-app/pull/1600), with the runtime in [relay-server](https://github.com/CherryHQ/relay-server). This Spec assumes those integration contracts; it does not include their code or claim that they have merged. It records the implementation target only: no P2P code, native dependency, package release or deployment is delivered here.

## Proposal

### Package and process ownership

Use WebRTC DataChannel for data only. Upstream libraries own ICE, DTLS, SCTP, retransmission and congestion control. The native P2P engines run on Desktop and Mobile, while the portable adapter lives in an independent `@cherrystudio/remote-transport/p2p` export. No separate npm package or P2P server is required.

| Component | Proposed location | Responsibility |
| --- | --- | --- |
| Shared P2P adapter | `remote-transport/p2p` in this repository | Control schemas, one negotiation attempt, chunking and a bounded MessageStream |
| Desktop native engine | Product Main adapter using `node-datachannel` | Endpoint PeerConnection and DataChannel |
| Mobile native engine | App adapter using `react-native-webrtc` | iOS/Android native connection and lifecycle integration |
| Capability declaration | `remote-protocol` connection hello | Optional endpoint version; existing business schemas stay unchanged |
| Connection owners | Existing product managers | App selects the attempt; Desktop validates authorization and confirms handoff |
| STUN | Client configuration | Existing or optionally self-hosted address discovery |
| Relay | Existing protocol, SDK and Bun/DO runtime | Rendezvous, opaque byte forwarding, limits and cleanup |

The P2P subpath takes narrow injected native and signaling interfaces. It must not import Electron, Node, Bun or React Native native modules, or depend on `relay-client`, `relay-protocol`, account APIs or a cloud vendor. The main `remote-transport` entry must not load P2P. The explicit export needs its own build, declaration and offline-consumer validation.

`remote-protocol` continues to describe business requests and reachable endpoints. Only an optional hello capability is added there. SDP, ICE and handoff-control schemas belong to `remote-transport/p2p`; product dispatchers explicitly register their isolated control namespace inside the encrypted RPC channel. They do not insert new data into existing business messages, Noise preambles or Relay rendezvous messages.

The first adapter carries signaling over the existing authenticated Relay/Noise channel. Relay cannot interpret it and needs no capability endpoint, selection state, protocol extension or additional DO attachment fields. The portable signaling interface can use another carrier later without making an unused second implementation now.

Required endpoint chunk/credit control stays inside the subpath; it does not duplicate reliable UDP or SCTP retransmission.

### Connection sequence and compatibility

The first release tries a reachable direct endpoint first. If it fails, establish an authenticated Relay channel and then attempt P2P before handing a connection to business callers. This deliberately pays for a Relay connection and a second Noise handshake to keep the server unchanged; it does not promise faster initial connection.

1. A direct connection that succeeds is delivered immediately. Otherwise use the existing v1 rendezvous, ready, RelayStream, Noise, hello and paired-device authentication without new server messages.
2. A new Desktop advertises optional `connectionP2PVersion: 1` in the existing loose hello response; the request stays unchanged. A new App starts P2P only when that version matches and its own support and setting permit it. An old Desktop omits it; an old App ignores it. Neither receives unsolicited unsupported controls.
3. The first release attempts P2P once per new connection of an already paired device, before business delivery. Initial pairing uses the existing direct/Relay path. A session already running RPC, subscriptions or uploads keeps its path; no background migration is attempted.
4. Desktop checks the authenticated device, current grants, feature setting and capacity before admitting negotiation. Each parent channel has at most one candidate. An unpredictable, single-use correlation value binds the parent secure channel, both verified identities, connection generation and deadline. It does not grant access.
5. App is the offerer and Desktop the answerer. Exchange SDP, trickle ICE and end-of-candidates over the old Noise channel. Endpoints contact their configured STUN services directly and create one reliable, ordered DataChannel with a fixed label/protocol. Do not enable partial reliability, extra channels or media tracks. Early candidates wait in a bounded queue for the remote description.
6. An open DataChannel is only a candidate. Adapt it to MessageStream, establish fresh Noise pinned to the same endpoint identities, repeat hello and device authorization, and validate the correlation value. Old Noise keys, access tokens or the correlation value alone cannot authorize the new business path.
7. Product owners confirm one handoff before delivering the new connection. Before commitment, a connectivity failure disposes the candidate and delivers the already authenticated Relay connection. After successful confirmation, release the old Relay data/signaling channel and retain the Desktop listener.

Existing QR reachability metadata, including the Relay integration's `RelayEndpoint { origin, targetId }`, is sufficient. No QR revision, persistent ICE credentials or new device registry is required. Disabling P2P, lacking native support or STUN configuration, and new/old client combinations preserve WSS access.

### Handoff, cancellation and recovery

`DesktopConnectionManager` owns selection, the attempt deadline, AppState and retries. `RemoteAccessService` owns the parent-bound Desktop candidate, identity, current grants, confirmation and cleanup. The shared subpath negotiates once and returns a candidate; it does not publish a business session or run a global reconnect loop.

- During preparation the parent Relay channel remains available but has not been handed to business callers. The candidate permits only handshake, authorization and handoff controls; successful authentication must not automatically open business RPC. If the old channel starts a business call, cancel the candidate and keep Relay.
- App requests commitment; Desktop serializes the generation/grants check and accepts at most one commitment. The old path stops accepting business at commitment, and the new path is delivered only after confirmation. Fix the request/confirmation, duplicates, deadlines and close ordering in protocol vectors before integration; local ready flags do not prove agreement.
- A pre-commit connectivity failure can retain Relay. An uncertain commitment or missing confirmation closes the related attempt and lets the owner reconnect. Neither side may independently guess a fallback that leaves two business paths active.
- After confirmed handoff, intentional release of the old channel must not abort the P2P candidate through a stale close callback. Relay socket accounting still follows its existing terminal-close rules.
- Identity mismatch, protocol violations or revoked grants terminate the related attempt rather than switching paths to bypass authorization. Disabling remote access, changing Relay origin or revoking pairing cancels associated negotiation and P2P connections. The LAN switch continues to affect direct ingress only.
- A real disconnection creates a new stream and Noise session, then uses existing business recovery without ciphertext migration or automatic command replay. Parent Relay loss before commitment cancels negotiation; normal DO hibernation keeps the socket usable. Established P2P survives listener loss, Relay restart and DO hibernation.

Keep the App's existing 15-second total attempt budget and at most 5 seconds for direct when Relay is available. Relay setup, both Noise/authentication steps and handoff all count. Initially cap the entire optional P2P attempt at 3 seconds, including ICE and the second authentication/confirmation, reserving at least 1 second for fallback/cleanup. Insufficient remaining time delivers the authenticated Relay channel immediately. These limits need real-network validation.

Expose a P2P opt-out and explain that direct peers learn connection addresses. Persist the setting and STUN configuration on the endpoints; keep SDP, ICE credentials, candidate addresses and correlation values transient.

### Binary data and resource bounds

Business semantics remain in `remote-protocol`; every data path remains protected by Noise. Start with at most 16 KiB per DataChannel message including endpoint framing, respecting any smaller negotiated maximum. Split existing 1 MiB records. Endpoint credit/chunk control must not reimplement SCTP reliability.

Bound bytes, item counts, receive credit, pending signals and simultaneous negotiations. Account separately for application queues, JS/native bridge traffic and native send buffers, including the peak while old and candidate connections coexist. Failed sends are not accepted sends; accepted sends must not be repeated. A peer ACK alone cannot release unrelated native-send reservations.

RN's bridge may Base64-encode binary sends and report bufferedAmount asynchronously. Network binary does not establish zero-copy delivery or synchronous accounting. Use verified native buffer/completion signals or minimal bounded receipt support; do not enable a platform whose native bounds cannot be demonstrated.

Initial signaling bounds are 32 KiB per SDP, 2 KiB per candidate, 64 candidates per side and 256 KiB total per attempt. Check the complete UTF-8 encoded control record against existing Noise/RPC record and rate limits, without widening Relay control limits. Reject malformed, over-limit, cross-device or stale-generation controls.

Relay measures opaque bytes and its own resources; endpoint instrumentation measures P2P bytes, success and latency. Do not log SDP, ICE passwords, complete candidate addresses, tickets or correlation values. Do not introduce a Relay database, usage ledger or P2P recovery snapshot.

### Service configuration and delivery

Configure STUN URLs at the clients using existing or self-hosted services. Product defaults and settings UI remain implementation decisions; no Relay capability API, account service or official hostname is required. Automatic public-network setup still needs signaling and usually STUN, as described in the [WebRTC guide](https://webrtc.org/getting-started/peer-connections).

A fully self-hosted installation may add coturn in `stun-only` mode with a public UDP endpoint, for example 3478/UDP. It may share a VM with Bun in a separate container or use another vendor. Clients access it directly; the existing HTTP/WSS Tunnel configuration does not carry it, and Workers/DO does not run it. A self-hosting guide is optional; do not add coturn to base Relay Compose or pre-create `deploy/stun/`. UDP/STUN failure retains WSS; TURN and its credential service are outside the first release.

Validate [node-datachannel](https://github.com/murat-dogan/node-datachannel), [react-native-webrtc](https://github.com/react-native-webrtc/react-native-webrtc) and [DataChannel interoperability](https://www.rfc-editor.org/rfc/rfc8831.html) against the actual Electron and mobile native builds, then pin working versions. Refresh product versions before implementation. Expo requires a new native build, not a JS-only update or Expo Go.

| Phase | Deliverable | Verification owner |
| --- | --- | --- |
| P0 | Native adapters and real MessageStream/Noise prototype; test signaling is allowed | Desktop and Mobile maintainers: native builds, bidirectional data, 1 MiB, slow reads and cleanup |
| P1 | Shared P2P subpath, optional hello capability and control vectors | Shared-package maintainers: schemas, bindings, budgets, exports and old/new compatibility |
| P2 | Product owners, candidate business gate, handoff, STUN setting and opt-out | Desktop and Mobile maintainers: fallback, uncertain commitment, revocation and AppState |
| P3 | Cross-network compatibility using unchanged Docker/Tunnel/DO; optional self-hosting guide | Product and Relay maintainers: NAT, blocked UDP, hibernation, restarts and measured costs |

Production wiring must use the authenticated Relay carrier after the isolated P0 prototype. Failed native validation keeps WSS and records the concrete blocker; it does not trigger construction of another complete P2P backend.

## Alternatives considered

- Extend Relay with SDP/ICE types, server-owned selection and DO snapshots: avoids part of the client bootstrap but couples deployment versions and creates server state for an endpoint feature. Keep the server opaque.
- Put P2P in `relay-client/p2p`: shares code but gives a Relay SDK ownership of transport that can use other carriers. Keep it in the already shared remote transport package.
- Deploy a separate signaling service or require self-hosted STUN/TURN: adds operational dependencies. Reuse the encrypted channel and configurable STUN; reconsider TURN only with evidence that the existing WSS fallback is insufficient.
- Migrate active Noise/RPC sessions between paths: requires in-flight ordering, replay and subscription ownership beyond this first release. Select once before business delivery and reconnect on real failure.
- Integrate Tailcat or custom UDP in parallel: creates a second native/network stack to validate. Use the selected DataChannel libraries first; retain other transports as future alternatives.

## Acceptance criteria

These are future implementation outcomes. This documentation-only Spec does not claim that any P2P acceptance test has passed.

- AC1 — Both products consume the portable P2P subpath through their native adapters while Relay runtime, protocol, SDK and deployment inputs remain unchanged; main imports do not load native P2P. (verification: package tests and packaged artifact; owner: shared-package maintainers)
- AC2 — Old/new clients, disabled or unavailable P2P, first pairing and direct success retain existing access; only supported, already-paired new connections negotiate P2P before business delivery. (verification: unit and cross-product integration; owner: Desktop/Mobile maintainers)
- AC3 — Parent identity/generation binding, fresh pinned Noise and current grants protect the candidate; unknown identities, replayed correlation values, stale controls and revocation never gain a fallback bypass. (verification: security integration; owner: Desktop/Mobile maintainers)
- AC4 — Preparation, single commitment, missing confirmation, cancellation and close races produce at most one business path; pre-commit connectivity failure retains Relay, uncertain commitment reconnects, and the total deadline never stacks extra timeouts. (verification: unit and integration fault cases; owner: Desktop/Mobile maintainers)
- AC5 — Bidirectional 1 MiB records, slow readers, asynchronous native events and hostile signaling remain within measured queue/native budgets; repeated cancellation and reconnection cause no sustained resource growth. (verification: native packaged artifacts and resource measurements; owner: Desktop/Mobile maintainers)
- AC6 — Real cross-network Desktop/iOS/Android runs validate STUN/UDP failure, background/network changes and unchanged Docker/Tunnel/DO; confirmed P2P releases the Relay data connection, survives Relay outages and reports startup, throughput, CPU/RSS and power without claiming an unmeasured improvement. (verification: Electron, mobile devices and runtime integration; owner: product/Relay maintainers)

## Risks

- Native library/build compatibility and bridge buffering remain unverified. Lock versions only after P0; no current package, device or performance acceptance is implied.
- Relay bootstrap and a second Noise handshake may make short sessions slower. Measure first-connect time and long-session egress savings separately under matched network/load conditions.
- Handoff confirmation must be specified before coding. Uncertain results intentionally reconnect rather than risking duplicate commands or inconsistent grants.
- STUN does not guarantee NAT traversal, and P2P exposes peer addresses. Keep the opt-out, bounded attempts and WSS fallback; never make optional services a prerequisite for basic self-hosting.
