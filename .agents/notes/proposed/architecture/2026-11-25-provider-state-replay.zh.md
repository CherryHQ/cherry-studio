# Agent Note: 模型路由之间的提供商状态重放

Status: proposed

[English](2026-11-25-provider-state-replay.md) | 中文

## 问题

Chat 和智能体在模型续聊或继续工具调用时会重放之前的响应。历史里可能包含带签名的正文、思考、多媒体和工具调用，也可能包含加密推理、续跑必需的明文思考或服务端续接引用。这些状态是否有效取决于生成它的路由和目标协议的规则。Chat 目前记录的是选中的模型，实际提供备用响应的模型可能不同。Pi 在 Gateway 收到请求前检查原生提供商、API 和模型。修改 Base URL 可能不会改变这三个值，Pi Durable 重新注册则可能在路由相同的情况下改变这些值。

[Gemini Chat 修复](../../implemented/bug-fix/2026-11-25-gemini-chat-tool-signature-replay.md) 处理原生 Gemini Chat 请求中来源不同的正文和客户端工具签名。[Anthropic 前缀修复](../../implemented/bug-fix/2026-11-24-anthropic-thinking-prefix.md) 处理一部分前缀变化。还有一些状态在这两条重放规则执行前就已丢失。现有 OpenAI 兼容适配器可能丢掉独立的密文帧。OpenRouter 同时返回密文和普通正文时，密文可能只留在步骤元数据中，下一次请求不会读取。HTTP 请求成功只能证明服务接受了请求。

## 方案

### 生成状态时记录实际路由

根据实际调用标记每个可重放的块或条目的来源，记录提供商连接、实际出站的端点、协议、运行时适配器，以及发给上游的模型 ID。适配器能确定实际项目、部署或账户范围，且协议将状态绑定到该范围时，也记录对应信息。用路由配置生成稳定标识，排除凭据和临时运行时别名。切换备用路由或重试时，记录实际生成结果的那次调用。同一条助手回复可能包含多次调用产出的内容，因此来源跟随可重放的块或条目。

状态和可选的来源信息随现有 Chat 内容块和 Pi 原生历史保存。保存、重新打开、分支和压缩时，保留未删除内容与来源的对应关系。摘要只携带摘要模型实际产出的状态。缺少路由来源的旧记录沿用现有适配器行为，有已保存的模型标识时仍可遵循 Gemini 修复中范围较窄的比较逻辑。无法确定旧端点时，保留来源未知。

### 根据目标端点的重放契约判定

每个实际使用的会话适配器都声明它能够接收的状态格式、需要一起重放的内容及顺序、所接受的来源范围，以及其他条件。例如原始上下文前缀、本轮工具续跑，或启用响应存储的会话中的服务端引用。只接收普通历史的适配器也声明这一点。路由可以沿用[现有推理契约](../../../../packages/provider-registry/src/schemas/provider-models.ts)按提供商、模型和端点覆盖适配器默认值。每次实际调用解析一次，并将结果传给请求序列化。

| 条件 | 请求行为 |
| --- | --- |
| 来源和目标路由相同，且满足协议条件 | 原样重放状态，保留原来的重放单元和顺序，包括正文为空但带状态的块。 |
| 已结束的历史超出目标支持的来源范围，或已知不满足协议条件 | 从出站请求中省略受影响的状态。保留普通内容和兼容的客户端工具调用与结果。由目标适配器选择它支持的提供商原生工具历史表示。 |
| 正在等待工具续跑，且需要绑定在原路由上的状态 | 在原路由继续执行，切换在下一轮生效。如果原路由不可用，返回续跑失败并保留已经记录的工具结果。 |
| 没有状态，或端点不接收会话历史 | 按常规方式处理消息和请求。 |

第一版采用同路由规则。后续增加跨路由规则时，必须明确来源范围、目标范围和状态格式，有文档支持，并用真实端点验证出站请求带着原始状态，以及服务实际消费了它。HTTP 成功、相同的模型名称和相同的字段名都不足以证明兼容。受影响的原始状态继续保存。显式省略必须传到最终序列化器，避免它用占位值补回字段。

适配器支持协议自身的绑定检查时，沿用该检查。对于本地历史改写，沿用已有的改写边界，按协议的依赖规则省略受影响的历史状态。例如 Anthropic 前缀变化时，即使未切换路由，也可能使之后的已签名块失效。协议要求思考块连续时，重放保持连续。服务端续接引用只在拥有它的路由和存储模式下使用。 [Anthropic 前缀规则](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking/prefix-checks) · [Vertex 思考签名](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/thinking/thought-signatures#constraints-and-limits)

### Chat 和 Agent 运行时使用同一判定

在主进程 AI 域内加入共用的重放判定。通过 AI SDK 的 `RequestFeature` 安装中间件。中间件的 `wrapStream` 和 `wrapGenerate` 把解码后的状态与实际调用关联，`transformParams` 在历史编辑和压缩之后、提供商序列化之前检查请求。适配器负责解码、状态在块中的位置和最终协议字段。SDK 未暴露提供商返回的状态时，在相应响应解码器或 Gateway 转换边界修复。响应采集同时覆盖仅含元数据的流式事件和非流式响应。 [AI SDK 请求组合](../../../../docs/dev/references/ai/params-pipeline.md)

Pi 和 Pi Durable 保留自己的原生历史和工具循环。在 Pi 转换请求前，由绑定入口调用同一判定，并使用可信对象传输在该次调用采用的实际路由。通过受信任的进程内调用传递来源及最终适配器需要的显式省略标记。运行时注册名继续用于查找，与重放范围分开。 [Pi 绑定](../../../../src/main/ai/runtime/pi/gatewayModelBinding.ts) · [智能体原生对象传输](../../implemented/architecture/2026-11-18-agent-object-transport.md)

Claude Code 保留自己的原生历史和工具循环。对于经过认证的 Agent 会话，Gateway 将提供商状态和来源保存在现有会话 checkpoint 中，与 Claude Code 传回的助手块匹配，并交给同一套 AI SDK 重放判定。工具循环依赖原路由时，Gateway 先选定路由，再转换请求。Anthropic 块自带的签名继续作为协议字段传递。无法匹配或有歧义的记录不向请求补充状态。订阅直连会话和外部 Gateway 客户端沿用原生历史规则。

### 实现顺序

1. 为现有缺口添加请求捕获夹具，修复在规范化前或序列化时丢掉状态的适配器。先覆盖 Gemini 兼容工具签名、无工具时的 OpenRouter 密文、Chat 顶层密文，以及 xAI Responses 的命名空间。用锁定版本的 SDK 和生产 Gateway 转换器验证从响应到下一次请求的往返。
2. 接入实际路由来源和 AI SDK 共用判定。现有应用自管重放规则对应的目标适配器通过等价验证后再迁移。验证已知路由切换、A → B → A、备用路由归属、旧历史和本地前缀改写。
3. 通过现有对象传输绑定接入 Pi 和 Pi Durable。验证原生历史重新打开、待续跑工具和同路由重新注册。完成 Spec 前，用 Electron 测试有代表性的真实提供商 Chat 和 Pi Durable 路径。
4. 将 Gateway 路径上的 Claude Code 接入，把返回的 Anthropic 块与同一会话中的状态关联。验证 Anthropic 请求与响应往返，以及后续使用原路由重放或切换到另一家提供商。

## 备选方案

- 单独比较模型 ID 或签名字段。一个模型可能走不同端点、项目或适配器，同一格式也可能有不同的重放规则。
- 切换路由后在 Gateway 中间件里去掉所有推理。这样会丢失本轮必需的状态，也无法处理 Pi 调用 Gateway 前已经去掉的来源和状态。
- 先发签名探测跨路由兼容性，收到 HTTP 400 后再重试。提供商可能静默忽略状态，工具已执行后的重试也无法建立安全的续跑条件。

## 验收标准

- AC1 — Chat 的备用路由调用成功后，状态归属于实际提供响应的路由。Chat 和 Pi Durable 在连接和模型 ID 相同的情况下能识别配置的端点、协议或 Base URL 变化，Pi 重新打开同路由时的来源标识跨运行时注册保持一致。 (verification: unit, owner: 请求路由与 Pi 运行时维护者)
- AC2 — 兼容的同路由序列在保存和重新打开后原样重放签名或密文。最终出站请求保留原始字节、块顺序和工具对应关系，包括空正文或仅含元数据的响应所携带的状态。 (verification: unit, owner: 适配器与历史维护者)
- AC3 — 已结束的跨路由历史在兼容性未知时，出站请求发送目标支持的正文和配对客户端工具历史，省略跨路由状态且没有替代签名。原始块保存在存储中，切回兼容路由后可再次重放。 (verification: unit, owner: AI SDK 与 Pi 运行时维护者)
- AC4 — 依赖状态的工具续跑期间发生路由切换或备用路由选择时，只要原路由可用就继续使用。原路由不可用时返回续跑失败，工具不会再次执行，也不会发出缺少必要状态的续跑请求。 (verification: unit, owner: Chat 与 Pi 运行时维护者)
- AC5 — 对绑定前缀的路由，确认前缀变化后，最终请求省略受影响的历史状态。相关前缀未变时，保留的兼容状态仍可重放。 (verification: unit, owner: 上下文与适配器维护者)
- AC6 — 捕获覆盖 Generate Content、Messages、Chat Completions 的不同实现、Responses 的不同实现和 Ollama Chat，包括必需的明文、加密状态及服务端引用。旧历史、调用方自管历史和非会话请求保留现有历史归属和有效的请求行为。 (verification: unit, owner: 适配器与 Gateway 维护者)
- AC7 — 一次真实 Chat 运行和一次真实 Pi Durable 运行均完成同路由工具续跑和结束轮次之间的路由切换。检查最终上游请求，验证应当保留的状态、应当省略的跨路由状态以及工具调用和结果的配对情况。 (verification: Electron, owner: 实现集成负责人)
- AC8 — 通过 Gateway 调用的 Claude Code 重开会话后能恢复匹配的状态，并对下一条上游请求应用同一套路由规则。提供商状态不会跨 Agent 会话或关联到无关的助手块。 (verification: unit, owner: Gateway 与 Claude Code 运行时维护者)

## 风险

- 网关可能隐藏实际上游部署，或在稳定别名背后切换部署。同路由重放依赖提供商暴露的身份以及其文档契约。无法辨明来源的别名不能作为跨路由规则的依据。
- 省略跨路由状态可能影响推理的连贯性。保留存储中的原始状态，并在工具链需要原始状态时继续使用生成它的路由。
- 协议转换器可能把状态留在步骤上，而没有附到实际参与重放的块。夹具需要经过真实历史转换和重新加载后检查下一次实际出站请求。
