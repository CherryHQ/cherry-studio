# Agent Note: 统一 Pi、Pi Durable 与 Claude Code 的审批展示

Status: proposed

[English](2026-11-10-unified-agent-approval-presentation.md) | 中文

## Problem

子任务工具可能正在等待审批，用户却只看到任务运行中。Pi 与 Pi Durable 共用 `createPiInteractionPorts`：请求携带工具名和输入，但主进程的流内分支将其缩减为审批 ID 和工具调用 ID。主回复未必包含子任务的工具输入，导致 `RootMessageProjection` 无法生成卡片。Claude Code 当前在适配层为子任务交互选择独立消息。因此，正确展示依赖各 runtime 自行选择及事件到达顺序。

11 月 10 日的调查使用已安装 2.2.0 的投影实现和受影响会话的持久化消息，复现了审批卡缺失路径。原生存储显示子任务写文件停在执行之前，父任务正在等待。没有读取生产进程的内存审批队列，因此证据确认了展示缺陷及相符的现场，尚未完整证明现场的挂起调用栈。本方案不包含会话内容、标识符和本地诊断产物。

这是[运行时边界所有权](../simplification/2026-11-05-agent-runtime-boundary-ownership.md)职责划分内新增的共享展示契约。它部分替代[废弃审批卡清理](../../implemented/bug-fix/2026-11-06-retire-abandoned-approval-cards.md)中按展示类型区分清理的假设；该文档的取消、用户拒绝归因和未送达回答处理继续适用。本 proposed 文档不改变已发布行为。

## Proposal

### 范围与职责

统一已经需要用户回答的请求如何展示、响应和撤销，覆盖使用现有审批通道的权限提示、用户问题和计划确认。保留各 runtime 的权限规则、自动放行、显式拒绝、无交互限制和原生恢复语义。不新增自动授权、工具能力、审批数据库、通用运行时框架或第二套回调注册表。

| 所有者 | 职责 |
| --- | --- |
| Runtime 适配层 | 判断原生执行是否需要回答；提供完整工具输入、可信来源和取消信号；将中立决定转换为原生结果。 |
| `ToolApprovalRegistry` | 持有活跃回调并保证最多结算一次；保留主进程为该次注册选择的响应锚点。 |
| `AgentSessionRuntimeService` | 验证连接归属，选择并绑定展示位置，发布卡片，验证回答并撤销绑定卡片。 |
| 现有消息服务与投影 | 持久化或投影选定的卡片，在后续工具快照中保留其身份。 |
| 渲染端 | 展示共享交互，提交审批身份及绑定锚点；不根据当前面板推断执行归属。 |

### 完整请求与明确来源

为 `AgentRuntimeToolApprovalRequest` 增加区分根任务与子任务的来源类型。根任务来源标识原生上下文，以及已知的发起回复；子任务来源携带当前连接 backend 内的原生子任务身份，以及已经确认的产品子会话。关联范围限定在发起连接及上下文内，不假定 `toolCallId` 全局唯一。产品投影尚未就绪的子任务仍然是子任务，不能根据标题或当前打开的面板猜测会话。

保留 `approvalId`、`toolCallId`、`toolName`、完整 `input` 和工具展示元数据。三个适配层迁移完毕后移除适配层选择的 `presentation`。分别通过 Pi 的 `CallRef.thread`、Durable 的 backend/conversation 归属及 Claude 已确认的 SDK agent 身份解析来源。如果 Claude 尚不能将原生子任务映射到产品会话，保留原生来源并展示通用子任务标签；缺少跳转链接不能阻塞审批。

适配层通过现有注册表先注册原生回调，再发出完整请求。主进程将展示锚点绑定到同一次活跃注册。未展示是明确的暂态，不默认视为流内锚点。来自旧连接、已经取消的注册或没有用户响应渠道的请求，必须结算，不能遗留等待回调。日志只包含关联 ID 和失败原因，不记录工具输入或问题答案。

### 一份审批，多个操作入口

子任务拥有执行，主进程统一管理审批，父会话提供操作入口，通知系统负责提醒。父会话展示与通知均不启动新的模型回合。

每次注册保留一个固定的消息记录锚点。根请求可以使用活跃回复；子请求使用现有消息存储，记录完整参数、原生来源及注册身份。存储锚点与展示位置分离。共享缓存中的派生投影通过可信子上下文和启动工具调用关联任务，不保存回调，也不能授权执行。

待审批请求替换父会话 composer，并保留原草稿；子面板在工具过程下方的 composer 区域提供同一审批。多个待处理请求可在 composer 中切换。任务区域只保留等待数量和定位入口，折叠时也显示数量，不放审批表单。独立审批存储记录不渲染为额外助手回复。无法关联产品任务时，父 composer 仍展示带来源的请求。通知定位会选中对应审批，并在可关联时打开子任务。稍后关联任务只改变投影，不移动锚点。原生任务状态与待审批状态分别保存。

### 通知跟随审批生命周期

审批持久化并通过活跃注册校验后，发布以注册身份去重的通知，携带会话、任务及具体审批位置。通知中心保存待处理及终态，已读独立于已处理。批准、拒绝、取消和失效同步更新共享投影与通知；关闭应用内提醒，尽力撤回系统通知。点击通知重新读取当前记录并定位会话或任务，不能授权执行。通知渠道失败不能破坏审批操作。

启动时，没有活跃注册的持久化待审批通知变为失效。历史卡片不能恢复回调。Durable 恢复请求即使复用原生审批 ID，也拥有新的注册和通知身份。

### 回答、取消与竞态

每次回答都验证活跃注册及绑定的消息、会话锚点，流内审批同样适用。先将接受的决定应用到该锚点，再释放原生回调。第一个被接受的回答生效；重复点击、错误锚点、旧连接及对已撤销注册的回答不能授权执行。批准后的输入修改交给原回调，各展示视图最终一致地呈现已接受的输入和决定。持久化失败时报告响应失败且不执行工具；回调仍活跃时保留待答卡片供用户明确重试。

取消继续走现有 `onAborted` 路径，但根据绑定锚点清理，不再依赖适配层选择的流内或独立消息形式。发布前取消不能产生可操作卡片。如果取消与持久化并发，写入完成后再次核对并撤销已经创建的行。父回合结束本身不取消独立的子任务请求。原生任务停止、会话关闭和连接替换保留既有取消归属，并撤销受影响的锚点。仅关闭子面板只解除观察。

对于旧的未注册请求，保留废弃卡片文档规定的首次未送达回答转交：问题答案可以变成用户文本，但绝不能隐式批准工具或转交给恢复后的回调。重复转交仍被拒绝。带注册身份的请求（包括子任务问题）在送达失败时绝不启动父模型回合。重开时，单凭持久化卡片不能重建回调。Pi Durable 可以通过原生恢复重新发起审批；Pi 与 Claude Code 遵循各自现有续接行为。所有情况下旧锚点都不能继续操作。

远程交互可携带注册身份，客户端回答时必须原样返回；带注册的请求拒绝缺失或过期身份。十进制版本号保持既有语义。旧客户端仍可读取新请求，但需要升级或通过桌面端回答。

### 实施与验证顺序

1. 在一个类型完整的改动中修改公共请求、来源和绑定锚点契约，覆盖三个适配层及真实消费者。一起替换适配层的展示选择并更新回答、取消处理，不保留长期兼容分支。
2. 增加共享投影和真实数据库服务回归，以及各 runtime 的适配覆盖。验证提前到达的审批、子任务来源映射、重复投递、输入修改、展示失败、持久化期间取消和恢复后旧锚点拒绝。
3. 在隔离 Electron 配置中分别验证 Pi、Pi Durable、Claude Code 的用户流程，覆盖双窗口及关闭子面板。受控提供方证据与真实提供方证据分开记录，不用生产会话作为执行工具的测试夹具。

实现负责人为每项标准提供证据。单元验证由共享审批、会话模块及各适配层分别负责；持久化消息测试使用 `setupTestDatabase()` 和生产迁移。只运行明确指定的受影响测试文件及变更文件检查。本方案的编写及文档检查不算实现或运行时验收。

## Alternatives considered

- 让 Pi 和 Durable 像 Claude 一样自行选择独立消息：局部改动较小，但展示策略和取消假设仍分散在适配层。
- 所有审批都使用独立消息：可靠，但会不必要地将普通根任务工具与已有卡片拆开。
- 每次审批前补发工具输入事件：修复一种顺序问题，却保留了双事件耦合，也未建立子任务来源及响应归属。
- 只在子面板展示可操作审批：面板关闭时会隐藏阻塞点，让审批可见性依赖导航。
- 工具消息到达后将卡片迁移过去：使响应锚点失效，并引入跨窗口重复点击竞态。
- 新建持久化审批队列或统一改变所有 runtime 权限策略：扩大范围，重复原生执行与恢复职责，却没有修复展示边界。

## Acceptance criteria

- AC1 — 根任务审批先于工具消息到达时，完整输入只展示一次，后续工具快照到达后仍正确关联。 (verification: unit; owner: shared projection/session)
- AC2 — 三种 runtime 的子任务交互，在父回复进行中及结束后，均可在关闭子面板的情况下从根会话回答，并保留已确认的来源身份。 (verification: unit + Electron; owner: adapters and session UI)
- AC3 — 批准、拒绝、问题回答及批准后的输入修改准确送达原生回调且仅一次，两个 composer 均收起已处理请求，通知反映已接受的决定。 (verification: unit + Electron; owner: registry and adapters)
- AC4 — 并发窗口、重复事件、错误锚点及迟到回答不能使工具重复执行，也不能授权其他或恢复后的调用。 (verification: unit + Electron; owner: registry/session)
- AC5 — 卡片持久化之前、期间及之后取消，均不遗留可操作孤立卡片或等待回调；只关闭子面板不取消执行。 (verification: unit + Electron; owner: session lifecycle)
- AC6 — 响应渠道缺失、旧连接及展示失败均明确结算而不自动授权；回答持久化失败时不执行工具。 (verification: unit; owner: session/registry)
- AC7 — 重开遵循各 runtime 原生恢复策略；旧卡片不能回答重新发起的请求，现有未送达回答转交最多发生一次。 (verification: unit + Electron; owner: adapters and session UI)
- AC8 — 保持各 runtime 既有权限策略和无交互限制，三个适配层统一使用主进程展示路径，不新增审批存储。 (verification: unit + source review; owner: adapters)
- AC9 — 父、子 composer 共享固定审批，不产生额外助手气泡；处理后恢复父会话草稿，延迟关联保留锚点，折叠任务列表仍显示待确认数量。 (verification: unit + Electron; owner: session UI)
- AC10 — 通知能定位具体审批，区分已读与已处理，终态撤销提醒，重启使旧通知失效；通知失败不影响审批。 (verification: unit + Electron; owner: notification/session)

## Risks

原生子任务身份可能先于产品子会话创建。应保留原生来源并允许没有链接的来源标签，不能阻塞或猜测。工具调用 ID 可能跨上下文重复，Durable 审批 ID 也可能在恢复后复用，因此必须限定作用域并固定锚点。

回调注册表与持久化消息无法共同原子提交。展示过程中保持取消信号连接，将锚点绑定到同一次活跃注册，并在异步写入完成时核对状态。不承诺跨进程崩溃的严格一次执行；执行安全仍由原生重放规则负责。

展示所有权迁移同时影响响应、销毁和渲染。只迁移请求事件会使现有 `presentation` 分支不一致。已有存储消息必须继续可读，单独的投影复现不足以证明三个 runtime 均能在 Electron 中正常工作。
