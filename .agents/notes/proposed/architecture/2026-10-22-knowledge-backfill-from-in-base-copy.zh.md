# Agent Note: 从库内副本回填嵌入，每个叶子条目一个索引任务

Status: proposed

[English](2026-10-22-knowledge-backfill-from-in-base-copy.md) | 中文

## 问题

`KnowledgeIngestionService.enableEmbeddingModel` 给只用 BM25 的库设置嵌入模型，然后通过 `knowledge.reindex-subtree` 对每个根条目重建索引，以此回填向量。这种回填有两个问题。

- **没有向量的条目仍显示为 `completed`。** 写入模型时，所有条目都还是 `completed`，条目要等自己的重建索引任务进入锁段才会离开 `completed`。重建索引任务声明了 `recovery: 'abandon'`，所以退出应用后，下次启动会直接取消还没走到那一步的任务。启动扫描（`failInterruptedItems`）只处理进行中的条目，于是这些条目一直是 `completed`，却没有向量：向量搜索会悄悄漏掉它们，也没有任何提示让用户修复（#22365）。
  - 在 `main` 上，这个窗口持续到唯一的回填任务拿到锁为止；任务还在重新抓取 URL 根条目时，窗口会更长。
  - [异步来源复制 Spec](2026-10-21-knowledge-async-source-copy.md) 为每个根条目各入队一个任务，把窗口扩大到回填任务仍在排队的整段时间。
- **依赖原始来源。** `reindex-subtree` 会从原始来源重新获取每个根条目：重新复制文件、重新扫描文件夹、重新抓取 URL。
  - 因此准入检查（`assertSubtreesCanReindex`）只要发现有一个原始来源被移走或删除，就拒绝为整个库启用模型。
  - 回填还会重新复制、重新抓取库里早已有的内容（#22092）。

回填只需要为搜索能返回的条目生成向量，也就是 `completed` 的条目。这些条目的内容都已经在库里：`raw/` 副本、已固定的处理产物，或者 URL、笔记的快照。

## 提案

回填不再经过重建索引，改为复用常规的逐条目索引流程。

- **先改行。** 在库级写锁内，用一个写事务完成三件事：
  - 写入模型，使用 `KnowledgeBaseService.update` 的事务版本；
  - 把库里每个 `completed` 的叶子条目（文件、URL、笔记）改为 `processing`；
  - 重新汇总这些叶子条目所在的容器，目录通过现有的容器汇总规则变为 `processing`。

  模型和状态要么一起提交，要么都不提交。从这一刻起，每个回填目标在它自己的索引完成之前，都不会显示为 `completed`。
- **`failed` 的叶子条目保持原样。** 它们保留原来的状态和错误信息，不会被调度任务。之后的重建索引会用新模型为它们建立索引。
- **每个叶子条目一个索引任务。** 释放锁之后，回填对每个已激活的叶子条目调用 `scheduleItem`，与 `addItems` 调度新条目的方式相同。某个叶子条目调度失败时，把它标为 `failed` 并附上原因，其余叶子条目照常调度。删除只会取消它所移除的条目的任务。
- **只读库内来源。** `knowledge.index-documents` 读取 `raw/` 里的文件或其已固定的处理产物，以及已抓取的 URL 或笔记快照，不抓取任何内容，也不复制任何文件。每个 `completed` 的叶子条目都有这样的来源：URL 和笔记要先存下快照才会完成，文件要等副本复制到位才会完成。
  - `scheduleItem` 调用时不带 `forceFileReprocess`，所以已有处理产物的文件不会重新处理。
  - `rebuildMaterial` 在一个事务里替换每个条目原有的 BM25 索引内容，因此不需要事先删除任何数据。
- **准入。** 该库必须允许运行时操作，每棵目标子树都必须是 `completed` 或 `failed`；`KnowledgeBaseService.update` 仍会拒绝切换已配置的模型。不再检查来源是否存在，所以原始来源被移走或删除不再阻止回填。这些状态在库级写锁内读取，所以启用模型等锁期间新增并开始处理的条目也会被看到；否则它会在没有向量的情况下完成索引，因为回填只处理 `completed` 的叶子条目。
  - 该库不能有排队中或运行中的 `knowledge.reindex-subtree` 任务。重建索引在任务重置条目之前，条目一直保持 `completed`，所以从状态上看不出来。如果回填与它同时进行，可能会用旧副本覆盖刷新后的内容，重建索引随后又会因为条目已是 `completed` 而跳过它。这项检查在库级写锁内、写事务之前进行。
  - 反过来，重建索引的准入也在同一把锁内重新读取子树状态并入队。因此，如果重建索引还在检查来源时回填激活了这些条目，这次重建索引会被拒绝。
- **恢复方式不变。** `knowledge.index-documents` 保持 `recovery: 'abandon'`。退出应用后，没做完的叶子条目仍处于进行中状态，启动扫描会把它们标为 `failed`（`indexing_interrupted`）；已经完成的叶子条目保持 `completed`。
- **用户发起的重建索引仍从原始来源重新获取。** 唯一的变化是上面说的：它的状态检查移到库级写锁内进行。在重建索引里区分「从库内副本重建」和「从来源刷新」，留给 #22092。

本提案部分取代[异步来源复制 Spec](2026-10-21-knowledge-async-source-copy.md)：即它 AC9 中关于回填的部分，以及其中关于重启缺口的已知限制。两份笔记都保持有效，并相互链接。

## 考虑过的替代方案

- **入队时就激活根条目，仍然每个根条目一个 `reindex-subtree` 任务。** 这能关掉重启窗口，但回填仍要从原始来源重新获取。原始来源被移走时依然会阻止回填；任务开始前原始来源就已消失的根条目，还需要额外的失败处理路径。
- **所有根条目共用一个回填任务，与模型在同一个事务里激活，并在每次打开知识库时做完整性扫描（#22402）。** 回填期间的任何删除都会取消这个共用任务，并让其他所有根条目失败。扫描会把条目标为 `failed`，即使它提示的重建索引修不了，比如原始来源已被移走。它还会在每次打开知识库时，在主进程里同步扫描一遍。
- **像 `main` 一样，把 `failed` 的叶子条目也纳入回填。** 搜索从不返回 `failed` 的条目，给它们补向量不会让搜索多找到任何东西。回填反而会变成没人要求的重试：首次抓取就失败的 URL 没有快照，会被重新抓取；处理失败的文件会再经过一次处理器。
- **重建索引入队时就把条目标为进行中。** 这样回填的准入检查只看条目状态就能发现待处理的刷新。但等待中的刷新会让条目从搜索里消失，退出应用后启动扫描还会把旧索引仍然有效的条目标为失败。专门的待处理状态可以避免这两点，但需要迁移和新的界面，应该放进 #22092。
- **重启后续跑从未开始的回填任务。** JobManager 需要按任务状态区分恢复方式；而且退出应用后，会在用户没有再次要求的情况下继续调用嵌入接口。
- **在知识库级别记录回填进度。** 用知识库级别的「向量待生成」状态，可以让条目在回填期间保持 `completed`、仍能被 BM25 搜到。这需要迁移和新的界面，暂缓。

## 验收标准

- AC1 — 在只用 BM25 的库上启用嵌入模型时，写入模型与把每个未在删除的叶子条目移出 `completed` 一起提交；这次写入失败时，模型和所有条目状态都不变。 (verification: unit)
- AC2 — 每个叶子条目由自己的任务从库内副本建立索引：不重新复制原始来源、不重新扫描文件夹、不抓取 URL，已有处理产物的文件不会重新处理。 (verification: unit)
- AC3 — 部分条目的原始文件或文件夹已被移走或删除时，启用嵌入模型仍然成功，并且每个叶子条目都能建立索引。 (verification: unit)
- AC4 — 回填期间退出应用后，下次启动时每个尚未完成索引的叶子条目都是 `failed`（`indexing_interrupted`），已完成的叶子条目保持 `completed`，没有任何叶子条目是 `completed` 却没有向量。 (verification: unit)
- AC5 — 回填期间删除某个条目，只会停止该条目的工作；其他叶子条目仍会完成。 (verification: unit)
- AC6 — 某个叶子条目的索引任务无法调度时，它被标为 `failed` 并附上原因，其他叶子条目仍会被调度。 (verification: unit)
- AC7 — 用户发起的重建索引仍从原始来源重新获取，原始来源缺失时仍会被拒绝。 (verification: unit)
- AC8 — 启用模型时已是 `failed` 的叶子条目保留原来的状态和错误信息，不会被调度索引任务，因此首次抓取就失败的 URL 不会被抓取。 (verification: unit)
- AC9 — 该库有排队中或运行中的重建索引时，启用嵌入模型会被拒绝，模型和条目状态都不变；那次重建索引结束后，再启用就能成功。 (verification: unit)
- AC10 — 重建索引检查来源期间，如果回填激活了它的条目，这次重建索引会被拒绝，不排任何任务。 (verification: unit)
- AC11 — 启用模型等待库级写锁期间，如果新增操作开始处理一个条目，启用会被拒绝，模型和条目状态都不变。 (verification: unit)

## 风险

- **回填期间知识库搜不到。** 每个叶子条目在它自己的索引完成之前都处于进行中状态，而进行中的条目不会出现在搜索结果里，BM25 也一样。对文件库来说，`main` 在回填任务开始之后也是这样。知识库级别的待生成状态可以避免这一点（见替代方案）。
- **每个叶子条目一个任务行。** 大库在队列里新增的任务行，与导入同样数量的条目相当，之后该库上的其他工作要排在它们后面。
- **一次性的文件处理。** 在知识库配置文件处理器之前就已索引的文件没有处理产物，回填会让它经过一次处理器，可能是付费调用。
- **失败的条目需要手动重建索引。** 启用模型前就已是 `failed` 的叶子条目，以及回填失败或因退出应用而中断的叶子条目，在用户重建索引之前都没有向量。这时模型已经设好，回填不能再触发一次。在 #22092 落地之前，这次重建索引仍然需要原始来源。
