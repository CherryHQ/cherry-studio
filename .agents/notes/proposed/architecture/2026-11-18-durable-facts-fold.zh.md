# Agent Note: 以折叠方式派生 Durable behavior 事实与观测

Status: proposed

[English](2026-11-18-durable-facts-fold.md) | 中文

## 问题

Pi Durable 的各个使用方都从已提交日志重新计算出当前状态，Cherry 又在好几层重复这样做。#24500 的负载（一个会话约 5,500 条历史、12 个以上子智能体，并带内联图片）让每次重算都既昂贵又频繁：

- **behavior 事实。** [`agent-behavior`](2026-10-18-agent-behavior-package.md) 把事实定义为完整谱系的历史、已出现的 key，以及直接子对话的事实。Durable 适配器每次读取都重新组装它们。#24714 之后只读新增的条目，但每次读取仍要：
  - 扫描本对话和每个子对话的全部任务；
  - 用缓存里的全部条目重算历史；
  - 对每个子对话，按每个保留的运行查一次 submission，并把子对话的整段历史加总。

  每次工具调用（审批钩子）、每个 behavior 步骤的两到四次、每次提交输入，以及给子智能体发消息、等待回答和停止时都会读取。发消息和等待回答这两条路径还会不经任何缓存、连同图片扫描子对话的完整历史。
- **运行时观测。** 适配器每次发布提交和每次实时预览，都对已加载的历史重跑 `historyOf`。每次更新都发布完整快照，尽管观测合约也有 `message.upsert`、`message.remove` 和 `input.changed`。
- **主进程投影。** 每次更新都是快照，所以 Main 每次更新都要按每条历史输入解析一遍上下文行。`ChildThreadProjection` 每次刷新都会重读、重新装饰并重写每个活跃子对话的 archive 和 checkpoint。

#24714 加的缓存减少了条目读取，但重算还在，而且它跟着运行时一直存在，没有淘汰。

这套设计要保证的几件事，都不需要每个事件重算一次：

- 决定和它的写入在同一个提交里；
- 带 key 的操作至多执行一次；
- 只靠日志就能恢复；
- 观测出现缺口后能恢复。

`agent-behavior` 已经写明了增量实现需要满足的性质，即回放不变量 I3：增量缓存等于全量重算。

## 提案

每一份派生状态都改成带游标的日志折叠：按提交顺序，对每个新条目和新任务应用同一个 reducer。重建就是从空状态应用同一个 reducer，所以增量结果在构造上就等于重建结果；折叠状态随时可以丢弃，不影响结果。折叠只放在内存里，日志仍是唯一的权威来源。

### P1 — Durable 适配器里的 behavior 事实

- **每个对话一份折叠。**
  - 折叠归运行时的 Session 所有，behavior harness 和运行时共用。
  - 折叠里存：历史、key 集合、子对话 id、来源和计划记录、工具任务的 call key、运行 id、每次运行的保留记录和用量、每次运行的最后一条回复，以及最近一次 assistant 的调用集合。
  - 不存条目正文，也不存图片。
- **在事务内追平。** 读取前，折叠分三步推进：
  - 读游标之后的新条目。
  - 按谱系里的每个对话，从新到旧读比已知最新任务更新的任务。任务 id 在同一条提交线上按提交顺序分配，任务也从不删除。
  - 只对还可能变化的状态做点读：没结束的 behavior 任务、最新的 generation 任务，以及 submission 还没绑定运行的保留记录。

  `LiveDoc`、`InboxDoc` 和用量汇总文档仍然是点读。事务写过之后就不能再读（`ReadAfterWrite`），所以折叠只会推进到已提交的状态。
- **迟到的工具任务。** 顺序执行的工具轮次，会在 assistant 条目之后才创建后面几个调用的任务。这种任务会就地更新那个调用的 key，以及通过这个调用解析出 key 的工具结果。
- **事实。** `readFacts` 用本对话和直接子对话的折叠组装 `ConversationFacts`。事实的结构和决策代码都不变。
- **只读所需部分。**
  - 工具审批钩子从折叠里读计划、目标轮次和调用窗口，不读子对话。
  - 步骤里的追加校验只在追加不进入运行的输入（quiet input）时读目标对话是否空闲。
  - 给子智能体发消息、等待回答和停止，读子对话的折叠，不再读它的历史。
- **生命周期。** 10 分钟没被用过的折叠在下次读取时丢弃；Session 关闭时丢弃全部折叠。

### P2 — 运行时观测

- 运行时发布的历史复用对话的折叠，不再每次发布和预览都重跑 `historyOf`。
- 在一次运行之内，适配器只为一次更新改动的部分发布 `message.upsert`、`message.remove` 和 `input.changed`。开始观测时、每次 `gap` 之后，以及运行开始和结束时，才发布 `snapshot`，因为 Main 靠这些快照识别自主回合。

### P3 — 主进程投影

- Main 只处理一次更新里改动的输入，不再处理快照里的每一条输入。
- `ChildThreadProjection` 只在 `snapshot`、`gap` 或 `mapping-reset` 时重读子对话 archive，其余时候直接应用 upsert 和删除。这三种事件仍然走"重算再比较"来恢复。
- Main 从 `activity.changed` 识别自主回合，运行开始和结束时就不再需要快照。

### 不在范围内

- 消息 part 存储和界面按 key 订阅：#24019 那条栈。
- 图片和超大工具输出的存储：#24650 和 #23873。
- 进程内网关调用，#24650 已推迟。
- Pi 适配器：它的事实读的是内存里的分支，不读存储。
- 把上下文 checkpoint 改成按行存储：它每个回合写一次，之后有修改再写；P3 之后，子对话投影也不再每次刷新都重写它。

## 考虑过的替代方案

- **保留 #24714 的缓存，只限制它的生命周期。** 它缓存的是折叠的输入，不是结果：每次读取仍要重算历史，并重新扫描任务、子对话的 submission 和用量。
- **把折叠作为 Durable 文档，在同一个提交里写入。** 重启后还在，但事实包含完整历史，每个提交都要重写一份很大的文档，而且每个 Durable 写入方都得维护它。每个 Session 重建一次，比每个提交都写一次便宜。
- **把 `Ledger.read` 换成按调用点的查询。** 这会打破"决定只依赖事实"的规则，还要改 `agent-behavior` 和两个适配器。折叠保留了合约，同时去掉了开销。
- **用 `observeCommits` 推进折叠。** 发布在存储完成后一个宏任务才到，事务可能在折叠看到上一个提交之前就开始了。在事务内追平是精确的，代价只是一次有上限的扫描。

## 验收标准

- AC1 — 对几段脚本化的 Durable 历史（工具任务晚于 assistant 条目的工具轮次、fork、带保留记录的子对话运行、压缩汇总和 behavior 任务），每次提交之后，经已预热的折叠读到的事实都等于经空折叠读到的事实，包括只读到某条较早条目的读取。（verification: unit — Durable history 测试）
- AC2 — 没有新提交时重复读取事实，不读条目、每个谱系对话至多读一个任务、不读子对话条目；有一次提交之后的读取，只读这次提交的行；两者都与历史长度和子对话历史无关。（verification: unit — 计数事务）
- AC3 — 工具审批钩子只读本对话的折叠，步骤的追加校验不读条目和任务，给子智能体发消息、等待回答和停止只读子对话折叠还没见过的条目；结果都不变。（verification: unit — 计数事务和合约套件）
- AC4 — 10 分钟没被用过的折叠会被丢弃，下次读取时重建出相同的事实。（verification: unit）
- AC5 — Pi Durable 上的 `agent-behavior` 合约套件和 Durable 包的测试套件都通过。（verification: unit）
- AC6 — 在一次运行之内，Durable 观测只发布一次更新改动的消息和输入，重放这些事件得到的视图等于重建的视图，发布的历史等于折叠的历史；开始观测、出现缺口，以及运行开始和结束时发送快照。（verification: unit — Durable 投影和运行时测试）
- AC7 — Main 每次更新只处理改动的输入，从 `activity.changed` 识别自主回合，使 Durable 在运行开始和结束时不再发送快照；活跃子对话的 archive 只在快照、缺口或映射重置时重读；在现有子对话场景里，产品消息行和 checkpoint 不变。（verification: unit — Main agent-session 套件）
- AC8 — #24500 的负载形态在开发版 Electron 里运行，报告记录主进程堆内存和按调用点的分配，并与栈的基线对比。（verification: Electron）
- AC9 — Durable README、`agent-session-runtime.md` 和本 note 的三个文件描述上线后的折叠语义。（verification: docs gate）

## 风险

- 折叠有缺陷时，得到的是错误的事实，而不只是慢。AC1 在每次提交后都和重建结果对比；折叠不持久化，所以之后发现状态有误，丢弃折叠就能修复。
- 从新到旧扫描任务，依赖 Durable 按提交顺序分配任务 id，条目读取已经依赖同样的前提。如果将来某个 Durable 版本不按顺序接纳提交，任务就需要一个提交游标。
- 子对话运行的用量现在先加汇总用量，再把条目用量作为一个总和加上。当这次运行有原生压缩汇总时，`costUsd` 可能和以前的加法顺序在最后一位浮点数字上不同。
- P3 依赖 P2 的增量流；P2 上线之前，Main 仍然收到快照，P3 不会降低开销。
