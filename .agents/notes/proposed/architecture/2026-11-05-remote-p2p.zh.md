# Agent Note: 由客户端持有的远程访问 P2P 传输

Status: proposed

[English](2026-11-05-remote-p2p.md) | 中文

## Problem

已配对的桌面和移动设备在 WebSocket 直连地址不可达时，需要跨网络连接路径。WSS Relay 提供了这条路径，但即使两端能够直接通信，长会话仍会消耗中间服务的带宽。P2P 应减少这些流量，同时保持远程访问与账号凭证解耦，也不要求每个 Relay 部署额外运行 P2P 服务。

共享的 [remote-protocol](../../../../packages/remote-protocol/README.md) 和 [remote-transport](../../../../packages/remote-transport/README.md) 包在本仓库维护。业务方法、设备身份、配对和 grants 已由端点负责。本方案保留这些归属，增加可选传输路径。

Relay 接入见[桌面 PR #23505](https://github.com/CherryHQ/cherry-studio/pull/23505) 和[移动端 PR #1600](https://github.com/CherryHQ/cherry-studio-app/pull/1600)，runtime 位于 [relay-server](https://github.com/CherryHQ/relay-server)。本 Spec 以前述接入契约为前提，不包含其代码，也不声称它们已合并。本文只记录实现目标：本次不交付 P2P 代码、原生依赖、包发布或部署。

## Proposal

### 包与进程归属

使用 WebRTC DataChannel，仅传输数据。ICE、DTLS、SCTP、重传和拥塞控制由上游库负责。P2P 原生引擎运行在桌面和移动端，可移植适配位于独立的 `@cherrystudio/remote-transport/p2p` 导出入口。不需要单独的 npm 包或 P2P server。

| 组件 | 计划位置 | 职责 |
| --- | --- | --- |
| 共享 P2P 适配 | 本仓库的 `remote-transport/p2p` | 控制消息 schema、单次协商、分块和有界 MessageStream |
| 桌面原生引擎 | 使用 `node-datachannel` 的产品 Main 适配器 | 端点 PeerConnection 和 DataChannel |
| 移动原生引擎 | 使用 `react-native-webrtc` 的 App 适配器 | iOS/Android 原生连接和生命周期接入 |
| 能力声明 | `remote-protocol` 的 connection hello | 可选端侧版本；既有业务 schema 保持原样 |
| 连接 owner | 现有产品管理器 | App 选择本轮连接；桌面校验授权并确认切换 |
| STUN | 客户端配置 | 使用已有或可选自建服务发现地址 |
| Relay | 现有协议、SDK 和 Bun/DO runtime | 会合、密文字节转发、限制与清理 |

P2P 子入口接受注入的原生与信令窄接口，不得导入 Electron、Node、Bun 或 React Native 原生模块，也不依赖 `relay-client`、`relay-protocol`、账号 API 或云厂商。`remote-transport` 主入口不得加载 P2P。显式导出需要独立的构建、声明和离线消费者验证。

`remote-protocol` 继续描述业务请求与可达入口，只新增可选 hello 能力声明。SDP、ICE 和切换控制 schema 归 `remote-transport/p2p`；产品分发器在加密 RPC 通道中显式注册隔离的控制命名空间，不向现有业务消息、Noise 前言或 Relay 会合消息插入新内容。

首个适配通过现有、已认证的 Relay/Noise 通道承载信令。Relay 无法解释其内容，无需能力接口、选路状态、协议扩展或额外 DO attachment 字段。通用信令接口允许以后使用其他承载方式，但现在不实现尚无消费者的第二套接线。

### 计划文件

以下是拟放置位置，不在原生原型通过之前创建这些目录：


Relay 仓库保留现有包、runtime 和部署输入。共享适配实现与 direct WebSocket、RelayStream 相同的 MessageStream 契约。必要的端侧分块和信用控制留在子入口内，不重复实现可靠 UDP 或 SCTP 重传。

### 建连顺序与兼容

首版优先尝试可达的 direct 地址；失败后先建立已认证的 Relay 通道，再于交付业务调用方之前尝试 P2P。为了保持服务端不变，此方案接受一次 Relay 建连和第二次 Noise 握手的成本，不承诺加快首次连接。

1. direct 连接成功即交付。否则使用既有 v1 会合、ready、RelayStream、Noise、hello 和已配对设备认证，不新增服务端消息。
2. 新桌面在既有宽松 hello 响应中声明可选的 `connectionP2PVersion: 1`，请求保持原样。新 App 仅在版本匹配、本机支持且设置允许时发起 P2P；旧桌面省略该字段，旧 App 忽略它，均不会收到未声明支持的控制消息。
3. 首版只在已配对设备的每轮新连接交付业务之前尝试一次 P2P。首次配对使用既有 direct/Relay；已经开始 RPC、订阅或上传的会话保持当前路径，不做后台迁移。
4. 桌面在允许协商前检查已认证设备、当前 grants、功能开关和容量。每条父连接最多一个候选。不可猜测的一次性关联值绑定父安全通道、两端已验证身份、连接代际和期限；关联值本身不授予访问权。
5. App 为 offerer，桌面为 answerer。通过旧 Noise 通道交换 SDP、trickle ICE 和 end-of-candidates。两端直接访问各自配置的 STUN，并创建一个固定 label/protocol、可靠且有序的 DataChannel。不启用部分可靠传输、额外通道或媒体轨道。早到候选在有界队列中等待 remote description。
6. DataChannel 打开仅表示候选可用。将其适配为 MessageStream，重新建立固定同一端点身份的 Noise，再次执行 hello 与设备授权，并校验关联值。旧 Noise 密钥、access token 或关联值本身都不能授权新的业务路径。
7. 产品 owner 确认唯一一次切换后才交付新连接。提交前的连通性失败会清理候选并交付已认证的 Relay 连接；成功确认后释放旧 Relay 数据/信令通道，保留桌面 listener。

既有 QR 可达元数据已足够，包括 Relay 接入中的 `RelayEndpoint { origin, targetId }`。不需要新 QR 版本、持久 ICE 凭据或新的设备目录。关闭 P2P、缺少原生支持或 STUN 配置，以及新旧客户端组合，都保留 WSS 访问能力。

### 切换、取消与恢复

`DesktopConnectionManager` 负责选路、整轮期限、AppState 和重试。`RemoteAccessService` 负责受父连接约束的桌面候选、身份、当前 grants、确认和清理。共享子入口只协商一次并返回候选，不发布业务会话，也不运行全局重连循环。

- 准备时父 Relay 通道仍可用，但尚未交付业务调用方。候选仅允许握手、授权和切换控制；认证成功不得自动开放业务 RPC。旧通道一旦开始业务调用，就取消候选并保持 Relay。
- App 请求提交；桌面串行检查代际与 grants，至多接受一次提交。提交时旧路径停止接受业务，确认完成后才交付新路径。接入前用协议向量固定请求/确认、重复消息、期限和关闭顺序；本地 ready 标记不能证明双方已达成一致。
- 提交前的连通性失败可保留 Relay。提交结果不确定或确认缺失时关闭本轮相关连接，由 owner 重连。任何一端都不能独立猜测回退结果，导致两个业务路径同时活动。
- 成功确认切换后，主动释放旧通道不得通过过期 close 回调取消 P2P 候选。Relay socket 计数仍遵守现有终态关闭规则。
- 身份不匹配、协议违规或 grants 撤销应终止本轮相关连接，不能通过换路绕过授权。停用远程访问、更换 Relay origin 或撤销配对时，取消关联协商与 P2P 连接。LAN 开关仍只影响 direct 入口。
- 真正断线后建立新的流与 Noise 会话，再使用既有业务恢复逻辑，不迁移密文或自动重放命令。提交前父 Relay 通道断开会取消协商；正常 DO 休眠保留 socket 可用。已建立的 P2P 能独立于 listener 丢失、Relay 重启或 DO 休眠继续运行。

保留 App 既有 15 秒整轮预算，以及存在 Relay 时至多 5 秒的 direct 阶段。Relay 建连、两次 Noise/认证和切换均计入总预算。可选 P2P 尝试初始上限为 3 秒，覆盖 ICE、第二次认证和确认，并为回退/清理保留至少 1 秒。剩余时间不足就立即交付已认证的 Relay。这些上限需真实网络验证。

提供 P2P 关闭选项，并说明直连对端会获知连接地址。端侧可持久保存开关和 STUN 配置；SDP、ICE 凭据、候选地址和关联值只保留临时状态。

### 二进制数据与资源边界

业务语义仍在 `remote-protocol`，所有数据路径继续由 Noise 保护。初始 DataChannel 单条消息最多 16 KiB，包含端侧封装，并服从协商后更小的上限。既有 1 MiB 记录需要分块。端侧信用/分块控制不得重复实现 SCTP 的可靠传输。

限制字节数、项数、接收信用、待发信令和并发协商。应用队列、JS/原生桥在途和原生发送缓冲分别计量，计入旧流与候选并存时的峰值。发送失败不能算作已接纳，已接纳的数据不得重复发送；对端 ACK 本身不能释放无关的原生发送预留。

RN 原生桥可能把二进制发送编码为 Base64，并异步更新 bufferedAmount。网络二进制不等于零拷贝或同步记账。使用经过验证的原生缓冲/完成信号，或最小的有界回执支持；不能证明原生边界的平台不得启用 P2P。

信令初始限制为每条 SDP 32 KiB、每条 candidate 2 KiB、每侧 64 个 candidate、每轮合计 256 KiB。按完整 UTF-8 控制记录检查既有 Noise/RPC 的记录和速率限制，不放宽 Relay 控制限制。拒绝畸形、超限、跨设备或旧代际控制消息。

Relay 计量密文字节和自身资源；端侧观测 P2P 字节、成功率和延迟。日志不记录 SDP、ICE 密码、完整候选地址、票据或关联值。不增加 Relay 数据库、用量账本或 P2P 恢复快照。

### 服务配置与交付

客户端配置已有或自建 STUN 服务的 URL。产品默认值和设置入口留待实现阶段确定，不要求 Relay 能力 API、账号服务或官方域名。跨公网自动建连仍需信令，通常还需 STUN，见 [WebRTC 指南](https://webrtc.org/getting-started/peer-connections)。

完全自建用户可以额外运行 coturn `stun-only`，提供公网 UDP 入口，例如 3478/UDP。可与 Bun 位于同一 VM 的独立容器，也可使用其他厂商。客户端直接访问；现有 HTTP/WSS Tunnel 配置不承载它，Workers/DO 也不运行它。自建说明为可选项，不把 coturn 加入基础 Relay Compose，也不预建 `deploy/stun/`。UDP/STUN 失败保留 WSS；首版不包含 TURN 及其凭据服务。

针对实际 Electron 和移动原生构建验证 [node-datachannel](https://github.com/murat-dogan/node-datachannel)、[react-native-webrtc](https://github.com/react-native-webrtc/react-native-webrtc) 和 [DataChannel 互通](https://www.rfc-editor.org/rfc/rfc8831.html)，通过后锁定版本。实施前刷新产品版本。Expo 需要新的原生构建，不能只更新 JS 或使用 Expo Go。

| 阶段 | 交付 | 验证负责人 |
| --- | --- | --- |
| P0 | 原生适配与真实 MessageStream/Noise 原型；允许测试信令 | 桌面与移动端维护者：原生构建、双向数据、1 MiB、慢读和清理 |
| P1 | 共享 P2P 子入口、可选 hello 能力与控制向量 | 共享包维护者：schema、绑定、预算、导出和新旧兼容 |
| P2 | 产品 owner、候选业务门禁、切换、STUN 设置与关闭选项 | 桌面与移动端维护者：回退、提交不确定、撤销和 AppState |
| P3 | 使用未修改的 Docker/Tunnel/DO 验证跨网兼容；可选自建指引 | 产品与 Relay 维护者：NAT、UDP 阻断、休眠、重启和成本测量 |

独立 P0 原型之后，生产接线必须使用已认证的 Relay 通道。原生验证失败时保留 WSS 并记录具体阻碍，不因此建设另一套完整 P2P 后端。

## Alternatives considered

- 扩展 Relay 的 SDP/ICE 类型、服务端选路和 DO 快照：可以减少部分端侧引导成本，但会耦合部署版本，并为端侧功能增加服务端状态。本方案让服务端继续只处理密文。
- 把 P2P 放入 `relay-client/p2p`：可以共享代码，但会让 Relay SDK 持有本可使用其他信令承载的传输能力。本方案放入已有共享 remote transport 包。
- 单独部署信令服务，或强制自建 STUN/TURN：会增加运维依赖。本方案复用加密通道和可配置 STUN；只有证据表明现有 WSS 回退不足时才重新评估 TURN。
- 在路径间迁移活动 Noise/RPC 会话：需要处理超出首版范围的在途顺序、重放和订阅归属。本方案在业务交付前选择一次，真正失败后重连。
- 同时集成 Tailcat 或自研 UDP：会增加一套待验证的原生/网络栈。先验证选定的 DataChannel 库，其他传输留作未来备选。

## Acceptance criteria

以下是未来实现应达到的结果。这个仅含文档的 Spec 不声称任何 P2P 验收已通过。

- AC1 — 两端通过各自原生适配消费可移植 P2P 子入口，Relay runtime、协议、SDK 与部署输入均不改变，主入口不加载原生 P2P。 (verification: package tests and packaged artifact; owner: shared-package maintainers)
- AC2 — 新旧客户端、关闭或不可用的 P2P、首次配对和 direct 成功均保留既有访问能力；只有支持且已配对设备的新连接才在业务交付前协商 P2P。 (verification: unit and cross-product integration; owner: Desktop/Mobile maintainers)
- AC3 — 父连接身份/代际绑定、全新的固定身份 Noise 和当前 grants 保护候选；未知身份、关联值重放、旧控制消息和撤销不能通过回退绕过检查。 (verification: security integration; owner: Desktop/Mobile maintainers)
- AC4 — 准备、单次提交、确认缺失、取消和关闭竞争至多产生一个业务路径；提交前连通性失败保留 Relay，提交不确定时重连，总期限不叠加额外超时。 (verification: unit and integration fault cases; owner: Desktop/Mobile maintainers)
- AC5 — 双向 1 MiB 记录、慢读端、异步原生事件和恶意信令均处于实测队列/原生预算内；反复取消和重连不导致持续资源增长。 (verification: native packaged artifacts and resource measurements; owner: Desktop/Mobile maintainers)
- AC6 — 真实跨网 Desktop/iOS/Android 验证 STUN/UDP 失败、后台/换网及未修改的 Docker/Tunnel/DO；确认成功的 P2P 释放 Relay 数据连接并能在 Relay 中断时继续工作，报告启动、吞吐、CPU/RSS 和功耗，不声称未经测量的性能提升。 (verification: Electron, mobile devices and runtime integration; owner: product/Relay maintainers)

## Risks

- 原生库/构建兼容性和桥接缓冲尚未验证。只有 P0 通过后才锁定版本；本文不代表已通过包、设备或性能验收。
- Relay 引导和第二次 Noise 握手可能让短会话更慢。应在相同网络与负载下分别测量首次连接时间和长会话出口流量节省。
- 编码前必须固定切换确认协议。结果不确定时主动重连，避免重复命令或 grants 不一致。
- STUN 不保证 NAT 穿透，P2P 会暴露对端地址。保留关闭选项、有界尝试和 WSS 回退，不把可选服务变成基础自建的前提。
