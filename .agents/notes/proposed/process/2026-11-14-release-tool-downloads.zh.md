# Agent Note: Release 外部工具缓存与并行下载

Status: proposed

[English](2026-11-14-release-tool-downloads.md) | 中文

## 问题

[二进制下载器](../../../../scripts/download-binaries.js)准备 mise、Bun、uv、ripgrep 和 Windows MinGit。开发模式有按版本共享的缓存，但 `--packaging` 直接写入 resources，不使用该共享缓存。工具通过同步 curl 子进程串行下载，pnpm store 缓存不覆盖这些资产。

[Release run 43434466816](https://github.com/CherryHQ/cherry-studio/actions/runs/43434466816) 首次 attempt 日志显示，两个 Windows 架构、两个版本均重新下载。每个 Windows job 从各工具开始下载到安装完成的区间合计约 46 秒，包含摘要校验、解压和发布。此次单次观测证明存在重复工作，不能认定稳定提速，也不能认定瓶颈仅在网络。

本说明负责工具原包复用与下载调度。[Release 性能提案](2026-11-13-release-build-performance.md)继续负责 JS bundle、原生 ABI、发布清单及签名和发布边界。

## 提案

### 已校验原包缓存

为打包增加可选的检出目录外资产缓存。CI 指定 `RUNNER_TOOL_CACHE` 下的专用目录；未配置时仍支持直接打包。开发模式按版本共享的缓存行为保持不变。

按固定 SHA-256 缓存官方资产，包括直接提供的可执行文件。复用时重新校验摘要；损坏条目删除后重新获取。不同摘要不能混用，相同资产可跨目标共享同一 blob。未完成传输位于保存的缓存之外。工具与并发调用之间隔离 staging，同时保留调用所属的续传能力。仅发布完整且校验通过的 blob；复用其他调用已发布的条目前先校验。复制或解压到目标私有输出，不使用可写硬链接，也不回写打包或签名后的文件。

保留 curl 重试、续传、拒绝 Range 时的回退、目标选择、安装后才写版本标记，以及 Release 拒绝不完整工具清单的约束。缓存失败时保留普通的已验证下载路径。

### 网络下载限流并行

使用 Node 异步子进程 API 执行 curl，每次调用最多同时下载三个工具。首轮保持同步解压，避免 Windows 多个 PowerShell 解压进程争用。仅将同步调用包装成 promise 无法实现网络重叠。

所有已启动工作结束后才报告失败并最终清理。开发保留可选工具告警；打包仍执行 `verifyBundledBinaries`，拒绝缺失工具。Windows 架构继续串行，USB 签名不变。

### Release 和 Preview 接入

在打包前通过独立步骤准备工具，使用检出的应用代码。兼容性预检在昂贵工作开始前拒绝缺少新接口的源码，不从控制工作流补入应用构建代码。打包 hook 保留准备及校验兜底，支持直接使用 electron-builder。

正式 self-hosted Windows 将原包保存在持久本地工具缓存中，跨检出和不同版本 job 复用。每套 runner 使用独立目录。Hosted Release/Preview 目标恢复 Actions 缓存，键包含格式、目标平台及架构、源码下载清单摘要，不包含 edition 或源码提交。GitHub 分支可见性限制仍适用。

每个目标的 hosted 缓存仅由 Global 保存，CN 只恢复。冷启动同时未命中时允许独立下载，不新增版本间依赖。准备后立即保存完整且校验通过的资产，不等待后续打包或签名成功。不保存未完成传输。

Computer Use 锁定的 npm 平台包、已验证的 Linux SQLite 缓存、JS bundle 传输、COS、签名和发布审批不属于本次改动。

### 交付与证据

设计与实现在一个 PR 中共同审查：原包缓存、限流并行和工作流接入包含定向行为测试。更新打包 README 与现有 Release 操作手册。直接打包未显式配置缓存目录时，使用按检出目录隔离的操作系统临时缓存，临时存储可能被驱逐。

在可测量时区分缓存状态、传输、校验与解压。远程冷暖运行需获得授权，缺失的目标执行仍属未验证。本地 fixture 不能证明 Windows 提速、USB 签名有效性或安装启动完成。全部验收项具备实际证据前，说明保持 proposed。

本地证据覆盖离线复用、损坏修复、摘要变化、真实原包解压、HTTP 并发限流、并发发布、curl 续传及 Range 回退、工作流缓存归属和源码接口拒绝。远程 Windows 冷暖执行仍未验证，AC6 未完成，因此说明保持 proposed。

## 考虑过的替代方案

- 缓存最终 resources 或签名后产物：拒绝，传输资产必须独立于打包修改和签名。
- 复用开发模式的硬链接输出缓存：暂缓，原包具有固定摘要，修改边界更小，开发语义无需改变。
- 引入 COS、自定义 HTTP 下载器或无限并发：暂缓，curl 已提供重试及续传，观测成本不足以支持另一套传输方式或无上限争用。
- 所有目标等待集中预热：首轮拒绝，各平台资产不同，仅为避免冷缓存重复下载不值得新增发布依赖。

## 验收标准

- AC1 — 首次获取后，新的打包目录可离线准备工具；修改输出不改变缓存，摘要变化不能复用旧 blob。 (verification: 真实本地 HTTP 及缓存 fixture；owner: 工具资产准备)
- AC2 — 损坏、中断传输、拒绝 Range 和并发发布不能产生可信的未完成资产、覆盖其他调用的未完成文件，或在可发布 resources 中留下下载残留。 (verification: 损坏、续传、失败及并发发布 fixture；owner: 工具资产准备)
- AC3 — 冷工具请求实际重叠，同时下载不超过三个；退出前所有已启动工作结束，成功工具保留正确的目标文件与版本标记。 (verification: 本地 HTTP 并发及失败 fixture；owner: 工具资产准备)
- AC4 — 直接打包无需 CI 准备仍能工作，开发保留共享缓存及可选工具策略，Release 校验对全部声明目标拒绝不完整工具。 (verification: 显式 downloader 与 before-pack 回归测试；owner: 工具资产准备)
- AC5 — 两个工作流使用精确源码对应的目标工具，在昂贵工作开始前拒绝不支持的源码接口，保留 Windows 架构串行及签名，正式 Windows 仅用本地缓存，每个 hosted 目标仅一个写入者且无版本间依赖。 (verification: 工作流及接口检查与定向 Release 测试；owner: Release 接入)
- AC6 — 准备后、打包前仅保存完整且校验通过的资产；目标清单仍有效，冷暖目标日志确认工具完整且安装版本不变。 (verification: 保存顺序 fixture 及获准目标运行日志；owner: Release 接入)
- AC7 — 文档符合交付行为，报告标明缓存状态和已测量及未知阶段，不凭本地检查推断稳定提速、USB 签名或安装启动验证完成。 (verification: 文档门禁及实际证据审查；owner: Release 接入)

## 风险

恢复小资产可能比直接下载更慢，因此记录缓存计时。并行传输可能争用 runner 连接，同步解压可能延迟回调。Windows 替换及并发发布需在对应文件系统上验证。资产版本占用磁盘，使用现有 runner 维护与 Actions 驱逐，不新增清理守护任务。冻结的 Release 源码必须先具备接口，新工作流才能依赖它。远程证据可能等另行授权后才能取得。
