# Agent Note: 官网文档双向同步

Status: proposed

[English](2026-10-31-website-docs-bidirectional-sync.md) | 中文

## Problem

桌面端功能修改与公开文档位于两个仓库。贡献者需要能在同一个 Cherry Studio PR 中更新两者，同时保留直接在官网仓库编辑文档的能力。单向镜像无法同时满足这两种流程；用最新目录覆盖另一个仓库会丢失并发修改。

官网拥有一个 Fumadocs 静态导出应用，包含本地 Markdown、资源、导航和内容配置。其页头导入了官网的导航、翻译和资源，定时参考资料任务也会修改文档。迁移整个应用会让桌面端开发不必要地耦合官网界面和发布工具。

这是一项新的流程决策。[文档治理决策](../../implemented/process/2026-08-18-docs-governance-and-spec-workflow.md) 明确暂缓了官网投影；本提案定义独立的公开内容流程，不替代其中的开发文档规则。本 Spec 尚未实施同步逻辑或导入内容。

## Proposal

### 内容边界与首次导入

两个仓库均保留编辑能力。在 Cherry Studio 中新增 `website-docs/`，按以下路径映射，不改变相对链接、公开文章 URL 或语言目录结构：

| Cherry Studio | 官网 |
| --- | --- |
| `website-docs/content/` | `docs-site/content/` |
| `website-docs/locales.json` | `docs-site/locales.json` |
| `website-docs/page-aliases.json` | `docs-site/page-aliases.json` |
| `website-docs/shadowed-baseline.json` | `docs-site/shadowed-baseline.json` |

映射范围内所有已跟踪内容均参与同步，包括桌面端和移动端指南、图片、附件、各语言的 `SUMMARY.md` 以及模型参考页面。官网渲染代码、依赖、生成产物、`docs-site/public/models-search/`、部署配置和官网共享组件仍由官网维护。本地 `website-docs/README.md` 和 `AGENTS.md` 说明编辑方法与边界，两者不参与同步。现有 `docs/` 继续承载开发文档。

从一个明确记录的官网 `main` 提交初始化，验证映射文件逐字节一致并建立共同基线后，再启用两个方向。启用时重新检查官网 `main`，把导入期间发生的修改纳入下一轮对账。不得把空目标目录解释为需要同步的删除操作。

### 对账与冲突

在 Cherry Studio 中运行唯一协调器。任一受保护 `main` 上映射路径的 push 请求一次对账；官网通过 `repository_dispatch` 通知协调器。手动触发和定时对账补偿遗漏的通知。通知只请求重新比较两个当前分支头，不授权事件载荷指定任意仓库、路径或版本。

协调器在独立的 `docs-sync-state` 分支中记录上一次内容一致时的两个提交 SHA 和映射内容树摘要。两个记录的提交都必须仍可读取。协调器串行运行且不取消正在执行的任务，并以比较后交换的 push 更新状态。状态更新不直接推送到任一 `main`。

每次运行读取两个当前分支头，将映射内容与上次一致的基线比较。文本使用 Git 现有的三方合并能力，不做空白规范化，也不自定义合并算法。保留互不冲突的修改、相同修改、新增和无歧义删除。重命名按删除加新增处理。文本冲突、不同的二进制替换、删除与修改冲突以及不兼容文件类型，均阻止整批内容同步；不得优先选择某一边、部分传播该批次或发布冲突标记。在运行摘要中报告冲突路径和三个版本。维护者通过普通 PR 将冲突路径的解决结果提交到两个仓库，使这些路径的内容一致；后续对账再处理批次中其余可合并的修改。

若合并结果与某一分支头不同，则在该仓库创建或更新一个机器人维护的同步 PR。如果两边独立修改都需要更新，则为同一轮对账分别在两个仓库各建一个 PR。每个 PR 标明基线、观察到的源和目标 SHA，以及映射内容树摘要。不自动合并这些 PR。已有同步分支若被人工编辑，则交由维护者处理，不覆盖它。同步 PR 未合并即关闭时，暂停该方向，直到手动明确恢复。

仅当两个当前映射内容树一致时才推进共同基线，包括两个 PR 都合并后的情况。部分合并、冲突、运行取消或检查失败都保留原基线。按内容比较，不跳过所有机器人提交：机器人更新可能包含需要传播的新参考资料。相同内容不创建 PR，因此导入同步提交不会导致反向重复同步。

### PR 打开期间发生修改

比较之后到达的修改仍须纳入下一轮运行。创建或更新同步 PR 前，重新获取两边分支头，放弃过期计划。PR 检查将计划绑定到观察到的版本；新的映射范围修改使计划失效时，检查失败，合并前必须重新对账并检查。不得用旧事件覆盖更新的 PR，也不得把尚未观察到的内容标记为已同步。映射范围之外的修改不会使仍然有效的内容计划失效。

### 编辑、验证与发布

贡献者可以正常编辑任一仓库。Cherry Studio 功能 PR 同时包含对应的 `website-docs/` 修改。提供本地预览和 CI 验证：在隔离 checkout 中使用明确记录的官网渲染器版本，覆盖候选内容，不修改其他工作 checkout。使用官网锁定的工具链及现有的生成、链接、导航和构建检查。渲染器版本更新必须作为明确的变更接受审核。Fork PR 验证不持有跨仓库写入凭证，也不能调用高权限同步。

官网 PR 合并后，现有官网流水线仍构建并部署完整产物。桌面端合并只请求文档 PR，不直接触发生产部署。审核者通过合并官网同步 PR 控制尚未发布功能的文档何时上线。官网修改可能在回传 Cherry Studio 的 PR 合并前就已公开；两个仓库提供最终一致性，不提供跨仓库原子发布。

保留官网现有的定时参考资料写入任务。其映射范围内的内容回传主仓库，官网专属的搜索产物保留本地。自动化令牌不产生触发 push 事件时，显式请求对账。单独检查现有向旧文档仓库发送的 release dispatch；不得在内容同步任务中静默改换无关下载版本事件的目标。

### 凭证与启用

使用安装在两个固定仓库上的 GitHub App，仅授予读取版本、写入机器人同步分支及状态、创建 PR 和触发对账所需的权限。机器人创建的 PR 必须执行正常的必需检查，不能依赖默认 `GITHUB_TOKEN` 触发它们。遵守各仓库的提交签名、sign-off 和分支保护规则。安装访问权或权限缺失必须报告失败，不能记录为成功检查点。

先导入并建立基线，再对两个方向执行 dry-run，批准的检查通过后才启用 PR 创建。Dry-run 输出源和目标 SHA、修改路径、冲突及计划执行的 PR 操作，不写入仓库。关闭通知和协调器即可停止同步，同时保留两份内容与最后基线。恢复后从该基线重新计算，不重新导入并覆盖任一内容树。

## Alternatives considered

- **单一可编辑来源。** 更简单，但无法满足在两个仓库编辑的需求。
- **迁移整个官网或文档应用。** 可以消除部分同步，但会把所有权扩展到官网渲染与部署；当前共享页头依赖仍需处理。
- **让贡献者直接使用 submodule 或 subtree。** 会给日常功能 PR 增加跨仓库 Git 操作，仍无法消除并发编辑和发布决策。
- **两个独立复制任务或最后写入者覆盖。** 可能丢失并发文本、资源和删除操作，还可能反复回传修改。
- **自动合并并部署同步 PR。** 会移除处理冲突和控制未发布功能文档上线的审核节点。

## Acceptance criteria

- AC1 — 从记录的官网提交初始化后，每个映射路径的内容逐字节一致，现有文章 URL 保持不变，官网专属文件和现有开发文档不进入同步范围 (verification: docs gate; owner: implementation author)
- AC2 — 任一仓库的修改，包括图片、导航新增或删除，均在另一仓库生成可审核的对应 PR，并在合并后传播，不直接写入任一 main 分支 (verification: GitHub integration; owner: implementation author)
- AC3 — 并发的独立文本修改共同保留；文本冲突、二进制替换、删除与修改冲突、类型冲突报告原始版本和路径，不丢失任一侧内容，也不发布部分批次 (verification: unit; owner: implementation author)
- AC4 — 重复、延迟和机器人产生的事件均能收敛，不重复创建 PR，也不形成同步循环，同时仍传播定时生成的新参考内容 (verification: unit and GitHub integration; owner: implementation author)
- AC5 — PR 打开期间到达的映射范围修改使过期计划失效，并进入后续对账；人工编辑的机器人分支得到保留，主动关闭的 PR 在手动恢复前保持暂停 (verification: unit and GitHub integration; owner: implementation author)
- AC6 — 触发失败、权限缺失、冲突、运行中断或仅一侧 PR 合并后，仍保留可恢复的基线；重试或定时对账仅在当前映射内容树一致时推进基线 (verification: unit and GitHub integration; owner: implementation author)
- AC7 — Cherry Studio 内容 PR 能使用记录的官网渲染器预览并验证未合并修改，不改变其他 checkout；不合法内容无法通过现有官网内容检查 (verification: docs gate and local preview; owner: implementation author)
- AC8 — Fork 检查不能访问同步凭证，任意载荷版本会被拒绝，机器人创建的同步 PR 执行目标仓库正常的必需检查 (verification: GitHub integration; owner: implementation author)
- AC9 — 官网发布仍由其 PR 合并和现有部署流水线控制；参考资料自动化保留官网专属产物，并在 push 事件被抑制时显式请求同步 (verification: GitHub integration; owner: implementation author)
- AC10 — Dry-run 报告计划修改且不写入，禁用同步保留两份内容，恢复后在不重置基线的前提下对账尚未同步的修改 (verification: unit and GitHub integration; owner: implementation author)

## Risks

导入资源会增加桌面端仓库体积。同步 PR 等待审核时，内容可能不一致；冲突会阻止同批次中其他无关修改。分别有效的导航、语言或别名修改，合并后仍可能在语义上无效；Git 合并无冲突后，仍必须通过官网验证器和人工审核。记录的渲染器版本可能落后于官网能力，必须明确更新。

公开文档也涉及移动端功能，桌面端贡献者必须保留这些内容，不能将其视为无关清理。共享内容配置可能需要协同修改映射之外的渲染器。若 Git 历史重写移除了基线版本，必须显式恢复，不能猜测新基线。只有配置 GitHub App 并完成真实双向集成运行，才能宣称同步已运行；本地测试不足以证明跨仓库权限、必需检查执行或生产发布有效。
