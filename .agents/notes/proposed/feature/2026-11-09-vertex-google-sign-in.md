# Agent Note: Sign in with Google for the Vertex AI provider

Status: proposed

English | [中文](2026-11-09-vertex-google-sign-in.zh.md)

## Problem

The Vertex AI provider authenticates only with a pasted service-account key. Organisations that roll Cherry out to staff must mint, send, track and revoke one long-lived key per person (or share one key). A key cannot be tied to a person's account lifecycle, so a leaver keeps access until someone revokes their key by hand. Many organisations forbid service-account key creation outright.

Vertex itself accepts a person's own Google OAuth token, so access can follow the person's Google account and IAM group membership instead. Cherry has no way to obtain or refresh that token today, and no way for an administrator to hand staff a ready-made Vertex configuration on devices the administrator does not manage.

## Proposal

Add a second Vertex sign-in method, **Sign in with Google**, next to the existing service-account key.

- **Settings.** Vertex AI settings gain a `Service account key | Sign in with Google` picker. The picker only switches the view and saves nothing. Saving the other method's credentials over a stored service-account key or Google client asks for confirmation first, and saving a key over a signed-in session signs out (revoking the token) before the key is saved. Changing the OAuth client ID while signed in also asks first and signs out before saving; a blank client ID or secret is never saved. Google mode takes a client ID and secret from a Desktop-app OAuth client that the organisation creates in its own Google Cloud project, and reuses `LoginOauthPanel` for Sign in / Sign out and the signed-in email. Project and location stay shared between both methods.
- **Flow.** Vertex signs in through the existing [OAuth runtime](../../../../src/main/services/oauth/runtime/README.md) as one more loopback PKCE provider (`providers/vertexGoogle.ts`): callback on `127.0.0.1:29875`, scope `openid email https://www.googleapis.com/auth/cloud-platform`, `access_type=offline` and `prompt=consent`. `PkceOAuthClient` accepts an optional `clientSecret`, which Google Desktop clients require at the token endpoint. The existing `oauth.*` IPC routes are reused; no IPC route is added. The built-in `vertexai` provider is registered, and any user-created provider with an `iam-gcp` authConfig resolves to the same definition.
- **Runtime seams.** A provider definition gains an optional `tokenStore` and an optional `revokeToken`; its `clientId` field is removed because the runtime now passes the store the client ID of the client that performed the exchange or refresh (Vertex reads its client from the provider's saved credentials), and `extractAccountId(accessToken)` gains a `tokenData` parameter (Vertex reads the email from the id_token, for display only). Definitions are looked up through one resolver in `providerDefinitions.ts`, which owns the rule that maps a user-created `iam-gcp` provider to a Vertex definition, so `OAuthRuntimeService` stays provider-agnostic. Logout calls `revokeToken` with the stored refresh token on a best-effort basis: a rejected or failed revocation is logged and the local session is still cleared.
- **Storage.** `VertexGoogleOAuthTokenStore` keeps the session inside the provider's `iam-gcp` authConfig as `credentials: { type: 'authorized_user', clientId, clientSecret, refreshToken, accessToken, expiresAt, account }`, written through `ProviderService.setAuthConfig`. The store refuses tokens from a sign-in that finishes after the saved OAuth client changed, so tokens never sit under a client that did not mint them. Logout keeps project, location and the OAuth client, and leaves the provider enabled. The credential schema lives next to the store; the renderer view and the session-preserving save live in `src/main/data/services/vertexGoogleSession.ts`; only the type constant, its guard and the view type are shared in `src/shared/utils/vertexGoogleCredentials.ts`. No database schema or migration change: `credentials` is already a free-form record.
- **Secrecy.** `GET /providers/:id/auth-config` returns an allowlisted view (client ID and secret, account, `signedIn` flag) without any token. `ProviderService.update` keeps the stored session when a save sends that view back for the same OAuth client; a different client drops the tokens and the email, and the `signedIn` flag is never stored.
- **Requests.** Chat and partner models (`buildVertexConfig`) take the access token from `OAuthRuntimeService.getValidAccessToken`, the only refresher. The Node build of `@ai-sdk/google-vertex` receives `googleAuthOptions` with a minimal `authClient` that serves that token, so google-auth-library never holds the refresh token. Model listing sends the same token as a `Bearer` header. A terminal refresh failure clears the session so settings show signed out; with no token, chat fails with "sign in with Google again". Service-account keys keep the edge build and `googleCredentials`.
- **Setup link.** `cherrystudio://providers/vertex-google?data=<base64 JSON {project, location, clientId, clientSecret}>` (any `v` parameter is ignored) targets only the built-in `vertexai` provider. A confirmation dialog shows the project, location and client ID, warns when the link replaces the current method, and asks the person to continue only for a link from their administrator. Confirming signs out first when the link replaces a signed-in session with a different client, then saves Google mode and enables the provider; navigation replaces the history entry so Back cannot reopen the secret-bearing link. The link never signs in by itself.

Out of scope: OpenClaw's legacy Vertex path (keeps service-account keys), Workload Identity Federation, and any Cherry-hosted OAuth client.

## Alternatives considered

- **Ship a Cherry-owned OAuth client ID.** One client for all users means Cherry, not the organisation, owns consent-screen verification for the sensitive `cloud-platform` scope, and every organisation's tokens hang off a client it cannot audit or restrict to its domain. Rejected; each organisation registers its own Internal client.
- **Read Application Default Credentials (`gcloud auth application-default login`).** Requires installing the Google Cloud CLI and running a terminal command, which non-technical staff cannot do, and the ADC file is shared with every other tool on the machine.
- **A dedicated Vertex sign-in service with its own IPC routes.** It would duplicate the OAuth runtime's loopback flow, window gating, cancel codes, attaching other windows to an active sign-in, and shutdown handling. Rejected in favour of the runtime.
- **Use the runtime's default `oauth` authConfig store.** It replaces the whole authConfig with `type: 'oauth'` and resets to `api-key` on logout, losing project, location and the OAuth client. The per-definition `tokenStore` seam keeps the session inside `iam-gcp` instead.
- **Store the session in a separate encrypted file.** Service-account private keys and other OAuth providers' tokens already live in the provider row; a second store adds lifecycle and migration cost for no stronger guarantee. The tokens are instead kept out of the renderer.
- **Keep the edge SDK and inject a bearer header.** The edge wrapper always calls its own JWT signer first and throws without service-account credentials, so a header override cannot bypass it.

## Acceptance criteria

- AC1 — In Google mode a person signs in through the browser and Vertex settings show the signed-in email; signing out shows signed out and keeps project, location and the OAuth client (verification: Electron)
- AC2 — Logout calls the provider's revocation with the stored refresh token and then clears the session, and a rejected or failed revocation still clears it (verification: unit)
- AC3 — With a Google sign-in and no service-account key, chat replies through the Vertex provider in both assistant chat and agent runtimes, and Sync models lists the project's models (verification: Electron)
- AC4 — The auth-config read returns Google credentials as an allowlisted view with a `signedIn` flag that never contains the refresh or access token (verification: unit)
- AC5 — Saving project, location or the same OAuth client keeps the person signed in; changing the OAuth client ID drops the tokens and the signed-in email, and tokens from a sign-in that finishes after the client changed are refused (verification: unit)
- AC6 — Chat requests for a signed-in user pass `googleAuthOptions` whose `authClient` returns the runtime's access token and no `googleCredentials`, and model listing sends that token as a `Bearer` header (verification: unit)
- AC7 — A session whose refresh fails terminally is cleared so the auth-config read reports signed out, and chat fails with a message telling the person to sign in with Google again (verification: unit)
- AC8 — Service-account configurations keep their behaviour: JSON key import fills private key, client email and project; chat passes `googleCredentials` through the edge build without `googleAuthOptions`; changing location keeps the key; model listing signs its request with the key (verification: unit)
- AC9 — Switching the method picker saves nothing, saving the other method's credentials over a stored key or Google client asks for confirmation first, saving a key over a signed-in session signs out before saving, and changing the OAuth client ID while signed in asks and signs out before saving (verification: renderer)
- AC10 — A `cherrystudio://providers/vertex-google` payload missing or blanking any of project, location, client ID or client secret is rejected, and a `v` parameter does not affect parsing (verification: unit)
- AC11 — Opening a setup link shows project, location and client ID with a warning when it replaces the current method, updates the built-in `vertexai` provider only after confirmation (signing out first when it replaces a signed-in session with a different client), replaces the history entry, and never starts a sign-in (verification: renderer)
- AC12 — Every new UI string has a translation in all shipped locales, checked by `pnpm i18n:check` (verification: unit)

## Risks

- **Scope breadth.** `cloud-platform` covers all of Google Cloud for that person. Mitigation: the organisation's consent screen is Internal, and the person's IAM roles still bound what the token can do; administrators should grant only `roles/aiplatform.user`.
- **Malicious setup link.** A link could point a person at an attacker's project so prompts are processed there. Mitigation: the confirmation dialog names the project and client and warns to continue only for a link from the person's administrator; the link never signs in automatically.
- **Tokens at rest in the provider row.** The refresh and access tokens are stored in the provider's authConfig, like service-account private keys and other OAuth providers' tokens; a paired-device export already carries provider credentials by design. Mitigation: tokens never reach the renderer, and signing out revokes the refresh token at Google.
- **Revocation outside Cherry.** If the refresh token is revoked at Google (for example by an administrator), the cached access token is rejected by Vertex until it expires, up to one hour, before the failed refresh clears the session and chat shows the sign-in-again message.
- **Shared fixed loopback port 29875.** Another process on that port blocks sign-in until it exits, and two Vertex providers signing in at the same time cannot both bind it; the second fails until the first finishes or is cancelled.
- **Setup link testing on macOS.** Development builds on macOS cannot receive `cherrystudio://` links, so the operating-system hand-off needs a packaged build to test.
- **Two google-auth-library majors.** v9 (service-account auth headers in `VertexAiService`) and v10 (the Node build of `@ai-sdk/google-vertex`) are both bundled, adding size and two versions to track on upgrade.
- **Client secret distribution.** Google classes Desktop-client secrets as non-confidential; exposure grants nothing without a user sign-in in the organisation's domain.
