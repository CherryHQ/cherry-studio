# Agent Note: Pi Durable owns turn lifecycle and outcomes

Status: proposed

English | [中文](2026-11-18-pi-durable-turn-authority.zh.md)

## Problem

Issue #24748 continues the ownership work in #23565. Pi Durable persists submissions, tasks and answers, while Main independently decides admission, running state and terminal status. A delivery failure or Stop can therefore override native work, and a completed native task can leave a product reply spinning.

Evidence is from HEAD `29d15009d47a70ee76c81ee7a148b83986e94293`. The relevant source trees/blobs are identical to the requested base `442ccc59195cc4cc070da9770c79b9ed65ceddb3`; the checkout is one version-release commit ahead. These are current-code observations, not verification of the proposed behavior:

- `submissionState` already normalizes native records into `InputState.outcome` and reasons, including the separate `unanswered` record branch (`packages/agent-runtime-pi-durable/src/projection.ts:221–283`). The connection instead treats every non-`completed` outcome as an error, gates settlement on `sending`, and selects the first non-success input in the batch (`src/main/ai/runtime/piDurable/PiDurableRuntimeConnection.ts:276–290`). Its `finishTurn()` selects `error` or `turn-complete` from local `failure`; `fail()` emits an error and closes the connection (same file:315–338, 562–565).
- Main converts `turn-complete` to success, runtime errors to error, and stream listener callbacks back into terminal state (`src/main/ai/agentSession/AgentSessionRuntimeService.ts:343–357, 2547–2558, 3051–3077`). The reducer retains `terminal`, settled delivery status and `lastTerminal`, and can retain an earlier non-success outcome over a later event (`src/main/ai/agentSession/agentSessionRuntimeState.ts:50–81, 421–425, 480–487`). These are additional outcome decisions, not just delivery acknowledgements.
- `sending` rejects sends and `autonomous` brackets runtime-initiated delivery (`src/main/ai/runtime/piDurable/PiDurableRuntimeConnection.ts:154–157, 294–299, 335–337`). Native submission already supports `reject`, `steer` and `follow-up`; admission is serialized and `follow-up` becomes native `followUp` (`packages/agent-runtime-pi-durable/src/runtime.ts:744–750, 799–804, 840–847`). Native `pi.live.run` supplies projected activity, and submission records supply accepted/queued/placed facts (`packages/agent-runtime-pi-durable/src/projection.ts:135–175, 210–217, 273–282`). `background-work-state` is a separate projection of behavior results, not foreground Task authority. Native no-input run settlement is also derived from `GenerationTask.state.outcome` into `facts.live.runEnd` (`packages/agent-runtime-pi-durable/src/behavior/history.ts:255–280`).
- The actual Stop chain is renderer `stop()` → `ai.stream.abort` → `AiStreamManager.abortAndDrain()` → stream abort plus `closeSession(..., true)` → `closeRuntimeConnection()` → connection `interrupt()` → native handle `interrupt()` → shared `userStop` → ordinary native abort, followed by connection `close()`. Evidence: `src/renderer/hooks/useStreamCommands.ts:118–120`; `src/main/ipc/handlers/ai.ts:184–185`; `src/main/ai/streamManager/AiStreamManager.ts:1385–1421`; `src/main/ai/agentSession/AgentSessionRuntimeService.ts:1167–1174, 3649–3662`; `src/main/ai/runtime/piDurable/PiDurableRuntimeConnection.ts:523–525`; `packages/agent-runtime-pi-durable/src/runtime.ts:851–861`; `packages/agent-runtime-pi-durable/src/behavior/harness.ts:153–168, 479–482`. There is no direct Stop → `fail()` hop; observation errors take that separate closing path.
- Final backend release currently shuts down the owner **before** the connection flush callback (`src/main/ai/runtime/piDurable/PiDurableRuntimeDriver.ts:88–97`). Native storage closure captures final archives, and the connection later drains observers and stops child projections (`packages/agent-runtime-pi-durable/src/runtime.ts:199–227`; `src/main/ai/runtime/piDurable/PiDurableRuntimeConnection.ts:592–607`). `durableDesktop.close()` closes host resources; `durableFork.ts` performs a native fork transaction, not backend shutdown. Idle TTL release is currently bypassed by `retainWhileIdle` (connection:61; Main service:3504–3507).
- Resume identity is already stored on the message: TypeScript `inputContextId` and `nativeInputId`, SQL `input_context_id` and `native_input_id`, with a unique pair (`src/main/data/db/schemas/agentSessionMessage.ts:32–33, 52`; `migrations/sqlite-drizzle/0040_agent_session_tree_constraints.sql:14–15, 40`). `nativeSubmission.ts` binds context before dispatch and native identity after evidence, and lookup accepts either logical or native input identity (same repository, `src/main/ai/agentSession/nativeSubmission.ts:28–71, 85–103`). The location is not `state/`. Native entry metadata `cherryInputId` is a different correlation field (`packages/agent-runtime-pi-durable/src/runtime.ts:799–808`). Main's replacement-connection reconciliation iterates in-memory `pendingInputs`, so that alone does not establish cold-start recovery (Main service:2304–2327).
- Reopen already emits a baseline, but baseline batches deliberately omit `completion` and historical messages are not live (`packages/agent-runtime-pi-durable/src/projection.ts:69–90`). `ThreadProjection.accept()` forwards content to `RootMessageProjection.accept()`, which skips historical sources without a saved owner; its constructor only restores saved source ranges (`src/main/ai/agentSession/ThreadProjection.ts:21–39`; `src/main/ai/agentSession/RootMessageProjection.ts:31–44, 128–136`). Rebuilding an unpersisted terminal reply needs an explicit recovery contract.
- Renderer pending state reads `topic.stream.statuses.<topicId>.status` and `activeExecutions`; message placeholders read `isActiveTurnProcessing`. Empty stopped replies render from `message.status === 'paused'`, through `message.chat.completion.paused` (`src/renderer/hooks/useTopicStreamStatus.ts:39–50`; `src/renderer/components/chat/messages/blocks/MessagePartsRenderer.tsx:1822–1841`; `src/renderer/components/chat/messages/markdown/ChatMarkdownRuntime.tsx:37–39`). These consumers do not directly read reducer `lastTerminal`; Main separately exposes it as `inspect().lastTerminalStatus` (Main service:1598–1611). Placeholder activity also combines message processing with topic status (`src/renderer/components/chat/messages/hooks/useMessageActivityState.ts:40–53`).

This is a new `feature` Spec for the Pi Durable desktop path. It proposes partial supersession of the [boundary-ownership note](../simplification/2026-11-05-agent-runtime-boundary-ownership.md) within `pi-durable`: the reducer's authority over lifecycle and queued, steer, autonomous or deferred successors transfers to native ownership on that path; the old note continues to own the other runtimes. It specializes, without replacing, the [runtime-contract note](../architecture/2026-10-17-agent-runtime-contract.md). Their native identity and ownership rationale remains applicable outside the proposed supersession.

## Proposal

### Scope and authority

Pi Durable owns turn admission, queueing, execution and terminal outcomes. Main owns product-message associations and delivery; renderer state is a disposable presentation of native observations. Apply this contract only to `pi-durable`. The legacy `process` runtime and its stop, queue, lifecycle and outcome behavior remain unchanged; shared consumers must preserve their existing behavior for other drivers.

This delivery is the proposed bilingual Spec only. Repository governance permits implementation after the Spec PR exists without prior human Approval; this task authorizes no implementation. The note stays proposed through intermediate layers. Only the final layer with evidence for every AC may move and rewrite it as implemented. The unresolved Stop scope below remains subject to human adjudication.

Out of scope:

- Children ownership hierarchy (#24231).
- Append-only queue and conversation branches, which require product decisions.
- Cache eviction under memory pressure, which requires a target behavior decision.
- The legacy `process` runtime.

### One product-result boundary

Keep native normalization in `submissionState`. A single Pi Durable product-result boundary consumes a context-scoped `InputState` with its logical/native identity, `outcome`, optional `RuntimeError`, and native response/run association. It produces either no terminal result or one typed product result containing the associated input/reply identity, `success | paused | error`, and the original reason code/message when present. Live observation, restored baselines and archive recovery use that same boundary; neither Main listeners nor renderer transport infer another result.

| Native input outcome | Product result | Reason contract |
| --- | --- | --- |
| `completed` | `success` | No synthetic error. |
| `aborted` | `paused` | Preserve cancellation reason; show stopped only after native evidence. |
| `unanswered` | `paused` | Preserve why no final answer exists, including `output-truncated` and `no-final-answer`; do not silently display success. |
| `failed` | `error` | Preserve native error code and message, including native `faulted`, `model_error` or normalized `model-error`. |
| Absent | No terminal result | Admission acknowledgement, idle activity and observation errors cannot substitute for an outcome. |

Associate each outcome with its actual input and native answer/run. A batch can contain several inputs; array order must not pick a result for an unrelated reply. Steering row boundaries remain presentation boundaries, not additional native terminal outcomes. For work without a submitted user input, the same boundary accepts a discriminated native Task settlement with task/run identity and native outcome/reason; it does not fabricate an InputState or use a second success/error selector. Native background continuation uses that committed run settlement and existing response attribution; absence of a user submission cannot imply success. Manual compaction remains a command: its committed native task/summary result owns completion, and an idle snapshot alone cannot create a successful answer or compaction card.

The resulting native projection feeds product row status, topic execution status and terminal notifications. Persistence/stream callbacks acknowledge delivery only. A failed projection write remains a delivery error and cannot change a native success into error. Replaying the same input outcome updates its existing projection and produces no second completion notification.

### Native activity and admission

Foreground running state comes from the observed native `ConversationView.docs['pi.live'].run` and its `taskId`, carried to consumers by `snapshot.activity` / `activity.changed`. This is a projection capability this Spec requires adding or extending: current `Activity` exposes only `state`, so carrying `taskId` requires implementation support grounded in native capabilities or an upstream issue where the native capability boundary prevents it. Task phase details, when needed, remain native Task facts. Native compaction tasks supply their own busy interval. `InputState.facts` supplies admission/queued/placed state and `outcome` supplies terminal state; queued input is pending admission to execution, not proof of a running Task. A child-only `background-work-state.active` retains resources and shows child activity without making Main busy. A failed observation reports activity unknown, never idle by default.

Remove `sending`, lifecycle `active` mirrors and `autonomous` as admission or settlement authorities. Local `compacting` and `failure` may describe command delivery, but cannot suppress native settlement or select its result. An autonomous delivery attachment may still exist without owning execution. Route ordinary follow-ups through native `whenBusy: 'follow-up'`, steering through `'steer'`, and explicit reject semantics through `'reject'`; preserve the submitted content and native ordering. Do not drain a second Main execution queue or reject with a local “already active” flag. Native refusal is an admission result, not a completed turn. Native queue state may be rendered directly; no local queue becomes the execution schedule.

### Stop and backend lifetime

For Pi Durable, renderer Stop requests the existing command path to invoke connection `interrupt()` only. Do not abort the transport first to manufacture `paused`, call `fail()`, clear delivery state, close/release the backend, or reset the session. A successful interrupt acknowledgement is not itself a terminal outcome. If completion won the race before Stop, the native completed result remains success.

Continue observing after `interrupt()`. Publish native input-state/outcome updates, message projections, foreground activity/settlement, background results and child task updates as applicable. The single result boundary supplies the eventual terminal notification; a native idle update clears the foreground running indicator. Retain observation access, input bindings, reply/controller associations, buffered content and stream positions, usage attribution, child handles, projection source mappings and pending persistence until delivery commits. Stop failure is a transient command error; it does not destroy these resources or invent a turn result. Stop scope for background children is the open product choice below.

For an established live backend, shutdown is allowed only on an explicit idle release or application exit. Idle release requires no ordinary native work, no active background work requiring the owner, and a completed delivery barrier; it is not forced memory-pressure eviction. Keep the existing retention policy unless an idle release is requested. One root/access detaching, a configuration rebuild or a fork handle ending cannot shut down a backend still owning work or serving peers. Initialization rollback and a cold, scheduler-free fork Session closing are resource cleanup, not turn Stop.

The closing contract is: hold new admission; establish a native quiescence/final-observation barrier without cancelling work as a user Stop; drain admitted callbacks; capture final native entries and flush child archives plus root projection writes; only then close native storage and desktop hosts, detach observations and release handles. Flush failure retains the writer and makes closure incomplete/retryable. The existing final archive capture remains useful but is not evidence that product archives flushed before storage shutdown. If the SDK cannot expose the required pre-storage-close barrier, raise that upstream lifecycle capability for maintainer decision; do not approximate it with an idle poll, sleeps or a new local turn state machine.

### Observation recovery

A diagnostic, disconnected gap, consumer error or unexpected observation closure invalidates delivery, not the native turn. Stop the old observation, fence its generation, and reopen/reattach the same backend/conversation observation. Await a fresh baseline and `drain()` before declaring delivery healthy; reconcile input identities, content, activity and outcomes from that baseline. No input is submitted and no backend is closed as part of observation recovery. Overflow and mapping-reset already have snapshot recovery semantics; consume their replacement baseline rather than treating them as terminal failures.

Serialize recovery and configuration reconciliation through the connection's existing reconciliation owner. Schedule recovery outside the failing callback so waiting for `drain()` cannot wait on itself. Only one generation may publish. Late callbacks from a timed-out or replaced observation are ignored.

The proposed recovery budget is at most three observe/baseline attempts, at most five seconds per attempt, with 250 ms and one second between attempts and an overall 20-second deadline. A successful full baseline resets the budget; incoming error events do not. Stop attempts immediately on application exit, owner release, or confirmed missing/corrupt native identity. After exhaustion retain bindings and projected content, publish a transient delivery-unavailable error with unknown activity, and await an explicit reopen/retry; do not label the turn stopped/failed or spin in an automatic retry loop. A permanently closed native source may remain unavailable; reopening cached dead access is not proof of recovery. Any missing native refresh capability must be resolved at its owning layer rather than hidden by product state.

`DurableObservation` currently exposes no stable batch identifier or public committed revision. Do not deduplicate by object identity or text. Repeated baselines may be read, but their effects are idempotent: upsert messages by context plus committed native message ID, apply preview aliases as replacements, and settle/notify each native input/run outcome once. Persist product parts and source checkpoints in one product transaction. An interrupted partial projection can be replayed safely; recovery must not replay a batch's content, usage attribution or terminal side effects twice. Any additional revision needed for coherent publication belongs in the native projection contract, not a second Main journal.

### Restart attachment and reply reconstruction

Before dispatch, persist `inputContextId` on the retained user message. Bind `nativeInputId` only from a native acknowledgement or observation carrying `nativeInput.id`, in that captured context. SQL uses `native_input_id`; native entry `data.cherryInputId` records the product message ID when placed. None is a separate execution Task ID: the native submission owns its existing Task relationship, including a queued input that has no execution Task yet.

On cold start, discover retained message/context bindings as well as live native inputs; do not depend on `pendingInputs` surviving the process. Strictly reopen the same native conversation, match by logical input ID or the context-scoped `nativeInputId`, and attach delivery to that existing submission/task and the original product turn/reply. A resumed input with an established native input identity must reattach to its original product turn/reply; never create a new product turn/reply for it or relabel it as autonomous. Recover a lost acknowledgement from placed entry metadata when available. A queued snapshot can contain only a native ref; resolving its product association before scheduler resume requires a persisted `nativeInputId` binding or recoverable placed entry metadata.

If `nativeInputId` was not persisted and placed entry metadata does not exist, keep that input explicitly `unknown`: do not guess ownership, automatically resend it or create a reply from that uncertainty, and keep its recovery blocked. Evaluate native conversation-scoped `requestId` correlation for new submissions as a way to resolve this gap; it is a proposed capability, not evidence already available to recovery. Existing data without such correlation still requires explicit manual reconciliation or a later reconciliation step backed by authoritative evidence before the block can be cleared.

Submit only a genuinely new/unattempted input, or retry after explicit evidence of non-admission (`rejected` / `unsupported`) with no confirmed native identity and the attempted binding released. An absent lookup, `unknown`, timeout, absent logical metadata on a queued input, or a missing store is not that evidence. Never automatically resubmit an already accepted, terminal or uncertain input. An intentional resend/edit uses the existing new-input product action and identity; branch behavior is outside this Spec.

The Main root-observation attachment is the reconstruction entry point, before recovered work resumes and before presentation is declared synchronized. Reuse native entries/archive → `ThreadProjection` / `ThreadMessageProjection` → `RootMessageProjection` → product persistence. Extend this path to associate previously unowned historical assistant sources with retained product inputs/replies using native submission answers, input metadata and existing response attribution. Read the retained native entries needed for reconciliation, not only the selected compacted context. Do not mark all historical messages live or route them to whichever turn is currently selected.

Committed native message identity is `entry:<entryId>:<modelIndex>`, scoped by backend/conversation; consumers use it opaquely. Combine that source identity, existing preview aliases and the context's root source-to-product-message checkpoint with the input binding. Upsert the same product reply ID and replace its parts; atomically commit parts and checkpoint, respecting removed-source tombstones. Recover a missing reply using a stable source association so retry cannot create another row. Multiple assistant sources may belong to one reply. Missing/ambiguous attribution remains an explicit recoverable delivery error, not a guessed duplicate. Terminal native outcomes pass through the same result boundary even though the new baseline has no `completion` edge.

### Permitted in-memory delivery state

For Pi Durable, `agentSessionRuntimeState` retains only the following kinds of ephemeral data. The names describe permitted field responsibilities, not a new required public API:

| Permitted field responsibility | Why native Durable cannot supply it |
| --- | --- |
| Delivery attachment and reply/stream handles | Which current consumer/controller is attached, and whether its delivery is opening, open, awaiting a write acknowledgement or detached, exist only in Main. No native running/terminal status is stored here. |
| `buffer` and streaming positions | Undelivered frames, text playout offsets and the last consumer-applied source identify delivery progress, not native task progress. |
| Typing/presentation indicators | A consumer's animation or placeholder interval between frames is local; it cannot assert native execution or survive a contrary native baseline. |
| Transient command/observation/persistence errors and retry generation | These describe access/delivery attempts, not the native turn outcome. |
| Delivery queue positions and pending handoff references | Which consumer frames or product writes await delivery is local. Native input ordering is read from Durable, never copied into an executable Main queue. |

Remove the Pi Durable use of `execution.kind` as idle/turn/steer/autonomous lifecycle, `ownership`, `deferred` native-work ownership, reply `admission`, `terminal`, `pendingResultToolCallIds`, settled delivery `status`, `lastTerminal`, execution `queue`, and execution `launch` scheduling. Replace them respectively with native activity/run identity, input facts/outcomes, behavior result facts, direct native admission and native queue order. Split any remaining delivery-only attachment/reservation work from those responsibilities. Remove connection occupancy mirrors for native background work and compaction; read their native projections. Resource handles, configuration and shutdown coordination stay with existing service/backend owners outside this delivery reducer. No second receipt, Task, outcome or recovery journal is introduced.

## Alternatives considered

- Keep the reducer authoritative and synchronize more flags: rejected because delivery timing still competes with persisted native truth.
- Close/reopen the whole backend on observation failure or Stop: rejected because it changes execution and affects peers merely to repair delivery.
- Reuse the live completion edge alone on reopen: rejected because a baseline intentionally omits it and may contain historical sources without product owners.
- Stop only Main's ordinary native scope, including foreground descendants while respecting background boundaries: preserves independently running background children and their resource/approval/result delivery needs. It matches the current native `abort(context)` call before the separate backend-close side effects. **Recommended, pending human decision**: retain the existing native boundary and the explicit per-child Stop action. This is not “ignore foreground children.” Native defaults are evidenced by `packages/agent-runtime-pi-durable/src/behavior/harness.ts:153–168` and installed SDK `node_modules/@earendil-works/pi-durable/README.md:727, 765` (version 1.5.2).
- Stop Main and background children: offers one action to stop the observed work tree, but interrupts independent work and must define the captured scope, queued-input withdrawal and children created concurrently. Native `abort(context, { background: true })` supplies a scope option; shared behavior must own any chosen policy. **Requires human decision**; this Spec does not authorize enabling it. Current backend closure and reopen policy can interrupt children independently of ordinary Stop, so the present UI effect must not be mistaken for an intentional all-children Stop contract. Choosing either option does not reopen #24231's ownership hierarchy.

## Acceptance criteria

- AC1 — Native inputs with completed, aborted, unanswered and failed outcomes produce success, paused, paused and error respectively in both live and restored baselines, preserving reasons; an absent outcome produces no terminal state, and subsequent delivery, persistence failures or duplicate replay cannot rewrite that result. (verification: unit)
- AC2 — A renderer given native foreground activity and then native settlement removes its running placeholder and shows the mapped result even when the delivery attachment remains open; background-only activity does not show Main as running. (verification: renderer)
- AC3 — While a native task is running, follow-up and steer submissions use native ordering and execute each accepted input once; explicit reject returns native busy without a local sending rejection. (verification: unit)
- AC4 — After Stop during a Pi Durable reply, the backend and conversation remain attached until native settlement; native aborted leaves the original reply paused, and resending a new message afterward does not change that reply's status; partial output and input identity are preserved, and completion that wins the race remains success. (verification: Electron)
- AC5 — Idle release and application exit flush admitted root/child projection writes before storage and host closure; an injected flush failure prevents completed release, and releasing one root does not shut down a peer's work. (verification: unit)
- AC6 — A disconnected gap or observation error during a reply does not end the original turn or close the backend while no native outcome exists; subsequent synchronization uses a fresh drained baseline from the same native conversation without duplicate input, body or terminal notifications. (verification: unit)
- AC7 — Three failing or timed-out observation attempts stop within the 20-second recovery budget and leave native identity/content intact with delivery unavailable and activity unknown, without backend shutdown or a synthetic turn outcome. (verification: unit)
- AC8 — After an application process crash and reopen, an accepted resumed run reattaches by its saved native input identity to the original context, submission and product turn/reply without creating an autonomous turn; a queued input carrying only native identity also reattaches to its original submission, and attachment adds no submission or provider call. (verification: unit)
- AC9 — Unknown admission, lookup absence and a lost acknowledgement never resubmit an input; explicit non-admission without a confirmed native identity permits a deliberate retry through the normal submission path. (verification: unit)
- AC10 — After native terminal commit but before product terminal persistence, reopen reconstructs the reply and mapped status from retained entries; a second reopen preserves the same product message IDs, source ownership and body without reviving removed sources. (verification: unit)
- AC11 — Existing legacy process-runtime fixtures retain the same submit, queue, Stop and terminal outcomes when Pi Durable consumers adopt the new contract. (verification: unit)
- AC12 — The paired proposed feature note has matching AC1–AC12, an explicit unresolved human decision for Stop-to-children, and a Pi Durable field/consumer audit showing only the permitted delivery state with native replacements for removed lifecycle facts. (verification: docs gate)

## Risks

- Product archives and native storage are separate transactions. Tests must fault between native settlement, reply write and checkpoint write; orderly close/reopen fixtures do not prove recovery after arbitrary process kill or exactly-once external tool effects.
- The current shutdown API closes native storage before the desktop flush callback; a stronger barrier may need an upstream lifecycle extension. `settled()` waits for all work and cannot serve as a bounded application-exit barrier for an indefinitely running task. Final native archive capture must remain available until product flush succeeds.
- Native activity currently projects only `pi.live.run`, while completion also considers admissions, compactions and unfinished inputs. Those intervals must remain distinct; merely deleting flags would lose compaction and queued-input presentation.
- Recovery against a cached dead native view may require native observation refresh support. Retry limits govern delivery only; they cannot manufacture native termination. Observe/drain deadlines must fence late effects rather than leave a second publishing observer.
- Removed historical sources, background attribution and steer aliases make reconstruction more than copying text. Existing input-context and checkpoint constraints must remain intact. Shared stream/reducer changes must be isolated to the Pi Durable path to protect legacy process behavior.
- Stop-to-children is not resolved. Removing incidental shutdown can expose independently running children that previously appeared stopped; a human product verdict and corresponding evidence are required before final implementation acceptance. No approval, implementation completion or runtime regression pass is claimed by this draft.
