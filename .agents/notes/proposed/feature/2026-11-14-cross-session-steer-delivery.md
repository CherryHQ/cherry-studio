# Agent Note: Cross-session steer delivery

Status: proposed

English | [中文](2026-11-14-cross-session-steer-delivery.zh.md)

## Problem

#24522 requests cross-session correction without interrupting an active target. Today `session_send` accepts only `target_session_id`, `message`, and optional `reply: 'none' | 'completion'`; it has no delivery mode (`src/main/ai/mcp/servers/cherryAutonomyTools.ts:320`). Its handler calls `AgentSessionDeliveryService.accept()` directly and synchronously returns `accepted` (`src/main/ai/mcp/servers/cherryAutonomyTools.ts:565`, `src/main/ai/mcp/servers/cherryAutonomyTools.ts:582`).

Acceptance persists a durable user message and delivery envelope in the receiver session (`src/main/ai/agentSession/AgentSessionDeliveryService.ts:86`, `src/main/data/services/AgentSessionMessageService.ts:1879`). Dispatch opens a new turn: busy gate, `validateDispatch` with `headless: true`, new assistant persistence, claim binding, then dispatch. The busy gate is at `src/main/ai/agentSession/AgentSessionDeliveryService.ts:256`, with rechecks at `src/main/ai/agentSession/AgentSessionDeliveryService.ts:301` and `src/main/ai/agentSession/AgentSessionDeliveryService.ts:322`; headless validation starts at `src/main/ai/agentSession/AgentSessionDeliveryService.ts:272`, and transactional persistence/claim binding starts at `src/main/ai/agentSession/AgentSessionDeliveryService.ts:329`. A busy receiver always yields `blocked`; runtime idle kicks and a 60-second sweep retry it (`src/main/ai/agentSession/AgentSessionDeliveryService.ts:75`, `src/main/ai/agentSession/AgentSessionDeliveryService.ts:77`, `src/main/ai/agentSession/AgentSessionDeliveryService.ts:18`).

Human messages already support mid-turn steer. `AgentSessionRuntimeService.enqueueUserMessage()` checks an open, live, non-headless turn and matching model / reasoningEffort / serviceTier / fastMode / effective knowledge scope (`src/main/ai/agentSession/AgentSessionRuntimeService.ts:1162`, `src/main/ai/agentSession/AgentSessionRuntimeService.ts:1171`). It registers pending input and calls `currentConnection(entry)?.redirect?.(...)`; otherwise it queues with `steer: true` (`src/main/ai/agentSession/AgentSessionRuntimeService.ts:1186`, `src/main/ai/agentSession/AgentSessionRuntimeService.ts:1195`). The next turn uses a reminder (`src/main/ai/agentSession/AgentSessionRuntimeService.ts:3165`). Cross-session delivery does not use this path.

`redirect?` is an optional runtime capability (`src/main/ai/runtime/types.ts:242`), currently implemented by pi (`src/main/ai/runtime/pi/PiRuntimeConnection.ts:415`), piDurable (`src/main/ai/runtime/piDurable/PiDurableRuntimeConnection.ts:194`), and claudeCode (`src/main/ai/runtime/claudeCode/ClaudeCodeRuntimeDriver.ts:320`). Another Agent currently cannot directly steer a running target through `session_send`; users can already correct eligible interactive turns through the existing human steer path (`src/renderer/components/composer/variants/AgentComposer.tsx:1468`). For an Agent, the current workaround is to stop and resend, which interrupts in-flight tool calls and may repeat non-idempotent operations; this motivates the issue rather than constituting a defect in the existing queue contract.

The issue's scheduled/background Agent scenario remains blocked by upstream gates: interactive authorization (`src/main/ai/mcp/servers/cherryAutonomyTools.ts:336`), headless interaction classification (`src/main/ai/agentSession/AgentSessionRuntimeService.ts:3290`), and unattended delegation denial (`src/main/ai/toolApproval/builtinToolPolicy.ts:20`). #21359 owns those gates. The UI already identifies cross-session senders (`src/renderer/components/chat/messages/frame/MessageHeader.tsx:50`); actual steer/queue admission and its visible status are missing.

## Proposal

1. **Tool contract.** Add optional `mode: 'queue' | 'steer'` to `session_send`, defaulting to `queue`. Omitted mode and explicit `queue` follow the existing path completely unchanged, including headless dispatch, waiting while busy, model selection, retries, and completion. The tool result continues to acknowledge only `accepted`, `requestId`, and `delivery` within the existing result shape: admission is asynchronous, so the requested mode must never be reported as actual admission. Delivery records and `session_deliveries` expose the eventual admission.

2. **Receiver-owned admission.** The delivery service owns requests, ordering, retries, and terminal delivery; the runtime service owns the single admission decision and native injection; data services own only transactions, conditional updates, and uniqueness. A result-bearing atomic attempt, shaped like `trySteerDelivery({message, expectedTarget, scope}) → {kind:'submitted'} | {kind:'queue', reason}`, shares the admission predicate and redirect process with `enqueueUserMessage`. A separate `canSteer()` query is insufficient: workspace validation, turn completion, and connection replacement can invalidate it. Atomic here means one guarded runtime attempt, not a transaction spanning SQLite and native submission.

3. **Fail-closed eligibility.** Steer requires an open, live current turn, a connection exposing `redirect`, and matching effective model / reasoningEffort / serviceTier / fastMode / knowledge scope. Headless target turns can accept steer because admission only injects input and creates no new approval; tool calls triggered by that input follow the receiver's existing headless denial and permission rules. The shared predicate takes `allowHeadless`: the human path passes `false` to preserve its behavior, and the delivery path passes `true`; tests must distinguish these paths. Resolve all configuration from the receiver's session overrides and Agent defaults, never the sender; headless target turns resolve the model against the Agent default and ignore session model overrides (`src/main/ai/runtime/types.ts:77`), so the effective-configuration match must be decided against that turn's resolution source. After asynchronous validation, recheck the expected execution and connection generation. Any unmet condition falls back to queue with a recorded reason.

4. **Persistence and compatibility.** Add immutable requested `mode` and `admission: pending | queued | steered` to the envelope, with an optional reason when queued. Historical records without `mode` mean `queue`. Keep lifecycle states `accepted | delivering | consumed | failed`; `steered` is admission shape, never a lifecycle state. Admission and lifecycle/outcome remain separately observable. Once new fields are written, downgrading to an older version is unsupported: the old reader uses `z.strictObject` and `literal(1)` (`src/shared/ai/agentSessionDelivery.ts:31`). This compatibility cost is explicitly accepted.

5. **Logical execution completion.** For actual steer, `reply='completion'` means the terminal outcome of the logical execution that admitted the input, not a display row. Ignore display boundaries such as `row-roll` (`src/main/ai/agentSession/AgentSessionRuntimeService.ts:1223`, `src/main/ai/agentSession/AgentSessionDeliveryService.ts:70`). Multiple deliveries can bind to one execution; finalize each idempotently, producing at most one result per `requestId` through `deliveryInReplyTo` uniqueness (`src/main/data/db/schemas/agentSessionMessage.ts:64`). A result must not claim the steer intent was independently completed.

6. **Crashes and unknown admission.** SQLite and native submission have no atomic transaction. Persist the original input/context association before native submit, following the prebinding direction in `src/main/ai/agentSession/nativeSubmission.ts:28`; after restart, distinguish not-yet-attempted requests from possibly-submitted ones. Retry is allowed only when the runtime proves that the input was not injected into any execution, including a subsequent run it started itself: atomically return the same request to `accepted/queued`, clear its old execution ownership, and retry at the existing cadence. If non-injection cannot be proved (as with current piDurable), never retry; reconcile the request with any subsequent run that admits it, treat that run as its admitting execution, and record `admission: steered` truthfully. Explicit injection tracks the admitting logical execution to terminality without a second dispatch. Unknown admission retains the original input/context association and performs reconciliation only, never speculative replay. A runtime's ability to prove binding to the expected run or prove non-injection is a prerequisite for enabling steer per runtime, not a capability implemented by this Spec. This follows the existing runtime contract proposal (`.agents/notes/proposed/architecture/2026-10-17-agent-runtime-contract.md:508`, `.agents/notes/proposed/architecture/2026-10-17-agent-runtime-contract.md:518`). “No lost messages” means traceable requests/results without silent discard; it does not promise exactly-once execution after crashes.

7. **Trust attribution.** The human steer reminder labels input as sent by the user, a new user instruction, and higher priority on conflict (`src/main/ai/steerReminder.ts:19`, `src/main/ai/steerReminder.ts:21`, `src/main/ai/steerReminder.ts:24`). Cross-Agent messages must never reuse that wording, which would elevate another Agent's text to human authority. Reuse injection and defang mechanisms with trusted source attribution saying the message comes from another Agent/Session. Do not inherit sender approvals, permission mode, trusted notify channels, tool grants, or workspace. Steering a headless target must create no new approval; tool calls triggered by the input follow the receiver's existing headless denial rules (`src/main/ai/toolApproval/toolGuards.ts:154`), and its existing permission mode and live updates remain effective.

8. **Ordering and fairness.** `queue` requests remain FIFO relative to one another. An eligible `steer` may enter the currently running turn even while an earlier `queue` waits for the next turn; steer requests retain their relative order. Steer must never delete, reorder, or merge any waiting queue item. Once the target becomes idle, waiting queue items execute at the original dispatch cadence. Steer may extend the current execution and thereby defer dispatch of waiting queue items; this Spec guarantees only FIFO among `queue` requests and that steer never deletes, reorders, or merges queue items, and any additional drain-fairness guarantee would require a separate mechanism that this Spec does not add. Record a fallback decision once; the 60-second sweep must not repeatedly upgrade that request to steer.

9. **UI.** Reuse sender attribution with Agent name, session name, and navigation; add actual `queued` / `steered` status. Show steered messages in the running execution's timeline without a separate delivery dispatch; a runtime-started late-admission subsequent run follows Proposal 6. This does not require zero new display rows: continuation rows may still appear, and #23933 owns turn/timeline projection.

10. **Scope and prerequisite.** #24522 owns this cross-session delivery mode. It does not change `assertSessionToolsAuthorized` (#21359), repair steer freezes/replay gaps/stale resume (#23421 and in-flight PR #23519), add cross-session stop/cancel, create a second turn/timeline projection (#23933), or define ACP-like runtime steer semantics; the runtime scope is pi / piDurable / claudeCode, subject to each runtime's admission prerequisite. Implementation requires #23519 or an equivalent fix already in the baseline, with evidence that steer does not freeze. In addition, piDurable must first support binding to the expected run or provable non-injection before steer is enabled for it. The sender gate (#21359) remains unchanged; target-side headless semantics follow the receiver's existing rules, and this Spec adds no target-side exemption.

## Alternatives considered

- Keep queue only and offer a stop-and-resend assistant: smaller surface, but still interrupts in-flight tools and retains the motivating operational cost.
- Limit the first step to the same parent session or scheduled turns: narrows entry points but fails to unlock the operational scenario while prematurely fixing a partial authorization model.
- Add `steered` to the lifecycle enum: makes admission visible there but mixes admission shape with lifecycle and adds another recovery/UI state family.
- Add a receiver switch or Agent-pair authorization: offers finer control but needs an additional product model; no existing receiver policy can be reused this round.
- Ship tolerant readers before writing new fields: best compatibility, but requires two releases and solves no user problem by itself. This round chooses new-format writes with explicitly unsupported downgrade.
- Reuse the human steer reminder verbatim: avoids new source wording but misrepresents cross-Agent text as a user's instruction and is rejected.
- Allow only non-headless targets: rejected because delegated/background targets are a primary scenario and input injection itself needs no approval response; the target's existing headless denial rules already govern tool calls.

## Acceptance criteria

- AC1 — Omitted mode and explicit `queue` preserve existing persistence, busy waiting, headless dispatch, model selection, retries, and completion behavior; historical records without `mode` mean `queue`. (verification: unit)
- AC2 — When `steer` is requested and the target has a configuration-matching, redirect-capable open+live turn, the message is admitted at that execution's next supported boundary only in the scenario where the original execution is controllably held open and that execution actually admits the input; if the original execution ends between submission and consumption and the runtime binds the input to a subsequent run, follow AC5's late admission (no retry; attribution to the run that actually admitted it). An earlier `queue` delivery may still be waiting: the later `steer` enters the current execution while the target is running, and that `queue` dispatches as its own turn after the target becomes idle; neither is lost or duplicated. When the sender queries `session_deliveries` by `request_id`, it can observe lifecycle `delivering` with `admission: steered` while the execution is controllably held running, then terminal `consumed`/`failed`, distinct from initial `accepted`. (verification: unit)
- AC3 — Cross-session steer does not stop / abort / cancel / restart the target task; already-issued tool calls continue under their original contract and retain their results. Verify pi / piDurable / claudeCode, with steer enabled only after each runtime meets its prerequisite, using real, in-progress tool calls; mocked `redirect` return values alone are insufficient evidence. (verification: Electron)
- AC4 — When the target is idle, lacks `redirect`, or differs in model / reasoningEffort / serviceTier / fastMode / effective knowledge scope, the request explicitly falls back to `queued` and executes at the original dispatch cadence without injection into another execution; the sender's same `session_deliveries` query by `request_id` returns `admission: queued` and the fallback reason. (verification: unit)
- AC5 — The same request falls back to queue only once and only with runtime proof of non-injection into any execution; the target execution ending first is insufficient. When the runtime binds a late steer to a subsequent run, do not retry: admission and completion belong to that subsequent run and the same request has no second dispatch. Real persistence/native-runtime tests cover submission racing with the target's terminal event and recovery after restart, distinguishing not-yet-attempted from possibly-submitted requests; crashes around submission, duplicate events, and unknown admission cause neither blind replay nor silent loss, and recovery results remain queryable. (verification: unit)
- AC6 — For actual steer, `completion` refers to the terminal outcome of the admitting logical execution, ignoring display `row-roll`; while the sending session still exists, `reply='completion'` produces exactly one associated result per request at that execution's terminality, including when multiple requests share the execution. Duplicate terminal events produce no second result, and `reply='none'` produces no result; results do not claim the steer intent was independently completed. (verification: unit)
- AC7 — Existing sender identity and delegation gates and receiver tool approval and permission-update rules remain effective; steering a headless target creates no new approval, and its existing headless denial and permission mode remain effective. The shared `allowHeadless` predicate preserves human-path rejection with `false` and permits eligible headless delivery with `true`. Model input identifies the true cross-Agent source instead of presenting a new user instruction, even with forged human reminder tags; sender workspace, tool grants, and trusted notify channels do not flow into the receiver. (verification: unit)
- AC8 — The receiver shows `steered` cross-session messages in the timeline of their admitting running execution, and `queued` messages as waiting for the next dispatch with their status; “waiting for the next dispatch” describes only queued deliveries still waiting — once dispatched, the receiver shows the actual `delivering` or terminal state, because `admission: queued` and lifecycle are separate concerns. Sender attribution and navigation remain consistent after refresh, and steer starts no independent execution except a runtime's reconciled late-admission subsequent run under Proposal 6. (verification: renderer)
- AC9 — The Spec states receipt timing for `accepted` versus final admission, lifecycle and outcome, crash uncertainty, historical defaults, and downgrade limits; English, Chinese, and sidecar pass documentation gates. (verification: docs gate)

## Risks

- **Freeze exposure.** Reusing the steer/projection chain broadens exposure to #23421-class freezes. Implementation is gated on baseline #23519 or an equivalent fix plus evidence of non-freezing steer.
- **Expanded unattended target control.** Steer can change an unattended target’s direction without human intervention. Constraints are the same local-user trust boundary, true source attribution in model input, existing headless denial rules, and envelope traceability. This risk is explicitly accepted, not eliminated.
- **Native late admission / subsequent run.** piDurable may start a subsequent run for a late steer (`packages/agent-runtime-pi-durable/README.md:45`, `packages/agent-runtime-pi-durable/README.md:154`); submission initially lacks a run binding (`packages/agent-runtime-pi-durable/tests/runMetadata.test.ts:71`). When `redirect` returns `true` the native submit has already been initiated, but its confirmation is not awaited (`src/main/ai/runtime/piDurable/PiDurableRuntimeConnection.ts:194`), so it cannot resolve this race. Do not enable steer for a runtime until it meets the expected-run binding or provable non-injection prerequisite; if late admission occurs, reconcile the actual admitting run without retrying.
- **Recovery duplication or loss.** Unknown admission must not replay automatically. `consumed` does not mean business success: existing finalization can store `consumed` with outcome `failed` or `interrupted` (`src/main/data/services/AgentSessionMessageService.ts:2182`). Keep recovery and outcome queryable.
- **Multiple deliveries and row-roll.** Single-assistant/single-`.limit(1)` assumptions are insufficient (`src/main/data/services/AgentSessionMessageService.ts:1923`, `src/main/ai/agentSession/AgentSessionDeliveryService.ts:442`). Finalization must follow logical execution ownership and settle each request idempotently.
- **Envelope rollout and rollback.** Old `strictObject` plus `literal(1)` readers reject the added fields. Downgrade after new-format writes is an explicit unsupported operation; an unchanged version number does not establish compatibility.
- **Ordering with #21359.** This scope does not deliver the complete scenario of a scheduled Agent autonomously correcting another session; upstream authorization remains a separate prerequisite for that scenario.
- **Cross-Agent control and redelegation.** An interactive steered receiver may make further cross-session calls under auto/bypass mode. This round retains existing interactive authorization semantics and explicitly accepts the newly introduced control risk.
- **Configuration races.** Model, tier, and knowledge changes could route input incorrectly. Decide from the receiver's currently effective configuration and recheck execution and connection generation after asynchronous validation.
- **Maintenance barriers.** Pause, backup, shutdown, and write quiesce also govern the new steer handoff. It must participate in existing barriers and drain tracking rather than bypass them.
