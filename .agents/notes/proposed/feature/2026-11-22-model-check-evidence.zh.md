# Agent Note: 持久化模型检查证据

Status: proposed

[English](2026-11-22-model-check-evidence.md) | 中文

## Problem

Issue #18967 希望模型检查证据能够持久保存，带有时间戳，并支持配置失效和过期。目前服务商检查已区分进度、完成结果、各密钥结果、跳过的探测和启用状态。`modelHealthStatusCache` 将行状态放在窗口内存缓存中；`useHealthCheck` 在卸载及端点、凭据变化时清除它，并协调部分模型字段。这些临时结果不是跨重启的可用性记录。

直接持久化 `ModelWithStatus` 会保留凭据对象和原始序列化错误，还可能在设置变化后把旧成功标为当前结果。现有的[流式探测决策](../../implemented/bug-fix/2026-11-17-streaming-model-check.md) 已定义探测完成语义；本提案只记录证据，不替换该决策。

## Proposal

### 证据不等于可用性

为用户在设置中显式发起并完成的模型检查增加独立的 Main 持久化证据。记录服务商标识、唯一模型和线上模型标识、所测能力或探测类型、端点协议、被测配置的不透明标识、完成时间、过期时间、结果、失败类别和可选的完整完成延迟。各凭据结果分别保存。汇总不能把一个密钥成功当成所有密钥成功，也不能把文本探测当成工具、视觉等未测能力的证据。

在现有模型检查详情中，为每个模型、凭据、探测组合显示最新记录，包含可读的本地时间、所测能力、配置标识以及当前证据、已过期或配置已变化状态。历史通过或失败结果与新鲜度分别显示。当前成功只代表当时该探测完成，不保证后续请求可用。现有临时进度和跳过状态保持临时性质；跳过或取消不能用失败覆盖最后一次已完成证据。

初始新鲜度窗口明确设为完成后 24 小时。过期证据保留原时间戳和 Recheck 操作，但不能标为当前可用性。Recheck 复用现有显式检查对话框及凭据、超时、生成成本策略。启动、过期、打开设置或配置变化时均不自动探测。不包含后台重试、新增服务商费用或基于可用性的路由。

### 绑定实际生效配置

Main 在探测前使用实际构造请求的同一解析路径捕获生效配置。标识覆盖服务商与模型关系、线上模型 ID、选定端点类型和解析后的路由、相关服务商请求设置及请求头、凭据标识与修订、模型能力与模态、流式、推理及探测相关参数设置。加入探测或标识算法版本，防止应用或注册表变化后在不同语义下悄然复用证据。外观名称、图标和排序不使证据失效。

使用稳定的非秘密凭据 ID 和 Main 管理的不透明修订，不保存凭据值，也不将未加盐的秘密哈希当作标识。服务商托管认证必须在实际认证材料或账户变化时改变修订，不能使用恒定的 provider-auth 标签。Main 必须在权威的凭据、配置修改边界生成和协调这些修订，包括会影响实际请求的设置导入和预设协调。如果不能确定标识，将旧证据显示为过时或未知，而不是假定匹配。

读取时同时比较已存标识与当前解析标识，并检查过期。失效判断必须跨重启有效，即使变化时没有挂载 UI。配置 A 下开始的检查若在改为 B 后结束，可以保存 A 的历史证据，但不能发布为 B 的当前证据。为每次探测分配操作序号，较早完成的操作不能覆盖同一组合中较新的已完成检查。重复终态回调应幂等。删除服务商或模型时移除所属记录，并防止迟到探测重新创建孤立记录。

### 持久化与隐私

通过现有 Main DataApi、服务和数据库归属存储证据，不使用渲染层持久缓存或用户偏好设置。增加迁移，不为历史检查虚构记录。每个模型、凭据、探测组合只保留最新完成记录，替换其旧配置快照；这是证据，不是审计日志。删除凭据时删除其证据。持久化失败必须显示为未保存，不能将保存失败或未知状态标为持久化成功。

只有 Main 可以根据自己的探测结果写入证据。渲染层可请求检查或读取证据，但不能提交任意通过或失败记录。保留现有 IPC 探测入口和普通服务商流程，将探测执行与只读数据契约分开。共享结构定义跨进程证据形态。渲染层设置模块负责格式化和展示新鲜度，Main 负责标识、校验、顺序、存储与删除。

仅保存允许的失败类别，例如认证、权限、限流、超时、网络、不支持的探测、响应格式错误或不完整以及未知。不保存原始响应体、提示词、令牌、API 密钥、认证请求头、带凭据的完整端点 URL 或异常堆栈。显示端点协议和脱敏标签，并通过不透明配置标识区分。普通实际请求的成功或失败及服务商、模型、密钥启用状态继续由原模块管理，读取或恢复证据不能修改它们。现有显式检查的启用行为不变，但历史证据绝不能触发该行为。

## Alternatives considered

- 持久化现有渲染层结果对象：包含秘密或错误，缺少 Main 管理的配置绑定。
- 每次配置变化就删除旧证据：丢失有用背景，也不能解释旧检查为何不再适用。
- 复用模型或服务商更新时间：外观变化过度失效，而凭据替换、注册表或实际端点变化可能遗漏。
- 保存原始凭据或端点哈希：存在秘密泄漏风险，也不能提供安全的展示标识。
- 定期复查或绕过失败模型：增加服务商调用，并在请求之外改变执行策略。
- 保留完整检查事件档案：在只需展示最后证据的情况下增加保留和迁移复杂度。

## Acceptance criteria

- AC1 — 已完成的单模型和批量检查跨重启保存正确的各凭据、探测证据与完成时间；进度、跳过和取消不制造终态证据，迁移不虚构结果。 (verification: database, main and Electron)
- AC2 — 生效端点或协议、凭据或认证、模型或探测设置及标识版本变化，在设置挂载、未挂载及重启后均使旧证据过时，外观变化则不影响。无法解析的标识绝不显示为当前。 (verification: unit, database and renderer)
- AC3 — 检查期间配置变化、完成顺序颠倒、重复回调以及服务商、模型、凭据删除，不能为错误配置发布证据、覆盖较新记录或重建孤立数据。保存失败明确显示未保存。 (verification: main and database)
- AC4 — UI 分别显示历史结果、新鲜度、时间、能力和脱敏被测标识，包括部分密钥结果和 24 小时过期；Recheck 为显式操作，恢复或过期路径不改变启用、路由或实际请求状态。 (verification: renderer and Electron)
- AC5 — 存储、读取和日志契约排除秘密及原始服务商内容，渲染层不能伪造终态证据。中英文标签、键盘或读屏访问、明暗主题和窄屏通过定向与原生检查，明确说明未验证的验收项。 (verification: main, database, renderer, docs gate and Electron)

## Risks

实际请求标识是主要正确性边界。不完整的指纹看似精确，却可能为不同路由、认证账户或模型协议复用证据。应与现有请求解析集中管理，并测试修改路径，而非相信渲染层快照。

持久证据是本地用户数据，需要迁移和删除生命周期。绝不序列化现有带凭据的行状态。错误分类无法识别时应归为未知，不保存敏感原文。

24 小时窗口是新鲜度策略，不是服务等级保证。时间流逝或后续请求失败不改写历史结果。时钟回退不能延长原过期时间或让未来时间的证据显示为当前；时间不一致时应标为新鲜度未知，直到重新检查。
