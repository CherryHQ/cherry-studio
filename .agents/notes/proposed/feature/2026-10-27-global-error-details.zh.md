# Agent Note: 全局错误详情、诊断与更新操作

Status: proposed

[English](2026-10-27-global-error-details.md) | 中文

## Problem

聊天和 Agent 的错误可以打开错误详情、运行 Doctor 并上报问题。绘画、文件、设置、辅助窗口和启动阶段的失败却不能：它们只显示一条 toast 或对话框，丢失了失败的操作和技术原因。诊断报告也不能稳定地带上失败上下文和对应的 AI 分析。版本过旧的客户端在出错的地方没有更新入口，启动早期的失败也没有受支持的反馈或导出诊断的方式。

## Proposal

- 每个面向用户的失败都可以携带一份发生快照（`AppErrorContext`）：独立的 ID、时间、来源、操作，以及可选的服务商、模型和记录。toast、Promise 失败、错误对话框、内联错误以及渲染或窗口兜底，都能打开同一个错误详情，同时保留原有的恢复操作和原始原因。
- Doctor 和 AI 咨询除了对话之外，也接受操作事件。纯图像模型跳过聊天探测；不涉及模型的操作只运行适用的系统检查。AI 咨询会说明它读取的内容：操作事件读取该错误上下文及其诊断，失败的消息读取该对话。
- 诊断上传和导出增加 `error-context.json`；同一故障存在对应的 AI 分析时，再增加 `ai-diagnosis.json`。重试保留快照。不新增数据库或图片附件的采集。
- 错误详情和关于页共用一份更新状态：按渠道检查、进度和安装确认。轻量窗口把检查交给主窗口。被暂扣的更新源绝不会显示为"已是最新"。
- 启动、迁移、数据目录迁移、数据重置和渲染进程崩溃等失败，在正常界面和服务不可用时，仍保留本地化文案、反馈、导出和官方下载兜底。
- 应用自身编写的错误文案使用语言包。原始外部错误和堆栈仅作为诊断证据。上报和安装始终由用户触发。

## Alternatives considered

- 诊断只限于对话：被否决，因为其他可见的失败仍然缺少有用的上下文。
- 为绘画和文件单独建诊断系统：被否决；复用现有的 Doctor、报告打包和更新流程，只增加发生快照。
- 自动上传报告或自动安装更新：被否决，因为这绕过了用户的选择。
- 操作事件沿用对话的说明文案：被否决，因为它描述的是分析并不读取的数据。

## Acceptance criteria

- AC1 — toast、Promise 失败、错误对话框、内联错误以及渲染或窗口兜底都能打开共享错误详情，且不丢失恢复操作和原始技术原因。(verification: renderer)
- AC2 — 每次发生都带有独立的 ID、时间、来源和操作；Doctor 能分析非对话操作，纯图像模型跳过聊天探测，不涉及模型的操作只运行适用的系统检查。(verification: unit + renderer)
- AC3 — 诊断上传和导出包含 `error-context.json`，仅当同一故障存在对应分析时才包含 `ai-diagnosis.json`；重试保留快照，不新增数据库或图片附件。(verification: unit)
- AC4 — 针对操作的 AI 咨询说明它读取错误上下文和诊断，失败的消息说明读取对话，没有事件时两句都不显示。(verification: renderer)
- AC5 — 已确认的服务商 HTTP 5xx 只隐藏直接上报按钮；AI 咨询仍可转交上报，非 5xx 错误仍可上报。(verification: renderer)
- AC6 — 错误详情和关于页共用更新状态、按渠道检查、进度和安装确认；轻量窗口交给主窗口处理，被暂扣的更新源绝不显示为已是最新。(verification: unit + renderer)
- AC7 — 启动、迁移、数据目录迁移、数据重置和渲染进程崩溃等失败，在没有正常界面时仍提供本地化文案、反馈、导出和官方下载兜底。(verification: unit + Electron)
- AC8 — 应用自身的错误文案来自语言包，原始外部错误仅作为诊断证据，上报和安装只在用户操作时发生。(verification: unit + docs gate)

## Risks

- 共享 toast 原语和弹窗宿主的改动影响所有调用方；需要在各窗口验证现有 toast、确认框和焦点行为。
- 原生对话框、启动消息框、迁移和数据目录迁移窗口、诊断上传和更新安装，需要 Electron 或打包产物验证，单元测试无法覆盖。
- 诊断、上报或更新过程中的失败必须留在本地并可重试，不能递归地再打开错误详情。
