# Agent Note: Doc2X v3-2026 document processing support

Status: proposed

English | [中文](2026-11-08-doc2x-v3-2026-support.zh.md)

## Problem

The Doc2X file processor currently has no user-selectable model contract for the provider's v2 and v3-2026 PDF APIs. Its export request sends a v2 formula field for every model, and the v3-2026 response's structured layout data is not available to the Markdown artifact path. This prevents users from selecting the provider model and loses layout information that can improve tables and repeated-page boilerplate in document output.

The change crosses the shared processor preference schema, renderer settings, main-process remote polling, persistence of task context, and the provider response schema. Existing users also need the current v3-2026 preset behavior to remain the default unless they explicitly choose another model.

## Proposal

Add Doc2X model and v3 export controls to the document-to-Markdown capability:

- Keep `v3-2026` as the preset default, while allowing users to choose `v2` or `v3-2026` in settings.
- Persist `formulaLevel` (0, 1, or 2) and `mergeCrossPageForms` as optional capability overrides. Apply these fields only to v3-2026 export requests; keep the documented v2 request shape for v2.
- Send the selected model in the preupload request and carry the selected options through remote polling and rehydration.
- Validate `version`, `inplace_pages`, page Markdown, and extensible `layout.blocks` response data. Treat `page.md` as the primary page body; use layout blocks as an additive structured layer that removes marked boilerplate, follows `reading_order`, prefers `table_data.html`, and can render a figure URL when no Markdown fallback exists.
- Preserve the existing ZIP artifact path for v2 and legacy responses. Use the existing Markdown artifact persistence for v3-2026 responses that contain structured layout data.
- Keep a standalone live E2E script for the provider's upload, parse polling, export polling, and ZIP download contract. It requires `DOC2X_API_KEY` and is run manually rather than as a CI test.

## Alternatives considered

- **Reconstruct every v3 page only from layout blocks.** Rejected because it discards provider Markdown content such as images and code; layout is an enhancement layer instead.
- **Always send v3 export fields.** Rejected because the v2 API has a separate documented request shape and existing v2 behavior must remain compatible.
- **Make v2 the new default.** Rejected because the shipped preset already defaults to v3-2026; changing that default would silently change existing users' output.
- **Put live provider calls in the regular Vitest suite.** Rejected because the check needs a real credential, external service availability, long polling, and remote artifact downloads. Deterministic unit tests cover transformation and request contracts; the script covers the live provider contract.

## Acceptance criteria

- AC1 — The Doc2X settings panel exposes v2/v3-2026 selection, formula levels 0/1/2, and cross-page formula merging; the existing v3-2026 preset remains the default. (verification: renderer and shared preference tests)
- AC2 — Preupload requests carry the selected model, and export requests send v3-only fields only for v3-2026 while preserving the v2 request shape. (verification: main processor tests and live E2E)
- AC3 — A v3-2026 structured response produces a Markdown artifact that preserves `page.md`, removes marked boilerplate, follows reading order, uses table HTML when available, and retains figure URLs when reconstruction is required. (verification: main processor tests)
- AC4 — v2 and legacy responses without structured layout continue to produce the existing ZIP artifact and remote URL handling. (verification: main processor tests)
- AC5 — The live E2E script completes upload, parse polling, export polling, and non-empty ZIP download for both v2 and v3-2026 without writing credentials to the repository. (verification: manual live E2E)
- AC6 — Existing persisted processor overrides remain valid because the new capability fields are optional, and existing users do not change model unless they select it. (verification: shared schema/config tests and upgrade review)

## Risks

- Doc2X may add block fields or block types. The response schema keeps the block type extensible and retains optional provider metadata, but new semantics may require a later renderer decision.
- A live E2E run depends on provider availability, a valid credential, and the public PDF fixture; it remains evidence of the provider contract rather than a deterministic CI gate.
- v3 structured output is stored as Markdown content while v2 continues to use the ZIP path. The shared artifact persistence contract must remain the single boundary so callers still receive a path-backed artifact.
- Formula and cross-page options affect output quality and provider cost/latency. Their defaults preserve the existing preset's v3-2026 behavior.
