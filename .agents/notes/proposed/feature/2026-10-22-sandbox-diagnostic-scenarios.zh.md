# Agent Note: 沙盒诊断场景

Status: proposed

[English](2026-10-22-sandbox-diagnostic-scenarios.md) | 中文

## 问题

[PR #21006](https://github.com/CherryHQ/cherry-studio/pull/21006) 中的沙盒工作提供了共用的 MXC 管理器、双向 RPC 和 Electron JavaScript 控制台。仅靠可编辑脚本，无法准备独立的文件授权、注册可信宿主回调、协调多个实例或配置强制执行的网络白名单。连接失败也不足以证明目标被策略阻止。

所需 UI 必须通过应用调用方使用的同一个包，验证文件权限、双向 RPC、实例管理和网络访问。本文是对该工作的扩展提案，不表示这些场景已经存在，也不表示基础 PR 已合并。

## 提案

### UI 与结果契约

保留现有“关于 → 沙箱诊断”入口和可编辑 JavaScript 控制台。增加四组场景，各自提供运行操作，并提供全部运行和停止。全部运行按顺序执行各组；实例组自行管理其有意并发的两个实例。每个用例展示预期结果、实际证据及状态：待运行、运行中、通过、失败、不支持、已取消或结果不确定。开始新运行时清除旧结果。后端不可用、超时、空响应或跳过均不能变成通过。

增加类型化的 `sandbox.diagnose` 命令，只接受固定的场景组标识。Main 提供路径、可执行文件、owner 身份、回调方法、网络策略和预算。Renderer 不能指定文件授权、任意代理端点、owner ID 或宿主方法。每组返回结构化用例结果和有大小限制的技术证据；标签和状态描述在 renderer 翻译。全部运行由 UI 组合这些命令，不引入后台任务系统。现有 `sandbox.stop` 同时支持取消当前窗口持有的场景组或脚本运行。

每个窗口最多运行一个脚本或诊断组，共用现有最多四个活跃窗口的预算。实例组最多持有两个沙盒根进程；不把公共 UI 变成无限制的进程启动器。组执行、启动、RPC、本地监听器操作和清理均有有限期限。组执行预算最多 30 秒；关闭另有有界清理阶段，不能把清理不完整变成成功。

### 场景

| 分组 | 必需用例 | 证据 |
| --- | --- | --- |
| 文件权限 | 在授权工作目录内读写；可读但禁止写入只读同级目录；禁止读写未授权同级目录；拒绝名称仅有共同前缀的同级目录 | 宿主创建已知内容的夹具，成功的正向对照，明确的权限错误，宿主确认被拒绝文件未变；授权写入可通过宿主已打开的文件描述符立即观察到 |
| 双向 RPC | 宿主 → guest → 宿主回调 → guest 结果；未授权回调；两个并发请求乱序完成；取消后恢复 | 现有 compute/double 示例返回 41，未授权宿主副作用为零，响应正确对应请求，观察到协作式取消，后续请求成功 |
| 实例管理 | 使用独立工作目录启动 A 和 B；两者运行期间交换请求；停止 A 后继续使用 B；停止全部持有实例 | 不同 ID，A 无法读取 B 的私有夹具，A 达到终态而 B 仍可响应，最终所持根进程退出且资源处理结束 |
| 网络 | 白名单内的 HTTP 和通过 CONNECT 的 HTTPS 请求；未授权主机名或端口；HTTP 重定向到未授权目标；直接 socket 绕过；代理丢失后的访问 | 两个可达的宿主持有目标，精确响应标记，代理决策和目标收到的请求数，未授权目标未收到流量，代理关闭后在有界期限内失败 |

文件夹具仅位于通过路径注册表取得的应用自有临时根目录下。分别授权每个子目录，绝不授权其共同父目录。保留直接访问语义，不用副本替换用户授权。不使用用户文档或秘密作为测试对象。继续明确现有硬链接限制及 `tree: unverified`；这些场景不会将其提升为更强保证。

RPC 两端使用现有 `createRpcPeer` 和 `vscode-jsonrpc`。将固定 guest 入口及其协议依赖打包为构建产物，复制到运行工作目录；不复制开发环境的 `node_modules`，不依赖全局 Python，也不实现另一套分帧引擎。Main 只注册诊断方法，使用宿主绑定的 owner/instance 身份授权，并独立于 RPC 通道消费 stderr。

实例场景的两个根进程都使用现有 `SandboxManager`。部分启动失败时停止每个已成功启动的同组实例。停止 A 不能销毁 B 的管理器。根进程终态和适配器清理结果须与未验证的整棵进程树保证分开报告。

### 网络归属与平台支持

在沙盒包内实现已有的 `network.mode: proxy` / 精确 `host + port` targets 契约，而不是由诊断流程单独发起原始 MXC 请求。包持有每个实例独立的回环代理，将端点传给 MXC，执行目标白名单，并继续禁止直接出站。先启动代理再启动目标；停止目标期间保持代理端口绑定，之后释放监听器和连接。代理失败时撤销转发并停止所持目标；终止不完整时保留所有权以便重试。不回退到无限制网络，也不只依靠环境变量限制出口。

采用有明确授权钩子的、持续维护的 HTTP/CONNECT 代理实现；增加依赖前先选型并验证能力。转发前匹配规范化后的精确主机名和端口，包括 CONNECT authority。不支持通配域名或任意 TCP/UDP 转发。统一处理 DNS 名称、大小写、尾随点、IDNA 和 IP 字面量的规范化，并测试不同拼写与缺省端口。不将 IP 地址等同于获准主机名，也不授权共享该 IP 的全部服务。每个新代理请求都重新授权；重定向目标不继承原授权。丢弃调用方可控制、可能扩大访问范围的代理配置。

首个 UI 夹具使用回环目标和由夹具解析的保留测试主机名，避免依赖公网、外部 DNS 和凭据。HTTPS 使用仅由诊断客户端信任的夹具证书，绝不全局关闭 TLS 校验。localhost 例外只适用于夹具目标，不是对任意主机名的私网访问许可。通用代理路径必须明确并测试 DNS 解析与私有地址处理，防止公网名称悄然重绑定到未授权本地服务。

已安装 MXC SDK 提供 `network.runtimeConfig.networkProxy`，但 schema 中存在字段不等于平台已强制执行。须通过真实流量验证已安装的 SDK/原生库组合。macOS 使用默认拒绝出站，并保持一般宿主回环访问被拒绝。Windows 将完整代理策略交由受支持的 BaseContainer 宿主及其请求感知 probe 检查；不假设 macOS 映射可直接移植，也不引入 Tier 3 初始化。某平台通过授权访问和绕过拒绝检查前，网络组显示不支持及原因。当前 adapter 继续不支持 Linux。不能用一个平台的结果宣布另一个平台的网络验收完成。

### 清理与交付

Main 持有诊断目标和夹具文件。沙盒包持有沙盒根进程、RPC 传输及白名单代理。停止、窗口销毁、部分准备失败和应用关闭均使用同一条所有权链。释放代理连接前先停止接受代理流量；若沙盒根进程可能仍访问文件，则保留文件并报告清理失败。重复停止应安全。在将后续运行报告为成功之前，验证端口和夹具资源已释放。

Spec 当前提交获批后实现，以 PR #21006 的沙盒基础为前置条件。先交付包内代理支持和固定 guest 构建支持，再交付 Main 场景运行器与 UI 结果展示。现有未提交的脚本示例工作与这个纯文档 Spec 分开保留。不引入插件架构、Durable API、WSL、任意宿主浏览或整棵进程树隔离。

## 考虑过的替代方案

- 只增加可编辑片段：不足以提供可信回调、独立授权、并发实例和代理所有权。
- UI 测试流程直接调用原始 MXC：验证的是与应用包不同的启动和清理路径。
- 设置 HTTP_PROXY 但允许全部出站：原始 socket 可以绕过白名单。
- 使用公网网站并将连接失败视为拒绝：DNS、互联网可用性和远端故障不能证明隔离生效。

## 验收标准

- AC1 — 真实 Electron 诊断 UI 可分别运行四组场景和全部运行，展示逐用例结果与实际证据，允许取消，且不会将不支持、不确定或跳过的工作标为通过。 (verification: renderer + Electron)
- AC2 — 宿主创建的文件夹具证明授权读写、只读保护、未授权及路径前缀同级目录拒绝、被拒绝文件未变，以及授权写入即时可见。 (verification: unit + Electron)
- AC3 — 真实沙盒 RPC 经宿主回调返回 41，未授权回调被拒绝且无副作用，乱序响应正确对应请求，取消后仍可使用。 (verification: unit + Electron)
- AC4 — A、B 使用独立授权并发运行；停止 A 后 B 仍可使用；停止和部分启动失败均处理完所持根进程，不声称整棵进程树终止。 (verification: unit + Electron)
- AC5 — 公共管理器的代理模式允许授权 HTTP/CONNECT 目标，拒绝未授权主机/端口、重定向目标和直接绕过，并具有可达的正向对照与目标侧证据。 (verification: unit + Electron)
- AC6 — 代理丢失、取消、窗口销毁和关闭均停止所持目标，释放资源或在清理不完整时明确保留所有权，随后可进行无监听器泄漏的新运行。 (verification: unit + Electron)
- AC7 — IPC 仅接受固定诊断组标识；Main 绑定调用者身份，执行窗口、并发、时长和输出预算；UI 无法扩大宿主能力。 (verification: unit + renderer)
- AC8 — UI 和文档说明实际平台/后端、策略及限制；Windows 原生代理验收使用受支持的 Windows 11，不支持的模式拒绝执行且不回退。 (verification: Electron + docs gate)

## 风险

- MXC 代理能力随原生版本和 Windows 隔离层不同而变化。上游能力缺口可能阻塞对应平台的网络验收；必须明确展示，而不是用更宽松的策略掩盖。
- 代理解析、CONNECT、主机名规范化、DNS 重绑定和私网访问构成新的安全边界。复用库不能替代策略测试或原生绕过测试。
- Electron guest 打包和原生库分发在开发环境与安装产物之间可能不同。不能将开发环境验证报告为打包验收。
- 协作式 RPC 取消不能强制中断不合作的 handler，现有根进程清理也无法证明脱离的后代进程已终止。
