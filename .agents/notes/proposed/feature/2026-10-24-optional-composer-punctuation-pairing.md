# Agent Note: Optional composer punctuation pairing

Status: proposed

English | [中文](2026-10-24-optional-composer-punctuation-pairing.zh.md)

## Problem

[Issue #22583](https://github.com/CherryHQ/cherry-studio/issues/22583) reports that entering punctuation in the Windows v2.1.7 chat input requires manually completing the other half. The [author clarification](https://github.com/CherryHQ/cherry-studio/issues/22583#issuecomment-6379229105) explicitly requests one opening key to insert a pair with the caret between, and the original report requests a switch. Neither the video comparison nor the clarification establishes that Cherry Studio discards a character emitted by an IME.

The inspected v2.1.7 composer preset has no punctuation-pairing extension. This proposal adds optional editing behavior; it does not classify a missing convenience as confirmed text loss or claim that a repair has been implemented.

## Proposal

Add one persistent, opt-in punctuation-pairing preference for the chat composer. Existing installations and new installations keep literal input by default. The switch belongs with chat input settings, uses the repository preference system and translated UI strings, and does not change other text fields or stored messages.

The initial supported pairs are `()`, `[]`, `{}`, `""`, `（）`, `【】`, `「」`, `『』`, `“”` and `‘’`. ASCII single quotes and backticks remain literal to avoid changing apostrophes and code delimiters. This is punctuation assistance, not language-aware code completion.

When enabled, outside active IME composition, one supported opening character inserts its matching closing character with the caret between. Pair only at the end of a text block or before whitespace or a supported closing character; leave typing before other text literal. For ASCII double quotes, leave the character literal immediately after a letter or digit. A non-empty plain-text selection within one text block is wrapped and remains selected; selections crossing blocks or containing tokens use normal editor behavior instead.

Track only closing characters generated by pairing in the current editor session. Typing the matching closer at that tracked position advances over it without adding another closer. Backspace between an untouched, empty generated pair removes both characters as one edit. Moving or editing content must map or invalidate that association; unrelated existing punctuation must never be skipped or removed. Undo and redo treat pairing, wrapping and paired deletion as normal single editing actions.

Never intercept active composition, paste, drop, programmatic content insertion or model output. If an input event supplies a complete pair or multiple characters, preserve it without adding punctuation. Chinese punctuation emitted by an IME retains native ordering and caret behavior; only a non-composing, single-opening-character insertion is eligible. Do not rewrite composition results to force pairing. A confirmed IME text-loss defect would require separate diagnosis of that input path.

Use the existing composer extension boundary and preference ownership. Check Tiptap/ProseMirror capabilities before introducing custom input handling. Do not replace the editor, add language parsers or change send shortcuts, prompt-variable tokens or suggestion navigation. The implementation layer must document its chosen extension mechanism and verify the affected composer consumers.

This is a Spec-only proposal. Implementation starts only after an explicit human `APPROVED` review on the current Spec PR head, following the [Agent Note rules](../../README.md#spec-first-stack). A material change to these behavior rules or acceptance criteria requires reapproval.

## Alternatives considered

- Always enable pairing: rejected because literal punctuation remains useful in ordinary conversation, code snippets and existing workflows.
- Rely only on operating-system input settings: rejected because this does not provide the requested per-application switch and varies by input method.
- Treat the report as proven character loss: rejected because emitted input has not been established; changing composition handling on that assumption risks corrupting valid text.
- Pair every quote and delimiter in every context: rejected because apostrophes, code delimiters, composition and existing text require explicit boundaries.
- Replace the composer or introduce language-aware parsing: rejected as disproportionate to optional punctuation assistance.

## Acceptance criteria

- AC1 — With pairing disabled, all typed text remains literal and existing installations preserve their current input behavior; the preference survives restart and its UI is translated (verification: preference tests and Electron settings check; owner: implementation author)
- AC2 — With pairing enabled, each supported opener at an eligible position inserts exactly its matching pair and leaves the caret inside; excluded delimiters and ineligible positions remain literal (verification: explicit composer renderer test cases; owner: implementation author)
- AC3 — A plain-text selection within one block is wrapped without losing text and remains selected; cross-block and token-containing selections retain normal editor behavior (verification: composer renderer tests; owner: implementation author)
- AC4 — Only a tracked generated closer can be skipped, and only an untouched empty generated pair can be removed together; unrelated punctuation is preserved after intervening edits (verification: composer renderer tests; owner: implementation author)
- AC5 — Composition, multi-character input, paste and programmatic insertion preserve the supplied text without extra punctuation; actual Windows input-method checks cover single-opening and already-paired output with the input method and mode recorded (verification: renderer tests and Windows functional evidence; owner: implementation author)
- AC6 — Pairing, wrapping and paired deletion undo and redo coherently, while send shortcuts, prompt-variable tokens and suggestion navigation keep working (verification: affected existing composer consumer tests and Electron functional check; owner: implementation author)
- AC7 — The implementation PR maps every criterion to actual evidence, names any unperformed scenarios, and remains separate from this Spec-only proposal (verification: PR evidence review; owner: implementation author and maintainer reviewer)

## Risks

IME behavior differs across Windows input methods. Synthetic editor tests alone cannot establish native composition correctness; missing real input-method verification must be reported rather than called a pass. Multi-character input deliberately stays literal even when pairing is enabled.

Generated-pair tracking can become stale under selection edits, undo or token transactions. Scope the state to the editor session, map or invalidate it through transactions and never infer ownership from adjacent punctuation alone. Quote heuristics intentionally favor literal input in ambiguous contexts, which limits convenience but protects existing text.

The switch and delimiter set are proposed product choices, not maintainer-approved behavior. This Spec contains no implementation, release note or completed feature verification. No existing active note was found to own composer punctuation pairing; documentation-governance and other composer decisions remain unchanged.
