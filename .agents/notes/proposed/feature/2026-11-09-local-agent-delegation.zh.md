# Agent Note: 将本地 CLI 委派统一到智能体服务

Status: proposed

[English](2026-11-09-local-agent-delegation.md) | 中文

## Problem

[PR #21221](https://github.com/CherryHQ/cherry-studio/pull/21221) 接入了持久化的本地 Agent 对话，但三个 Code Mate 技能仍启动独立的无界面 CLI 命令。技能从 shell 选择可执行文件，指向已经退役的 Code Mate 配置界面，并且只要二进制可用就自动安装，不考虑本地 Agent 的启用开关。在具备等价委派路径之前删除它们，会丢失在指定项目执行任务的能力。

以下边界来自对 PR 头提交 `909ce14a6882b9ff6fe98ecfa12cc6b635bf3e7d` 的代码检查。这是代码证据，不代表真实 CLI 验收已经完成。

| 现有机制 | 可复用能力 | 缺失契约 |
| --- | --- | --- |
| `cherryAutonomyTools.ts`：`agent_list`、`session_create`、`session_send` | 不可变 Agent/会话标识、调用方实时审批、异步完成请求 | 发现列表不过滤未启用的本地 Agent；创建时不能显式指定项目 |
| `AgentSessionDeliveryService` 与消息持久化 | FIFO 接纳、持久化请求/结果关联、终态报告、恢复 | 投递按无人值守模式运行；不拥有委派任务控制或父会话审批路由 |
| #21221 的本地运行时 | 已配置的可执行文件、模型、凭据、工具流、协议审批及取消 | 没有向发起会话暴露完整的宿主委派关系 |
| `SkillService.uninstallBuiltinSkill` | 来源和命名空间所有权检查保护用户技能 | CodeCliService 仍会自动重新安装三个旧技能 |

现有[跨 Agent 工作目录决策](../../implemented/bug-fix/2026-10-20-cross-agent-session-workspace.md)有意保留目标 Agent 上次的工作目录。这对普通会话创建仍然正确。针对指定项目的编码任务需要独立、显式的工作目录绑定，不能静默修改原默认行为。

[子智能体控制设计](../architecture/2026-10-18-agent-runtime-subagent-control.md)将宿主创建的跨运行时工作交给宿主编排。原生子智能体关系和普通跨会话消息不能被重新归类为宿主拥有的委派。

## Proposal

### Public behavior and scope

智能体服务作为唯一配置所有者。直接聊天和委派工作使用同一个已启用 Agent、配置的可执行文件、原生模型及环境。驱动已注册不等于二进制、凭据或模型已经就绪。发现列表只提供已启用的本地目标，如实报告配置和就绪状态；开始执行前再次检查启用状态并调用驱动验证。

在现有 Cherry 工具界面增加一个明确的 `agent_delegate` 入口。它接受不可变的目标 Agent ID、任务文本，以及显式的已有工作目录 ID 或使用调用方工作目录的选择。创建专用目标会话后立即返回持久化请求 ID 和会话 ID，异步交付一次终态结果。默认使用调用方工作目录；没有用户项目时使用新的托管目录。项目不存在或已删除时拒绝执行，不回退到目标上次使用的项目。执行前的委派审批明确展示目标和项目。

普通 `session_create` 和 `session_send` 保持现有目录和无人值守语义。委派显式启用，且限制为单跳。首批调用方是已经暴露 Cherry 工具的 Cherry 运行时；本地 Agent 是目标，不自动成为新增调用方。不向原生 CLI 配置注入 Cherry 工具，也不承诺每个 ACP Agent 都能继续委派。

### Ownership, approvals and progress

由纳入生命周期管理的宿主委派所有者编排创建、取消、父会话展示和恢复。复用运行时调度、原生连接、消息持久化及现有结果关联。`AgentSessionDeliveryService` 仍负责投递，不成为原生子智能体的所有者。复用已持久化的投递请求 ID、发送方/来源消息标识、接收会话和运行关联。只补充现有记录无法表达的带类型委派标记及控制元数据，不新增平行的任务表或执行引擎。如需修改 SQL schema，必须追加迁移并验证已有数据的数据库。

发起会话展示目标、项目、进度及目标会话链接。复用已有消息/工具渲染与审批控件。目标的每项审批和受支持的结构化问题均通过真实目标会话和审批 ID 路由，同时显示来源任务。批准委派不等于批准目标工具。父轮次结束不能丢失目标待处理审批。确实没有响应者时沿用拒绝/不可用路径，不强制自动模式或绕过权限。

### Stop, cancellation and recovery

增加 `delegation_cancel(requestId)` 及对应任务卡片操作。宿主检查所有权；取消请求 A 绝不能中断后续请求 B。排队工作在启动 CLI 前取消；运行中工作通过目标运行时取消，再报告观察到的终态。重复取消及完成/取消竞争只产生一次最终结果。CLI 失败和超时应报告失败，不能作为成功的空回复。

停止父会话回复不取消委派工作。取消须通过任务卡片操作或 delegation_cancel 明确发起。切换离开视图不取消任务。完成结果继续通过现有异步投递返回。删除来源会话会取消其工作并释放待处理审批。禁用目标会阻止新委派接纳，并取消该目标排队和运行中的委派工作；历史仍可读取。

重启后将持久化记录与实际目标执行状态对齐。只有运行时能证明连续性时才恢复，否则标记为已中断，保留部分输出，不重放任务。通过现有结果关联避免重复终态投递。不改变原生 harness 拥有的子智能体生命周期。

### Retire legacy skills after parity

下列验收条件通过后，停止 CodeCliService 自动安装技能，移除打包的 `code-mate-claude-code`、`code-mate-codex`、`code-mate-opencode` 资源及仅用于技能的预设字段。保留 CLI 安装、认证和终端启动行为。

使用现有来源/命名空间所有权检查清理已安装的系统副本。用户创建、导入或其他来源的同名技能及其文件不受影响。重复启动和安装/升级操作不得重新创建退役内置技能。更新已有工具指南，说明 Agent 发现和统一委派；不要把三个 shell 技能换成三个新的包装技能。在替代能力通过验收前保留旧技能，不能发布中间阶段的能力缺失。

### Delivery sequence

1. 用户已在开发对话中批准实施，并明确无需等待 GitHub Approval。将 Spec 堆叠在 #21221 上，保持当前用户测试实例不变。
2. 核心 PR：实现发现、显式委派入口和项目绑定，复用持久化结果投递；验证 AC1、AC2 及受影响的 AC8 回归。
3. 交互 PR：实现父会话进度/审批展示、精确取消和恢复；验证 AC3–AC5，并在隔离的配置和项目中运行真实 Codex、Claude Code、OpenCode 有界场景，覆盖 AC7。
4. 迁移 PR：能力对齐后只退役系统拥有的旧技能，更新工具指南，补齐 AC6/AC8 证据后再将 Spec 移至 implemented。

## Alternatives considered

- 仅重命名技能并修改设置链接：改动更小，但保留两条执行路径及不一致的启用和配置规则。
- 立即删除技能并直接使用现有 `session_create`：失去显式项目选择、发起会话审批路由和按任务取消的能力。
- 将所有跨会话消息改成交互式委派：破坏现有无人值守消息及其所有权边界。
- 对所有目标使用原生子智能体工具：原生创建/控制不是可移植的跨运行时契约，本地运行时也不都暴露 Cherry 工具。

## Acceptance criteria

- AC1 — 未启用的本地 Agent 不出现在委派发现列表中；发现与接纳之间禁用也不能启动；已启用目标复用智能体服务配置，不凭空要求 Cherry 模型。 (verification: unit — 发现及本地运行时负责人)
- AC2 — 委派仅在显式选择或调用方工作目录执行，拒绝过期目录 ID，并保持普通跨 Agent 会话默认行为不变。 (verification: unit — 真实数据库路由测试)
- AC3 — 父会话 UI 展示关联的进度及目标审批/问题；保留目标 ID，父轮次结束不丢失交互，无响应者时不能授权。 (verification: renderer and Electron — 运行时/UI 负责人)
- AC4 — 排队/运行中/重复取消、父会话删除、目标禁用及完成竞争只结束对应请求一次，不停止无关的后续工作；仅停止父会话回复时，委派工作继续运行。 (verification: unit and Electron — 委派所有者)
- AC5 — 崩溃/重启、CLI 失败及超时保留部分历史、如实报告结果，不盲目重放工作，也不重复交付结果。 (verification: unit — 已有数据数据库及运行时夹具)
- AC6 — 系统拥有的旧技能仅在替代能力对齐后移除；保留同名用户技能；重启/安装/升级不重新安装退役内置技能；CLI 安装/认证/终端流程继续正常工作。 (verification: unit and Electron — 技能及 CodeCli 负责人)
- AC7 — 真实 Codex、Claude Code、OpenCode 分别以正确项目/模型配置完成有界委派并回传结果；验证受支持的审批/取消路径，记录版本限制，不宣称普遍兼容。 (verification: Electron — 集成负责人)
- AC8 — 现有会话投递与原生子智能体契约通过聚焦回归；工具指南与双语设计明确受支持的调用方/目标边界及恢复行为。 (verification: unit and docs gate — 集成负责人)

## Verification progress

2026-11-10，真实委派任务分别通过 Codex、Claude Code 2.1.260（Cherry Gateway / DeepSeek V4.1 Flash）和 OpenCode（原生 `opencode/deepseek-v4.1-flash-free`）完成并回传结果。Claude Code 的 AskUserQuestion 显示在父会话卡片，选择红色后回传红色。OpenCode 的 `sleep 180` 任务在完成前通过父卡片取消并回传取消结果；更早的 `sleep 45` 是自然完成，不作为取消证据。

OpenCode Gateway 失败运行的日志指出 `provider.cherry-gateway` 配置格式错误。Cherry 根据模型元数据写入了 `limit.context`，却缺少 `limit.output`；OpenCode 要求两者同时存在，否则会跳过该服务商。配置生成器现在只在两个值都有效时写入限制，元数据不完整时保留 CLI 默认行为。重新选择模型会重新生成之前写入的配置；修复不会自动改写用户 CLI 文件，也不会绕过 ACP 模型校验。

失败的子任务现在会把已持久化的错误消息同时回传到完成文本和投递元数据，保留部分输出，并排除错误堆栈。显式的委派超时或取消错误优先。回归覆盖直连和 Gateway 模型限制不完整、有或无部分文本的失败任务，以及终态只投递一次：75 项 renderer 测试和 150 项 main 测试通过。随后使用隔离配置进行真实运行，验证了 OpenCode Gateway 完成、具体模型错误回传、主动取消、禁用运行中的目标、父会话权限批准，以及正常退出重启后不重放任务；六条请求各生成一条终态回执。拒绝 OpenCode 工具权限会停止执行，但只回传“Session failed without a text response.”，未清楚说明拒绝原因。强制崩溃、超时、删除父会话、项目目录覆盖和用户自有技能保留尚未纳入本轮实测。本文保持 proposed，不宣称所有模型配置均兼容。

扩展本地 Agent 验收发现 Qwen、MiniMax 和 Hermes 的配置文件模型 ID 与 ACP 模型 ID 不一致。连接现在仅将已知的服务商配置 ID 对照真实目录转换，不可用的模型仍严格报错。通过正常服务商配置流程重新发起真实委派，分别收到 `FIX_QWEN_OK`、`FIX_MINIMAX_OK` 和 `FIX_HERMES_OK`，每条请求均只有一条持久化完成回执。修正错误的可选服务获取方式后，Qwen 与 MiniMax 卸载成功。Cursor 检测不再将 Grok 的 `agent` 符号链接误认成 Cursor。Bun 依赖检测现在会查找 PATH 后面的兼容版本；OMP 18.18.8 使用官方源安装后完成 ACP 握手，本机配置的 npm 镜像则缺少一项依赖。Factory Droid 1.7.1 从官方源隔离安装后也完成握手。握手均不代表模型认证或真实提示词执行已通过。Antigravity 身份检查现在同时读取标准错误输出中的帮助信息；真实卸载已成功移除其 CLI 和 ACP 适配器。Pi 启动文本混入仍属于上游适配器问题；Trae 和源码安装的 Hermes 仍不支持卸载。Hermes 的共享网关按上游设计在闲置超时后退出，不会随 ACP 查看端立即退出。

## Risks

目标 CLI 决定模型访问和协议功能；安装成功不等于就绪。已有本地运行时就绪检查和错误诊断仍是依据。父会话路由审批需要明确响应者所有权，不能仅清除无人值守标记。取消必须绑定到某次运行，而非仅会话；启动恢复不能重复修改文件。工作目录选择会扩展工具 schema，必须保留普通会话原有语义。旧技能移除以真实替代能力证据为前提；CLI 验收失败或不可执行时，不能声称已具备完整退役条件。
