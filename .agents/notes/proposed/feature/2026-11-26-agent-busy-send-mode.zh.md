# Agent Note: 智能体输入区显式忙碌发送模式选择

Status: proposed

[English](2026-11-26-agent-busy-send-mode.md) | 中文

## 问题

智能体正在运行轮次时，发送控件需要明确提供排队、追加和中断三种方式，并告知用户主进程接受了哪种操作。

## 提案

当智能体正在流式运行并且运行时声明了全部三种 `busySendModes` 时，显示使用组件局部状态的选择器。处于编辑状态或启用 `steerWhileBusy` 时隐藏选择器。默认模式为排队。专用追加快捷键覆盖当前选择。中断被接受、智能体进入空闲状态或切换会话后，模式重置为排队。触发按钮的无障碍名称包含当前所选模式。

仅在交互式智能体提交请求未携带旧字段 `followUp` 时接受 `busyMode`。依据主进程返回的 `busyDisposition` 显示反馈。追加回执表示提交已被接受。原生队列沿用 [Pi Durable 后续输入队列](../../implemented/feature/2026-11-26-pi-durable-queue.md)和 [Pi Durable 轮次归属](../../implemented/architecture/2026-11-18-pi-durable-turn-authority.md)的归属规则。宿主回退项在队列面板中只读，原生项仍可重新排序。宿主将等待中的输入行保存为可恢复的 `paused`，直到原生放置或本地处理确认接收。

若当前轮次仍在运行，先预留替换轮次的用户行和助手行，再执行用户停止流程。持有停止目标的话题锁。若需同时持有根话题锁和恢复话题锁，先获取根话题锁。获取锁后重新检查目标。空闲时按普通方式发送。处于忙碌过渡状态但没有运行目标时，拒绝中断。停止或激活失败时原子修复两行。替换轮次的用户行从预留到关联回复始终以 `paused` 状态保留，即使进程在原生绑定前崩溃也可恢复。

## 考虑过的替代方案

持久化模式会使中断选择延续到其他会话。自动重发已撤回的后续输入会违背显式停止的语义。先停止再预留可能导致崩溃时丢失替换输入。

## 验收标准

- AC1 — 符合条件的运行时声明三种模式，请求和响应保留所选模式和回执，并拒绝无效组合。(verification: shared and main Vitest)
- AC2 — 原生队列和宿主队列返回各自的回执。原生项仍可编辑、排序和撤回，宿主项只读，队列清空后可按未发送消息恢复。(verification: main and renderer Vitest)
- AC3 — 当运行时将输入放置到当前 Run 时，显式追加和专用快捷键保持同一 Run 归属。回退到队列时报告实际去向。(verification: main and renderer Vitest)
- AC4 — 中断在执行保留连接的用户停止流程前预留替换输入，持有目标话题锁直至排空，并在失败或原生绑定前崩溃时保留未发送输入。空闲提交跳过停止流程。(verification: main Vitest with SQLite)
- AC5 — 关闭的选择器读出所选模式，各语言下的显示和重置行为与智能体状态一致。对变更范围运行静态检查、格式检查、词条检查、两个 TypeScript 项目检查及 Electron 冒烟场景。第二轮的定向 Vitest、静态检查、格式检查和词条检查均通过。两个 TypeScript 命令均以非零状态退出（最终运行均为 1，较早的运行中为 2），诊断均已存在（Node 10 条，Web 2 条），其中三条位于两个已修改文件的未变更行。第二轮未运行 Electron 或 Playwright，相关场景仍待验证。(verification: renderer Vitest, static checks, and Electron)

## 风险

原生接纳回执可能先于实际放置。定向测试覆盖保留连接的停止行为和重启恢复。实际 Electron 冒烟场景仍待验证。
