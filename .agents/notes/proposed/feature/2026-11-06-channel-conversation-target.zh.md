# Agent Note: 即时通讯频道可绑定对话

Status: proposed

[English](2026-11-06-channel-conversation-target.md) | 中文

## Problem

目前，频道必须绑定智能体。`readDesired` 只有在记录处于启用状态、带有 `agentId`，且对应智能体未归档时，才会报告运行时已连接（`src/main/ai/channels/ChannelManager.ts:153`）；已连接的运行时目标必须带有非空的 `agentId`（`src/main/ai/channels/ChannelRuntime.ts:11`）；如果收到的消息所属会话没有智能体，该消息会被视为孤立消息而丢弃（`src/main/ai/channels/ChannelMessageHandler.ts:390`）。设置表单提供智能体选项和“无”（`src/renderer/pages/settings/ChannelsSettings/ChannelDetail.tsx:292`），选择“无”的频道始终不会连接。

智能体并非中性容器。频道一旦绑定智能体，就会引入会话工作区、该智能体的模型、MCP 和禁用工具配置，以及智能体运行时；每条回复都会进入智能体会话。用户若想通过 QQ、Telegram 或飞书访问自己日常使用的助手对话，目前没有办法做到：为了接入这段对话而创建智能体，会改变模型和工具配置，也会把回复放到用户原本想用的对话之外（#23722）。

## Proposal

一个频道最多绑定一个目标：智能体（与现有行为一致）或对话（一个 topic）。

### 绑定

- `agent_channel` 新增可空的 `topicId`，引用 `topic.id`，并采用 `ON DELETE SET NULL`，与现有可空的 `agentId` 并列。不做回填：每条现有记录保留 `agentId`，且 `topicId IS NULL`，因此升级不会改变现有行为。
- 实体、创建和更新 schema 新增 `topicId`。在服务写事务内，基于合并后的记录校验这一对目标字段，因为部分更新可能新增一侧，而另一侧已存在于存储中；内部调用方会绕过传输层 schema；频道变更通过 `channel.create` / `channel.update` IpcApi 路由进入，而该资源的 DataApi 处理器只提供 GET。
- 没有任何目标的记录仍会保存，但保持断开连接，这与现有“无”选项的行为一致。
- 工作区和权限模式控件仅配置智能体。对于对话目标，表单隐藏这些控件，并说明对话使用其助手自身的模型配置来回复。

### 运行时

- `ChannelRuntimeDesired` 的已连接变体改为携带 `target: {kind: 'agent', agentId} | {kind: 'conversation', topicId}`，替代单独的 `agentId`；`ChannelAdapterConfig` 携带相同的目标。适配器基类保留 `agentId` 作为便捷属性，对于对话目标，其值为 undefined；目前没有具体适配器读取它。
- 当记录处于启用状态，且对应对话存在、未被移入回收站时，`readDesired` 将对话目标报告为已连接；其他情况报告为断开连接。将对话移入回收站会断开频道，但保留绑定；恢复对话后重新连接，永久删除对话则会彻底清除目标。
- 凭据回调和二维码注册不再限定目标类型：`saveCredentials` 目前检查智能体归属，而对话目标没有智能体可供检查。
- 更改任一目标时，在同一次写入更新中清除另一目标和该频道的任务订阅；运行时对账会中止正在执行的轮次并丢弃排队批次，然后连接新目标。切换边界是这次对账：在此之前已接纳的批次仍可能投递一次，已发送的回复无法撤回。

### 消息

- 对话目标通过主进程侧新增的辅助函数，在绑定的对话中执行普通聊天轮次来回复；该函数参照 `startAgentSessionRun` 实现。现有聊天入口 `dispatchCommand` 不接受调用方监听器，因此该辅助函数必须在同一个派发锁内注册完成哨兵和 `ChannelAdapterListener`；派发确认不等于轮次完成，只有终态事件才能放行回复。
- 轮次沿对话当前选中的活动分支继续。`parentAnchorId` 在同一个接纳锁内解析为分支末端：省略它会让新用户记录挂在虚拟根下，使每条平台消息都变成对话的新分支。
- 轮次使用助手配置的模型；没有助手的对话则使用 `chat.default_model_id`。模型或提供商缺失时，通过平台回复返回翻译后的提示，而不是让轮次停滞等待。
- 轮次采用仅限主进程的无界面策略，该策略从请求一路传递到 SDK 工具边界。现有 `headless` 标志只传到智能体运行时；目前，没有窗口的聊天轮次仍然启用 SDK 工具审批，并会在无人查看的情况下停留于 `awaiting-approval`。在该策略下，本轮拒绝执行需要用户批准或用户输入的工具，能够无人值守运行的工具仍可使用；结果不得取决于是否恰好有窗口正在查看该对话。不修改共享工具注册表，也不伪造智能体会话。
- 如果平台消息到达时，对话中已有正在执行的轮次，则在写入任何用户记录之前拒绝该消息，并返回翻译后的提示。普通聊天提交会改为持久化一条转向消息并附着到正在执行的轮次，这会把另一个轮次的输出投递到平台。此拒绝规则仅适用于平台提交；用户从 UI 交互式提交时，保留现有的转向行为。
- 图片和文件复用现有基于 `FileManager` 的持久化；对话目标不再要求预先具备智能体工作区。
- `/help` 根据目标类型提供内容，因为它目前读取智能体元数据和会话命令目录；`/whoami` 保持不变；`/new` 和 `/compact` 仍仅限智能体，对话目标收到这两个命令时返回提示。
- 同一频道的每个平台会话都写入唯一绑定的对话，因此这些外部聊天共享历史和上下文，一个会话可能影响发送给另一个会话的回复。回复仍按来源平台会话路由：只发回提出请求的聊天。

### 设置

- 频道详情表单保留“绑定智能体”，并新增“绑定对话”，选择任一项都会清除另一项。对话选择器按助手和标题列出现有对话。
- 频道列表显示绑定目标的名称；目标已不存在的频道显示为未绑定。

## Alternatives considered

- **绑定助手，并为每个平台会话创建一个对话。** 这更接近智能体现有的会话分流方式，而且已有对话创建能力；但它需要持久化外部会话到对话的映射（现有映射引用的是 `agent_session`，而非 `topic`），行为也不同：各对话相互独立，不共享上述上下文。暂缓；本提案不会阻碍今后采用该方案。
- **仍仅支持智能体，并在文档中指导用户“创建智能体”。** 这是现状，不采用：该请求恰恰无法采用这条路径。
- **复用智能体为空的智能体会话。** 不可行：会话运行时需要从智能体获取模型和工具配置，而且处理器已将这类会话视为孤立会话并丢弃其消息。

## Acceptance criteria

- AC1 — 可以从设置中创建或更新绑定对话的频道，绑定在重新加载和重启后仍然保留，且同一频道绝不能同时绑定智能体和对话。 (verification: 主进程服务测试、渲染进程测试、Electron)
- AC2 — 绑定平台会话中的消息作为用户消息持久化到绑定对话，回复投递回同一个平台会话。 (verification: 使用确定性模型流和模拟适配器的主进程集成测试；真实平台投递另行报告)
- AC3 — 连续的平台消息沿对话的活动分支继续，并在上下文中保留已有历史，而不是每条消息都新建分支。 (verification: 主进程集成测试)
- AC4 — 消息到达时，若绑定对话已有正在执行的轮次，则在写入任何用户记录前拒绝该消息，平台收到翻译后的提示。 (verification: 主进程集成测试)
- AC5 — 频道轮次执行期间，需要用户批准或用户输入的工具既不执行，也不会让轮次停滞等待，即使有窗口正在查看该对话也是如此。 (verification: 主进程集成测试)
- AC6 — 绑定智能体的频道保留可观察到的现有行为：每个平台会话对应一个会话，既有斜杠命令、附件持久化和流式回复均保持不变。 (verification: 既有频道与智能体测试集，加上使用模拟适配器的回归测试)
- AC7 — 将绑定对话移入回收站、永久删除、恢复或批量删除时，频道会保持断开且不崩溃，恢复时重新连接，并在设置中显示为未绑定。 (verification: 主进程服务测试和渲染进程测试)
- AC8 — 新增标签、说明和提示在所有随产品发布的语言中均完成翻译，且 i18n 检查通过。 (verification: i18n 检查和语义审查)

## Risks

- 共享对话上下文是绑定单个对话所接受的代价：一个外部聊天可能影响另一个聊天收到的回复。如果无法接受这一点，就应实现暂缓的备选方案。
- 切换目标无法撤回已发送的回复，对账前已接纳的批次仍可能投递一次。
- 普通聊天没有工作区，因此附件持久化及任何假定存在 `session.workspace` 的路径都必须按目标类型分支处理，不能直接沿用。
- 新列是可空的增量变更，但仍然属于 schema 变更：实现层需要生成迁移，并在已有数据的数据库上验证升级。
- 用户在 UI 中向同一对话输入消息时，共享同一接纳规则；上述忙碌拒绝机制用于防止平台消息与交互轮次交错。
