# Agent Note：持久化 Model Check 证据，支持过期与失效

Status: proposed

[English](2026-11-28-model-check-evidence-persistence.md) | 中文

## 问题

Model Check 的结果只保存在渲染进程内存中（`modelListHealthContext.tsx`）。关闭设置页或重启应用后结果即被丢弃：昨天检查过某个模型的用户，既找不到那次检查的持久证据，也没有检查时间和所针对配置的记录，更不会在后续配置变更悄悄使结果失效时得到任何提醒（[#18967](https://github.com/CherryHQ/cherry-studio/issues/18967)）。脱离上下文展示的历史成功结果具有误导性：端点、凭据或模型设置变更后，旧结果已无法描述今天会发生什么。

Issue 明确了目标（带检查时间、被测配置身份和失败类别的持久证据）、相关配置变更时的失效标记，以及三个验证场景，但没有确定证据存放位置、"被测配置身份"的具体构成，以及如何展示证据而不与实时请求成功混淆。本 Spec 解决这些决策。

## 方案

*存储。* 使用 Renderer Persist Cache（`usePersistCache` / 渲染进程 `CacheService.setPersist`），新增固定 schema 键保存证据映射，记录键为 `(providerId, modelId, resolvedEndpoint, capability, credentialReference)`。Persist 不支持动态模板键。证据是可重新生成的非关键 UI 状态，不是用户设置或会话数据；清空缓存可丢弃证据，但正常重启必须保留。端点 A、B 的检查结果并存，同一元组的复查只替换自身记录。记录包含结果、时间戳、成功延迟、失败类别和被测配置身份。禁止存储原始错误文本、请求头、令牌、凭据或真实请求结果。

*配置身份。* 从执行探测所用的同一解析配置捕获规范化、带版本的非机密快照，不在检查结束后重读设置。包含 provider/model ID、端点类型及去除用户信息和机密查询值的 base URL、wire model ID、能力/探测模式、凭据引用和持久凭据修订号，以及有效探测输入。输入包括 `supportsStreaming`、端点 dialect/传输选择、`AiService.checkModel` 实际使用的 provider/model 请求选项和模态默认参数；固定提示词、选项和 registry 变化由探测契约版本覆盖。仅规范化明确的非机密字段白名单，不整体序列化 provider/model，也不对密钥求哈希。纯标签修改无需使证据失效。

*凭据修订号。* 每个 key entry 新增持久、随机、不透明的修订号，独立于 `ApiKeyEntry.id`。旧 key 在接受新证据前初始化；每次替换 key 值时与写入原子更新，包括 Edit 保留 entry ID 的路径。新增或轮换 key 使用新修订号。provider 级 OAuth/IAM 凭据同样需要持久非机密修订号，在凭据或账户改变时更新，不能只使用常量 `provider-auth`。修订号归现有权威 provider 凭据存储所有，跨重启保留，且不从机密派生。每次检查捕获实际选中的 key 引用和修订号。未提供可信修订号的凭据路径不得将证据标记为当前有效。实现需修改 provider schema/存储，不能假定字段已经存在。

*失败类别。* 对序列化错误使用 `src/renderer/utils/errorClassifier.ts` 的 `classifyError(error, providerId).category`；仅字符串、缺失或无法分类的错误使用 `unknown`。当前 `ModelCheckStatus` 只格式化错误文本，并不提供类别映射。只持久化类别，不保留原始错误。跳过检查不作为失败证据。

*失效。* 当当前配置身份与存储身份不一致时，证据即为失效。失效在读取时通过从当前 provider 和模型配置重新组合身份来计算，因此无需监听器捕获每一次设置写入。失效证据不会被自动删除：它保持可见并标记为失效，直到用户重新运行检查或手动清除。

*展示。* `ModelCheckStatus` 按模型展示持久证据：可见的被测端点、模型/能力、凭据标签/引用及非机密修订号/探测身份、相对检查时间、身份不一致时的失效标记，以及失败检查的失败类别。内存中的新检查结果在展示上始终优先于持久证据。证据行与实时检查状态在视觉上分离，不会被误读为当前可用性信号，也不表明模型是否已启用。

*重置。* 修改 provider 的端点或凭据、编辑模型不会删除证据（仅使其失效）。删除 provider 或模型时，其证据一并删除。

## 已考虑的替代方案

- 持久化到主进程 SQLite 数据库：否决。证据是设置 UI 的展示状态而非会话数据；Renderer Persist Cache 是可重新生成 UI 证据的受支持归属。SQLite 业务记录会增加不必要的生命周期和迁移工作；凭据修订号仍需权威 provider schema/存储变更。
- 身份包含 API key 的哈希：否决。持久化任何由密钥派生的材料只会扩大暴露面而无收益；不透明凭据修订号可覆盖保留 entry ID 的原地修改，而不泄露密钥派生材料。
- 通过订阅设置写操作来失效：否决。读取时重组身份不可能遗漏写入路径，而监听器必须枚举所有写入路径。
- 每个 provider 仅展示最近一次检查而非按模型：否决。Issue 要求按 provider、模型、端点和能力的粒度，且检查本就按模型运行。
- 认为 issue 自带的 spec 已足够、跳过 Agent Note：否决。存储位置、身份构成（尤其是不含密钥材料的规则）以及读取时失效计算，都是 issue 未定的实现决策。

## 验收标准

- AC1 — 成功的检查留下可跨应用重启保留的持久证据，展示结果及其时间戳（验证：渲染层 + 单元测试）
- AC2 — 变更端点、通过 Edit 替换密钥且保持 entry ID、或切换模型流式设置会将先前证据标记为失效，而不是继续显示为当前有效（验证：单元测试）
- AC3 — 失败的检查记录其失败类别，并与时间戳一并展示（验证：渲染层）
- AC4 — 证据按 provider、模型、解析端点、能力和凭据引用为键；同一模型先检查端点 A 再检查 B 后，两条结果均保留，并可见各自被测配置身份（验证：单元测试）
- AC5 — 持久化身份不包含 API key 材料或密钥派生哈希；轮换密钥或保留 entry ID 原地修改 key 值会使旧证据失效，重启后仍失效（验证：单元测试）
- AC6 — 检查成功后的真实请求失败不会改变已存储的检查证据，且证据展示与实时请求状态和启用状态在视觉上保持区分（验证：渲染层）
- AC7 — 删除 provider 或模型会移除其证据；所有新文案覆盖全部 18 个语言文件（验证：单元测试）

## 风险

- 缓存增长：同一元组复查会替换记录，但历史端点/凭据元组仍会增长。最多保留最近 1000 条，先淘汰最旧记录，支持手动清空。淘汰只表示证据丢失，不表示成功。
- 虚假信心：失效标记依赖身份覆盖所有会改变检查结果的字段。上述身份字段与检查路径实际使用的输入一致；未来新增的检查路径输入（例如新的代理设置）必须在引入时加入身份。
- 迁移：新增固定证据缓存键初始为空。持久凭据修订号需要 provider schema/存储初始化；缺少受支持身份/修订号的旧证据只能失效，不得标记为当前有效。
