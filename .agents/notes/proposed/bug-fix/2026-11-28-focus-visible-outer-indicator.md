# Agent Note: Keyboard focus uses a ring-colored border and a translucent outer halo

Status: proposed

English | [中文](2026-11-28-focus-visible-outer-indicator.zh.md)

## Problem

[#17436](https://github.com/CherryHQ/cherry-studio/pull/17436) (merged 2026-08-01) made keyboard focus reuse a control's border, fill, or an inset indicator, and `DESIGN.md` § Focus forbids outer rings and positive outline offsets. The pull request correctly removed pointer and open-state feedback (`focus:ring-*`, `aria-expanded:` and `data-[state=open]:` rings and borders), and it also removed about 80 keyboard-only `focus-visible:ring-*` rings.

Focus drawn only inside a control competes with state, which lives on the same border, fill, and inset area ([#24947](https://github.com/CherryHQ/cherry-studio/issues/24947)):

- Tailwind v4 emits `data-*`, `aria-*`, and the custom `dark:` variant after `focus-visible:` at equal specificity, so a state rule wins on the same property. A checked `Checkbox` replaces `focus-visible:border-primary` with `border-foreground`, and the checkbox in the agent permanent-delete dialog shows no focus once checked.
- When state and focus share a value or hue, the change is invisible: a checked radio item is already `border-primary`, and the `Switch` inset ring measures 1.16:1 before/after focus over the track of a switch that is on.
- `--ring` is the primary color at 40% alpha, so the inset ring tried in #25041 reached about 1.3:1.
- `SelectItem` adds `data-[state=checked]:bg-primary/10` (0b3cefb125) on top of shadcn's `focus:bg-accent`, so focusing the checked option changes nothing.
- `src/renderer/assets/styles/index.css` declares `@layer app { *:focus { outline-style: none } }`. The `app` layer follows `utilities`, so in every window that imports this file it suppresses all outline utilities.

## Proposal

Keyboard focus follows shadcn's two-part design: an opaque `--ring` border carries contrast, and a translucent halo outside the control marks focus even when a state owns the border.

1. `--cs-ring` in `packages/ui/src/styles/tokens/colors/providers.css` stays derived from the brand color, independent of the user's theme color, as the design token system documents, so an extreme user color cannot hide focus. It becomes opaque: `var(--cs-brand-700)` in the light theme (4.37:1 against white) and the current dark value without alpha, `oklch(0.76 0.204 131)` (8.79:1 against the dark background). `--ring` keeps the meaning documented in the custom CSS guide and the mini-app `/__cherry/theme.css` contract, the focus color; only its value changes.
2. The packages/ui base layer, generated by `packages/ui/scripts/build-theme-css.ts`, draws the halo for every element: on `:focus-visible`, a 3px solid outline of `--ring` at 40% alpha, with no offset. The halo is an outline rather than a `box-shadow`, so it does not interact with `shadow-*` utilities, and forced colors mode keeps it. The app-layer `*:focus` reset is removed. Every renderer window receives the rule through `@cherrystudio/ui/styles/theme.css`, including the screenshot, selection toolbar, and selection capsule windows, which import only `tailwind.css`.
3. Controls with a visible border change it to `--ring` on keyboard focus with `focus-visible:border-ring`, which replaces `focus-visible:border-primary`. This covers Input, Textarea, the Select trigger, Checkbox, RadioGroup items, and outline Button. When a state owns the border, such as a checked checkbox, a checked radio item, or an invalid input, the state wins and the halo alone marks focus. This loss is accepted.
4. Controls without a visible border keep their current focus fill or text change and gain the halo. This covers filled, ghost, and link Button variants, Tabs triggers, and the buttons of `menu-list`. The `Switch` inset ring is removed, and the halo alone marks focus on the switch.
5. Controls drop the `outline-none` or `outline-hidden` that would hide the halo. Text-entry controls also match `:focus-visible` after a pointer click; this is browser behavior and is accepted.
6. Popup containers that Radix focuses as a landing point opt out in their packages/ui primitive with `outline-none`: menu, context menu, popover, hover card, dialog, alert dialog, sheet, drawer, and Select content. Radix Menu focuses its content on every open, and Chromium marks a script focus as `:focus-visible` after keyboard input or before any input.
7. Items that receive focus inside a popup list follow shadcn. These are the `menuitem` and `option` items of menus, Select, and Command. The accent background shows the current item, and no halo is drawn. Checked state does not use a background: `SelectItem` drops `data-[state=checked]:bg-primary/10` and keeps its check mark.
8. Where a container clips the halo (scroll viewports, `overflow: hidden`), the container gets padding. Where a sibling paints over the halo, the focused control is raised. Both are established during the keyboard walkthrough.
9. `DESIGN.md` § Focus is rewritten to these rules.

The work ships as a stack: (1) this Spec, `DESIGN.md`, the global rule, the token, and the packages/ui primitives; (2) renderer call sites; (3) the keyboard walkthrough, padding, and stacking fixes.

The walkthrough routes are the Settings pages General, Appearance, Selection Assistant, and Model Provider; the chat page sidebar, message actions, and composer toolbar; the agent permanent-delete dialog; and the selection toolbar window.

## Alternatives considered

- An opaque outer outline (2px, 2px offset) reaches 3:1 for every control in every state, including borderless controls and states that own the border. The maintainer preferred the look of a translucent halo; the accepted cost is listed under Risks.
- A translucent halo alone cannot carry contrast: at 40% alpha, even black reaches only 2.85:1 on a white background.
- Reusing the border or fill alone, which is the current `DESIGN.md` rule, fails because state variants override the same property or already use the same value, and borderless controls have no border to reuse.
- An inset ring (#25041, closed) is not overridden, but it blends into the fill: about 1.3:1 for checked checkboxes and radio items, and 1.16:1 on a switch that is on.
- Restoring the per-call-site `focus-visible:ring-*` from before #17436 means about 80 call sites, each drawing a `box-shadow` that MDN documents forced colors mode removes. One global outline keeps the halo uniform.
- shadcn's newer Radix, Base UI, and React Aria styles define `data-checked` and `data-selected` with `:where()`, so the focus border wins over those states. This change does not adopt it because losing the border to state is accepted. Measured against the vega style, an invalid checkbox still shows no change on focus there.
- A separate `--primary-focus` token would duplicate `--ring`, which the custom CSS guide and the mini-app contract already define as the focus color.
- Deriving `--ring` from the user's theme color with a lightness clamp (`oklch(from var(--primary) min(l, 0.55) c h)` in the light theme) reaches 3:1 for a 38-color sweep. It was not adopted because the design token system keeps the ring independent of the runtime primary, and the maintainer kept that boundary.
- A global `:not([tabindex="-1"])` exclusion was rejected because `tabindex` does not say whether an element is a landing point. Select options and the unfocused items of roving groups also carry `tabindex="-1"`. The popup primitive is the code that knows its container is a landing point.
- A halo on popup list items would be clipped by the scroll viewport and overlap neighboring items. Lists driven by `aria-activedescendant` never move DOM focus to an item (cmdk `Command`, `EntitySelector`), so only a highlight can work there.

## Acceptance criteria

- AC1 — On the walkthrough routes, every control reached by keyboard shows a 3px halo of `--ring` at 40% alpha directly outside its edge in every state, including the checked checkbox in the agent permanent-delete dialog, a switch that is on, a checked radio item, an invalid input, and the active tab, in the light and dark themes. (verification: Electron keyboard walkthrough)
- AC2 — On keyboard focus, a control with a visible border that no state owns changes the border to `--ring`, and a borderless control keeps its focus fill or text change. (verification: Electron keyboard walkthrough)
- AC3 — A pointer click on a button, checkbox, radio item, switch, tab, or popup trigger draws no halo and no `--ring` border, and an open popup adds neither to its trigger. (verification: Electron pointer walkthrough)
- AC4 — Opening a menu, context menu, popover, dialog, sheet, drawer, or Select by keyboard or by pointer draws no halo around the popup container. (verification: Electron walkthrough)
- AC5 — In menus, Select, and Command lists, the accent background shows the current item, including when that item is checked, and a checked Select option shows its check mark without a background. (verification: Electron walkthrough)
- AC6 — The opaque `--ring` reaches at least 3:1 against the page background in the light and dark themes, whatever theme color the user selects. (verification: headless Chromium contrast check against the built tokens; Electron spot check of the dark theme on macOS)
- AC7 — On the walkthrough routes, no halo is clipped by a scroll viewport or overflow container, and no sibling paints over a halo. (verification: Electron keyboard walkthrough)
- AC8 — `DESIGN.md` § Focus documents the `--ring` border, the halo, the popup-container opt-out, and the popup-list highlight, and no longer forbids outer rings. (verification: docs gate)

## Risks

- Where a state owns the border, and on borderless controls, focus relies on the halo and any existing fill change. The halo stays below 3:1 there (about 1.7:1 on a white background and 2.4:1 on the dark background), so those cases do not meet WCAG 1.4.11 for focus indicators. This is accepted for appearance.
- User custom CSS and mini-apps that read `--ring` get an opaque color instead of 40% alpha. The release notes announce the change.
- Dark-theme contrast was computed against `#181818` under the translucent background token. With vibrancy on macOS, the real backdrop depends on the desktop, so AC6 includes an Electron spot check.
- Embedded editors whose content element is `contenteditable`, such as CodeMirror in `CodeViewer` and `PromptEditorField`, may start matching the global rule. Layer 2 checks each one and opts out where the editor frame already shows focus.
- Pointer-driven Radix flows can still produce a script focus that Chromium marks as `:focus-visible` (see the [tooltip pointer focus note](../../implemented/bug-fix/2026-11-19-tooltip-pointer-focus-restore.md)). AC3 and AC4 cover these flows in a real window.
- That forced colors mode keeps outlines comes from documentation and has not been verified on Windows.
