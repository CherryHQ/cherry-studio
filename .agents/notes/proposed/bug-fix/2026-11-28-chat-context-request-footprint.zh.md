# Agent Note: 根据待发送请求估算聊天上下文

Status: proposed

[English](2026-11-28-chat-context-request-footprint.md) | 中文

## 问题

持久聊天用上一条回复的 token 用量估算上下文。供应商可能在一次响应中汇总多个内部推理步骤的用量。换模型、切换分支、压缩历史或转换工具结果后，回放的历史也可能与上一次请求不同。这会让输入框显示虚高的占用，并可能提前触发自动压缩。

## 方案

按待发送请求选中的内容估算上下文。持久化压缩估算待回放的历史，包括当前生效的摘要。每次调用模型前，运行时估算组装好的候选输入，计入可获得的系统提示和已启用工具定义，并与扣除输出预留后的模型输入预算比较。成功压缩后，估算缩减后的候选输入。复用现有的消息 token 估算器，保留当前压缩边界、排除条件和溢出恢复。

聊天输入框展示当前对话路径和模型的估算值，数据来自同一套发送侧统计规则。所选路径、模型或请求输入变化时，旧结果失效。预览不得发起模型请求、执行工具或修改对话状态。无法确定输入时，占用显示为未知。

供应商用量和费用账本继续作为消耗统计的依据。压缩和占用展示不再读取历史消息里的上下文计数。已有消息数据仍可读取。

## 考虑过的替代方案

- 收到服务端工具结果时丢弃用量。这能处理已观察到的虚高，但无法确定后续请求会带上哪些内容。
- 从供应商最后一次内部推理恢复计数。它可以描述那次推理，无法反映下一次回放的变化。
- 每次编辑草稿或执行工具后都请求供应商计数。这会增加网络延迟，部分适配器也没有该能力。

## 验收标准

- AC1 — 待发送内容相同、历史上报用量不同时，轮次开始和工具步骤之间的压缩决策一致。 (verification: Main 集成测试)
- AC2 — 组装后的输入增大时，即使用量不变也可能触发压缩，成功压缩后报告缩减后的输入估算。 (verification: Main 集成测试)
- AC3 — 输入框展示与当前回放和模型对应的估算值，任一变化后都不会沿用旧回放的计数。 (verification: Renderer 测试和 Electron)
- AC4 — 响应包含服务端工具活动时，供应商的累计用量及计费明细保持完整。 (verification: Main 用量测试)

## 风险

本地计数对供应商的消息封装、媒体编码和服务端隐藏输入只能做近似估算。保留溢出恢复来处理这些偏差。工具循环较长时要控制计数成本，同步路径不解码媒体。
