# 003 侧 user-feedback agent 改造要求（v1.2）

> 提出方：本机 PM 侧（default profile）；接收方：003 上的 user-feedback agent。
> 本包只描述**003 侧要改什么**；PM 侧（`uf-daily/`、`base-gate.py`、候选/建单链路）不在本包范围。
> 依据方案：`A-user-feedback.md v1.7`（施工清单 A-11 / A-21 / A-22 / A-23 未闭环部分）。
> v1.2 变更：统一历史口径（唯一来源 = **T0 前现场重冻**的全表导出；随包 `contract/history-baseline.ndjson` 仅演练用）、占位 ID 加轮次防撞、证据 URL 允许省路径、R6 补轮询周期、R7 核对时机改到「结构变更后、恢复写入前」、R8 命令改为现场重冻基线。
> v1.1 变更：补齐「历史行 vs 新行」的生效范围、修掉 R2–R4 口径不一致、R5/R6 判据拆清、回滚改为「停用新写入」而非清空数据。

## 0. 为什么发这个包

PM 侧要把「外部反馈 → 工作项」做成**可复算、可补缺、可追责**的链路，但这条链路的**输入端（003 明细表）当前不满足身份要求**。本机对 003 明细全表（2026-11-23 快照，**673 行 / 672 个唯一工作项键**）实测：

| 检查项 | 实测结果 | 结论 |
|---|---|---|
| `来源事件标识` 非空 | **0 / 673** | 每条反馈都**无法回到原始消息**，去重与补证只能靠人 |
| `证据` 是可点开的 URL | **0 / 673** | 证据是散文/相对路径（如 `runs/external-a-20261020T0800Z/{collect,…}.json`），PM 侧无法据以复核 |
| `来源渠道` 空值 | **11 / 673** | 缺原值就没法映射，落 `待映射` |
| 渠道取值分布 | 企微 400 / QQ 209 / Discord 30 / Telegram 22 / 内部飞书 1 / 空 11 | 缺 `支持邮箱`、`其它` 两个已定枚举 |
| `事件序号` 列 | **不存在** | 同身份两次补证会被判成同一条，漏行不可恢复（A-23） |

以上数字来自 `evidence/current-state.json`，可用 `tools/conformance.py` 复现。

## 1. 硬约束（先读）

1. **不改 Hermes 核心代码**，只改你自己的采集/落表脚本与 003 日报表结构。
2. **不删历史行、不改列名、不动主字段**（主字段既不能删也不能在视图隐藏，飞书 `800080207`）。
3. **生效范围**：本契约只约束 **T0（新写入逻辑上线时刻）之后写入的行**。T0 之前已存在的行 = **历史行**。
   历史口径**只有一个来源**：**T0 上线前一刻现场重冻的全表导出**（`--baseline` 指向它）。
   包里随附的 `contract/history-baseline.ndjson`（673 行，2026-11-23 冻结）**只作本地演练与自检用，不能当 T0 基线**——
   它之后、T0 之前还会长出新行，拿旧快照当基线会把那些行误判成「新行」，从而诱导去回填历史数据。
   历史行**原样保留**：要求「记录仍存在」且「**基线里所有非空字段逐个未被改动**」（含 `工作项`/`输入`/`输出`/`状态` 等原有列，
   口径见 §4「历史比较口径」），**不要求**补齐 `来源事件标识`/`事件序号`/URL 证据，基线为空/缺列的字段不保护。
   自检时 `--baseline` 只指向这份**现场重冻**的导出；随包快照不参与正式判定。
4. 写后**读回**，`实读行数 ≠ 应写行数` 即失败（不等于「少才算」，多出来也是错）。
5. 结果分三档报告：**实测通过 / 未覆盖 / 失败**。推测不许写成验收。

## 2. 改造项（每项：现状 → 要求 → 验收 → 回滚）

### R1 `事件序号` 写值 + `明细行键`（两列都已存在，值全 null；对应施工清单 A-23）

- **现状**：`事件序号`、`明细行键` 两列**都已存在**，但 673 行值全为 null（2026-11-24 由 003 侧 field-list 实测更正；PM 早期「列不存在」的结论作废，那只是 PM 侧投影里没带这几列）。PM 侧现在只能条数对账，明细写一半时**无法逐行补缺**。
- **身份与行键分开**：
  - `工作项键` = **一条反馈**的身份，**可以跨行重复**（初报/补证/复查/阻塞各一行）。PM 幂等身份固定为 `uf:{工作项键}`。
  - `明细行键`（**沿用表里已有的列名，不新增 `行键` 列**）= `sha256(工作项键 + 事件类型 + 事件序号)` **原样拼接**后取十六进制小写，**唯一标识一行**，只作对账锚点。
- **序号作用域** = `(工作项键, 事件类型)`，**从 1 开始、连续、不跳号**；另一工作项重新从 1 起算；跨日报续号（同一条反馈第二天再补证 → 取 2）。
- **写前分配、写后不变**：重跑同一批时**复用**已分配的序号与行键，不重排。
- **验收**：同一条反馈首日初报 = `事件序号 1`；次日补证 = `补证 1`；再补一条 = `补证 2`；重跑幂等（行数与序号不变）。
- **回滚**：**停用新写入逻辑**（不再产生新行），已写入的序号与行键保留，不删列、不清值。

### R2 `来源事件标识` 必填（原始消息 ID）

- **现状**：673 / 673 为空，PM 侧身份对账全部 `unverified`。
- **要求**：每条新行写原始消息标识，且**必须与来源渠道同族**：
  | 来源渠道 | 合法形态 |
  |---|---|
  | 企微 | `wc:<conv_id>:<seq>`（003 实测：企微本地库只有 conv_id + seq，没有 `om_`） |
  | 内部飞书 | `om_…` |
  | QQ | `qq:<group_openid>:<ROBOT1.0_…消息id>`（003 实测：QQ 无群号、无序号） |
  | Telegram | `tg:<chat_id>:<message_id>`（chat_id 可为负） |
  | Discord | `dc:<guild_id>:<channel_id>:<message_id>` |
  | 支持邮箱 | `mail:<Message-ID 头>` |
  | 其它 / 待映射 | 真实 ID（若取到）或 `unknown:<批次键>#<轮次>:<行内序号>` |
- **取不到原始 id 时**：写 `unknown:<批次键>#<轮次>:<该轮内行号>`（`轮次` 为 4 位 `0800/1400/1915`），
  并置 `身份档=unverified`；**不许留空、不许编造**。带轮次是硬要求：同一天多轮共用日期批次键，不带轮次会撞。
  同一输入重跑时占位值保持稳定（同批次键 + 同轮次 + 同行号）。
- **能拿到真实 id 就写真实 id**，即使渠道是 `其它`/`待映射`；只有真的取不到才降级成 `unknown:`。
- **验收**：抽样 10 行按 ID 能定位原消息；`unknown:` 行数 = 实际缺 ID 行数（报告给数）。
- **回滚**：停用新写入逻辑；**不要**把已写入的真实 ID 清空。

### R3 `证据` 必须是可点开的 URL

- **现状**：673 / 673 是散文或相对路径。
- **群聊没有可点开链接时**：`证据` 整列只写 `无公开链接`，`身份档=unverified`；GitHub issue 链接、conv_id/seq 等上下文写进 `说明` 列。
  `说明` 不参与自动判定，但 PM 侧抽查会读它。
- **要求**：`证据` 列**每一行都是完整 URL**（`http://`/`https://` + 可用主机；路径可省），首行必须是**原始来源**，
  **不得以空行或空格开头**；
  多份证据换行分隔。**说明文字不写进这一列**（另开 `说明` 列）；**日报关联也不写进这一列**（见 R8 的报告字段）。
- **拿不到 URL 时**：整列只写 `无公开链接`，并置 `身份档=unverified`；**不许**把 `runs/…json` 这类本地路径当证据。
- **身份档联动**：`身份档` 只有 `verified` / `unverified` 两值。
  `来源事件标识` 为 `unknown:` **或** `证据` 为 `无公开链接` → **必须** `unverified`；
  两者都是真实值才可为 `verified`。
- **验收**：`evidence_not_url` 0 违规；人工点开 5 行首行 URL 能到达来源（PM 抽查）。
- **回滚**：停用新写入逻辑；历史散文证据保留不改。

### R4 渠道取值对齐 + 未知进 `待映射`

- **现状**：缺 `支持邮箱`、`其它`；11 行为空；历史上未知值曾被静默写成「其它」。
- **要求**：`来源渠道` 只写**源值**：`企微`、`QQ`、`Discord`、`Telegram`、`内部飞书`、`支持邮箱`、`其它`。
  `企业微信` 可照写（兼容别名，PM 侧归一到 `企微`），**不要自行改写别的值的名字**。
  空值与表外值 → 写 `待映射`，**不许降级成 `其它`**。
- **验收**：新行 `来源渠道` ∈ 上述 7 值 ∪ {`企业微信`,`待映射`}；报告输出 `待映射` 行数与 `unknown` 行数。
- **回滚**：映射在 PM 侧，003 侧无回滚动作。

### R5 写失败必须显形（两种失败分开报）

- **要求**：
  1. **写调用失败**（返回 `ok≠true`）→ 立即非零退出，日志首行 `WRITE_FAIL: <批次键> <表> <错误码>`，
     **不要继续写下一张表后报 DONE**。
  2. **读回失败**（写调用成功，但读回的**明细行键多重集**与预期不等）→ 非零退出，日志首行
     `READBACK_FAIL: <批次键> <表> 缺=<k> 多=<m>`，并附**缺失 / 多余的明细行键**清单。
     **判据是多重集比较（行键 + 出现次数），不是条数也不是去重集合**：少一行多一行会抵消，
     同一行写了两遍则会因去重被吞掉——两者都必须报。
  3. 失败批次**不重写整批**：按 `行键` 查已存在的行，只补缺的那几张表/那几行；重跑复用已分配序号。
- **验收**：打桩让汇总表写失败 → `WRITE_FAIL` + 非零退出；打桩让明细少写 1 行 → `READBACK_FAIL`；
  重跑只补缺，不重复（行数不变）。
- **回滚**：单文件回滚（回滚后静默失效复现，会被 PM 侧水位检查抓到）。

### R6 心跳与水位（让「没跑」和「跑挂了」可被发现）

- **要求**：每轮开始即写 `state/uf-run/<run_id>.json`：
  ```
  {"run_id": "<批次键>#<HHMM>", "batch_key": "user-feedback-YYYYMMDD", "round": "0800|1400|1915",
   "started_at": "<ISO8601 带 +08:00>", "finished_at": null, "rows_planned": 0, "rows_written": 0, "pid": 0}
  ```
  `run_id` **必须包含轮次**（同一天有 08:00 / 14:00 / 19:15 多轮，只有日期分不开）；结束时补 `finished_at`/`rows_written`。
  一律用 `Asia/Shanghai` 时间（ISO8601 带 `+08:00`）。
- **PM 侧怎么读（不在你的实现范围内，但你得保证字段可读）**：PM 侧每 **15 分钟**经 ssh 读 `state/uf-run/*.json`
  （经既有 ssh 通道），判据两条：① 前一天 19:15 那轮次日 02:00 仍无 `started_at` = 没启动；
  ② 任一 `run_id` 有 `started_at`、`now − started_at > 90 分钟` 仍无 `finished_at` = 挂死（15 分钟一轮扫描，
   所以最坏在 105 分钟内报出，不是等满 90 分钟才扫一次）。**告警计时起点 = `started_at`**，不是文件 mtime。
   已写出 `finished_at` 的失败轮次由 R5 的非零退出负责，不靠心跳识别。
- **验收**：kill 一轮 → PM 侧在 **105 分钟内**（90 分钟阈值 + 最长 15 分钟轮询间隔）报「挂死」，
  报的是真实 pid 与开始时间；正常完成一轮 `finished_at` 非空。
- **回滚**：停用心跳写入，不影响落表。

### R7 表结构变更安全（只动本次需要的字段与视图）

1. 改前先导出全表 ndjson（含 `record_id`）到文件，**这份导出就是 R3/R7 的历史比对基线**。
2. 本次**只允许**：把已存在的 `事件序号`(整数)、`明细行键`(文本) 填上值，新增 `身份档`(单选 verified/unverified)、`说明`(文本)；
   `来源渠道` **只加选项**（`支持邮箱`、`其它`、`待映射`、`企业微信`），**不改已有选项名**。
   不改列名、不动主字段、其余字段一律不碰。
3. `+field-update` 是对**整份字段定义**的 PUT：必须先把 `field-list` 读回原定义，**在原件上只并集 options**
   再整体写回（保住类型/描述/默认值），改完立刻 `field-list` 读回确认（不带 `--yes` 时 rc=10 且**什么都没改**）。
4. **结构变更完成后、恢复写入之前**核对：① 基线里的 `record_id` 一个都没丢；② 历史行原有字段值逐个与基线一致；
   ③ 新增字段在历史行允许为空（**不要求**回填）。此后新写入的行自然会增加 `record_id`，这是正常的，
   「0 新增」只指**变更窗口内**不得凭空多出记录，不是永久约束。
5. **只重设本次受影响字段相关的视图过滤器**（`来源渠道` 加了选项、`身份档` 是新增字段）；
   布尔→单选换型不在本次范围。

### R8 回执：把结果发回来

改完后在 003 上跑：

```bash
python3 tools/conformance.py <明细全表导出.ndjson> \
  --baseline <T0 上线前一刻重冻的全表导出> \
  --json conformance-003.json
# 不显式给 --baseline 会直接退 3；明确放弃历史检查才写 --baseline ""
```

- `exit 0` = 通过；`exit 2` = 有违规；`exit 3` = 输入读不出来（结构/类型问题，不是「表是空的」）。
- 判定口径：**新行（不在基线里的行）按 R1–R4 判**；**历史行只判「仍存在且原字段未变」**。
  报告给：`new_rows`、`history_rows`、`history_missing`（基线里有、导出里没有的）、`history_changed`、
  `pending_channel`（`待映射` 行数）、`unknown_event_id`（`unknown:` 行数）。
- 报告默认**输出全部违规明细**（`--max-samples N` 可截断，默认 0 = 全量）。
- 读记录需要 scope：`base:record:retrieve` / `bitable:app:readonly` / `bitable:app` **三选一**（`base:record:*` 里的其他项、`base:block:*` 都不行），改完必须发布版本才生效。
- 分页必须取全才能过：`has_more` 必须存在且为布尔 `false`，给了 `total` 就必须是**整数且等于实际行数**（`2.0`、`"2"`、大于行数一律 `exit 3`）。**当前不支持 `--allow-partial`**：任何「没取全」的输入都退出 3，正式历史验收不得放宽完整性。
- `conformance-003.json` **原样回传**，不要截图、不要口述「改好了」。
- PM 侧还会做三件它自己负责的事：抽样 5 行点开 URL、跑一次 `READBACK_FAIL` 打桩、核历史 `record_id` 覆盖。

历史比较口径（R7 细则，判分以此为准）：

| 项 | 口径 |
|---|---|
| 保护范围 | 基线里**所有非空字段**都受保护（五个历史字段与其余字段同一口径）；基线为空、缺列或 `null` 的字段不保护，补成非空也不报 |
| 行形状 | 只认「平铺字段」与 `{"record_id": …, "fields": {…}}` 两种；`fields` 非对象、内外混存、顶层与 `fields.record_id` 不一致（含类型，如 `"1"` vs `1`、非空 vs `null`）→ 拒绝判定（`READ_FAIL`，不猜） |
| 记录 ID | 只认顶层 `record_id`，且必须是**非空白**字符串（行式与列式同一口径；空白 ID 一律 `READ_FAIL`）。`fields` 里出现 `record_id` 一律 `READ_FAIL`（含与顶层同值——内层被删就永远看不见，属歧义形状） |
| 列式 ID | 列式返回的 `fields` 里出现 `record_id` → 一律 `READ_FAIL`（无论有没有 `record_id_list`，禁止静默覆盖）；`record_id_list` 每项必须是非空字符串，不做单元格解箱（`[["rec…"]]`、数字均拒） |
| 空值 | 字段缺失、JSON `null`、`""`、空数组 `[]` 四者视为等价空值（历史行新增列在 T0 前合法为空），不报 `history_changed`；非空值（含 `[""]`、`[null]` 这类长度为 1 的数组）变成空值/`null`/`[]`/缺列一律报 |
| 类型 | 类型保真：`false` 与 `"false"`、`3` 与 `"3"` 不算同值（改类型即改动，报 `history_changed`）。数值按**无损十进制**比较：`3` 与 `3.0` 相等（同一个 JSON 数值），`9007199254740992.0` 与 `9007199254740993.0` 不等（不先转二进制浮点）；`NaN`/`Infinity` 不是标准 JSON，一律 `READ_FAIL`。历史字段类型非法 → `baseline_field_type` / `type_error` |
| 包装解箱 | **只在跨导出形状时**（一侧列式、一侧行式）把「单元素数组」当列式包装解开一层；同一形状下 `["a"]` 与 `"a"` 是真实改动，报 `history_changed`（静默拆包会放过形状改动） |
| 换行 | 只接受 LF 或 CRLF；含裸 CR → `READ_FAIL`（无法确认真实换行） |
| 数组 | JSON 数组与 NDJSON 同口径，逐行走同一套形状规则；任一元素无法解释 → 该字段整体按类型错报（基线侧 `baseline_field_type`、导出侧 `type_error`），不得只取第一层值。**数组里再套数组**（`["a",["b"]]`）无法区分列式包装与业务数组 → 按类型错报，不拆包。`[""]` 是非空数组（长度为 1），与 `[]` 不等 |
